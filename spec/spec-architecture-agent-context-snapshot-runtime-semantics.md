# Introduction

This specification defines the accepted runtime semantics for Agent Context Snapshot and Context Command behavior in Personal Symphony.

Source issue: [#37 Accept Agent Context Snapshot Runtime Semantics](https://github.com/MatheusBBarni/symphony-orchestrator/issues/37).

## 1. Purpose & Scope

The purpose is to define domain language and architecture boundaries before implementation changes Runtime Settings, Runtime State, Agent Prompt composition, or Runtime Home diagnostics.

This specification applies to the Product Repository implementation and to Workspace Repository Runtime Contract behavior.

Out of scope:

- Implementing Context Command execution.
- Implementing independent stage completion review.
- Installing or mutating global Codex lifecycle hooks.

## 2. Definitions

- **Workspace Repository**: The repository where the operator runs Personal Symphony.
- **Product Repository**: The Personal Symphony source repository.
- **Runtime Home**: The `.symphony/` directory in a Workspace Repository.
- **Runtime Contract**: Repository-owned Runtime Home files that define Personal Symphony behavior.
- **Runtime Settings**: The `.symphony/settings.json` portion of the Runtime Contract.
- **Runtime State**: Ignored Runtime Home files and backend snapshots that record current orchestration activity.
- **Agent Prompt**: The rendered task instruction sent to an agent.
- **Stage Goal Handoff**: A stage-specific Codex handoff that sets a Codex goal before the normal Agent Prompt.
- **Agent Context Snapshot**: A bounded, deterministic context section generated by the Symphony launch harness before agent launch or retry.
- **Context Command**: An optional operator-configured local command whose bounded stdout may supplement Agent Context Snapshot content.

## 3. Requirements, Constraints & Guidelines

- **REQ-001**: Agent Context Snapshot MUST be generated by the Symphony launch harness.
- **REQ-002**: Agent Context Snapshot MUST be scoped to the active Workspace Repository.
- **REQ-003**: Agent Context Snapshot MUST supplement, not replace, the Agent Prompt.
- **REQ-004**: Agent Context Snapshot MUST coexist with Stage Goal Handoff.
- **REQ-005**: Runtime Settings MUST own operator-configurable context behavior.
- **REQ-006**: Runtime State MAY expose context generation status and bounded diagnostics.
- **REQ-007**: Ignored Runtime Home diagnostics MAY store bounded metadata about context generation.
- **REQ-008**: `CONTEXT.md` MUST define accepted context terminology.
- **CON-001**: The implementation MUST NOT install or mutate global Codex lifecycle hooks.
- **CON-002**: The implementation MUST NOT store full Codex transcripts in the Runtime Contract.
- **CON-003**: The implementation MUST NOT persist `GITHUB_TOKEN`, `GH_TOKEN`, or local `.env` contents.
- **GUD-001**: Use precise names such as Agent Context Snapshot and Context Command instead of ambiguous phrases such as "full context."

## 4. Interfaces & Data Contracts

### Runtime Ownership

| Concern | Owner | Notes |
| --- | --- | --- |
| Enablement and limits | Runtime Settings | User-editable Runtime Contract. |
| Prompt injection | Agent Prompt composition | Generated immediately before launch. |
| Live status | Runtime State | Exposed to CLI/server/dashboard snapshots. |
| Debug metadata | Ignored Runtime Home diagnostics | Bounded and secret-free. |
| Domain terms | `CONTEXT.md` | Source of truth for glossary. |

### ADR Requirements

Any accepted runtime semantic change MUST be documented in `docs/adr/`.

## 5. Acceptance Criteria

- **AC-001**: Given implementation begins, When runtime context semantics are introduced, Then an ADR exists under `docs/adr/`.
- **AC-002**: Given `CONTEXT.md` is reviewed, When Agent Context Snapshot and Context Command are used, Then the terms are defined there.
- **AC-003**: Given Stage Goal Handoff is enabled, When Agent Context Snapshot is enabled, Then both mechanisms remain distinct and ordered.
- **AC-004**: Given Runtime Contract files are inspected, When diagnostics are generated, Then full prompts and secret values are absent.

## 6. Test Automation Strategy

- **Test Levels**: Documentation validation and backend tests in implementation slices.
- **Frameworks**: OCaml Alcotest for backend behavior.
- **Test Data Management**: Use temporary Workspace Repository fixtures.
- **CI/CD Integration**: Run `pnpm test` after implementation slices.
- **Coverage Requirements**: Each runtime semantic implemented later must have focused tests.
- **Performance Testing**: Not required for this design slice.

## 7. Rationale & Context

`codex-loop` uses Codex lifecycle hooks for continuation. Symphony already owns agent launch, Agent Worktrees, prompt writing, retries, and Runtime State. Therefore, the transferable design is harness-level bounded context generation, not global hook installation.

## 9. Examples & Edge Cases

```text
Stage Goal Handoff content, when enabled
---
Agent Prompt
---
Agent Context Snapshot, when enabled
```

Edge cases:

- Missing context settings means context behavior remains disabled.
- Context diagnostics must not make Runtime Contract files non-idempotent.
- Ambiguous domain terms must be rejected during documentation review.

## 10. Validation Criteria

- ADR exists and describes runtime ownership boundaries.
- `CONTEXT.md` includes accepted terms and avoid-list wording.
- Later implementation issues can reference this specification without redefining context semantics.
