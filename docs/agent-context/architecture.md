# Agent Context Architecture

Personal Symphony is the Product Repository. Users run the `symphony` CLI inside a Workspace Repository. In a Self-Dogfooding Workspace Repository, the same checkout is both roles, but Runtime Home ownership remains Workspace Repository scoped.

Runtime ownership:
- Bootstrap creates a Runtime Home at `.symphony/` in the Workspace Repository.
- Runtime Contract files are `.symphony/settings.json`, `.symphony/prompt.md`, and `.symphony/agents/*`.
- Runtime State, Runtime Diagnostics, Local Environment, and Agent Workspaces are ignored Runtime Home contents.

Dispatch model:
- GitHub Issues are work items and GitHub Projects `Status` is the dispatch board.
- Each dispatched task gets a Task Branch and an Agent Worktree under `.symphony/workspaces/`.
- The Loop-Start Worktree must be clean before a new Agent Worktree is created.
- Auto-merge is fast-forward only and skipped for Protected Trunk Branches.

Packaging:
- npm exposes `symphony` through `bin/symphony.js`.
- Published packages should include `vendor/symphony-linux-x64`, `vendor/symphony-darwin-x64`,
  `vendor/symphony-darwin-arm64`, and `vendor/symphony-win32-x64.exe`.
- Product Repository development falls back to `opam exec -- dune exec symphony --`.

## Accepted Agent Context path

Agent Context Snapshot is generated by the Symphony launch harness for a dispatched task. It is not a Codex lifecycle hook and does not install or mutate global Codex configuration.

High-level path:

1. Symphony loads Runtime Settings from `.symphony/settings.json`.
2. Missing `context` settings preserve existing Runtime Contract behavior and leave context disabled for that Stage Agent.
3. Invalid Stage Agent context settings are reported as Readiness Gaps before dispatch.
4. When a task is dispatched, Symphony creates or reuses the Task Branch and Agent Worktree.
5. Immediately before agent launch, the harness builds the normal Agent Prompt from stage instructions, Stage Skill Load, `.symphony/prompt.md`, issue data, and issue comments.
6. If enabled, Symphony generates an Agent Context Snapshot from deterministic launch data and appends it to the rendered Agent Prompt under `## Agent Context Snapshot`.
7. If a Context Command is configured, Symphony runs it synchronously before prompt write, then appends bounded stdout under `### Context Command` inside the Agent Context Snapshot.
8. If Stage Goal Handoff is enabled for the Stage Agent, Symphony prepends the Codex `/goal` command before the normal rendered Agent Prompt. The Agent Context Snapshot remains part of the normal prompt body after the Agent Prompt content.
9. Symphony launches the selected Agent Harness from the Agent Worktree and exposes Context Status through Runtime State.

The built-in snapshot currently includes the issue identifier and title, project status, labels, blockers, attempt number, Stage Agent, Task Branch, Agent Worktree, optional Loop-Start Branch, and Previous Attempt Output on retry launches. Previous Attempt Output is bounded stdout and stderr tail data from the immediately previous failed launch only; it is not a full transcript replay.

## Prompt coexistence rules

Agent Context Snapshot supplements the Agent Prompt and Stage Goal Handoff. It must not replace either.

Prompt ordering when all pieces are enabled:

```text
/goal {"kind":"Stage Goal Context", ...}

---

<Stage Agent instructions and Stage Skill Load>

---

<Agent Prompt rendered from .symphony/prompt.md plus issue data/comments>

---

## Agent Context Snapshot
...
### Context Command
...
```

Operationally:
- The Stage Goal Handoff carries deterministic issue and stage data to Codex before the normal prompt.
- The Agent Prompt remains the primary task instruction.
- The Agent Context Snapshot gives bounded launch-time context to the agent inside the normal prompt.
- A retry launch may include Previous Attempt Output inside the Agent Context Snapshot, after the built-in task fields.

## Runtime Settings examples

These are Runtime Settings fragments to merge into an existing `stageAgents.stages[]` entry. They are secret-free and do not include token values, webhook URLs, or Local Environment contents.

Enable only the built-in Agent Context Snapshot:

```json
{
  "states": ["Todo", "In Progress"],
  "agent": "engineer",
  "harness": "pi",
  "context": {
    "snapshot": {
      "enabled": true,
      "maxOutputBytes": 12000
    }
  }
}
```

Enable a Context Command from the Agent Worktree:

```json
{
  "states": ["Todo", "In Progress"],
  "agent": "engineer",
  "harness": "pi",
  "context": {
    "snapshot": {
      "enabled": true,
      "maxOutputBytes": 12000
    },
    "command": [".symphony/scripts/agent-context.sh"],
    "cwd": "agentWorktree",
    "timeoutMs": 30000,
    "maxOutputBytes": 12000
  }
}
```

Run a Context Command from the Workspace Repository root:

```json
{
  "states": ["In Review"],
  "agent": "reviewer",
  "harness": "codex",
  "context": {
    "command": [".symphony/scripts/review-context.sh"],
    "cwd": "workspaceRepositoryRoot",
    "timeoutMs": 15000,
    "maxOutputBytes": 6000
  }
}
```

Context setting rules:
- `context.snapshot.enabled` must be a boolean.
- `context.snapshot.maxOutputBytes`, `context.timeoutMs`, and `context.maxOutputBytes` must be positive integers when present.
- `context.command` must be an argv array with at least one non-empty string.
- `context.cwd` is either `agentWorktree` or `workspaceRepositoryRoot`; when omitted, it defaults to `agentWorktree`.
- `context.timeoutMs` defaults to `30000`.
- `context.maxOutputBytes` defaults to `12000` for Context Command stdout.
- `context.snapshot.maxOutputBytes` defaults to `12000` for the whole Agent Context Snapshot.
- A configured Context Command also requests an Agent Context Snapshot, even when the `snapshot` object is omitted.

## Context Command contract

A Context Command is a trusted local command owned by the Workspace Repository. Symphony runs it before writing the final Agent Prompt.

Inputs:
- stdin receives JSON with `kind`, issue identifier/title/status, Stage Agent, attempt number, Workspace Repository root, Agent Worktree path, and Task Branch.
- `SYMPHONY_CONTEXT_COMMAND_INPUT_PATH` points to a temporary JSON input file with the same payload.
- The command inherits the process environment, so commands should avoid printing secrets.

Outputs:
- Successful stdout is appended to the Agent Context Snapshot, bounded by `context.maxOutputBytes`.
- Oversized stdout is truncated and marked with a bounded warning.
- stderr is counted for diagnostics but is not injected into the Agent Prompt by default.
- Non-zero exits, missing executables, signals, and timeouts produce bounded prompt warnings instead of injecting command output.

## Failure behavior

Context warnings do not retry tasks by themselves.

Runtime behavior:
- Invalid context Runtime Settings create Readiness Gaps and must be fixed before dispatch.
- A missing Context Command executable records Context Status `failed`, includes a bounded warning in the Agent Prompt, and still launches the agent.
- A non-zero exit or signal records Context Status `warning`, includes a bounded warning, and still launches the agent.
- A timeout records Context Status `timed_out`, includes a bounded warning, and still launches the agent.
- Truncated successful stdout records Context Status `warning` because the prompt contains only bounded output.
- If the launched agent later fails, normal retry behavior applies. The retry is caused by the agent result, not by the context warning.

## Runtime State and diagnostics

Runtime State exposes context information without turning it into a primary task metric:
- `running[].context_status` and `retrying[].context_status` include `state`, `summary`, and `diagnostics_path`.
- Supported Context Status states are `skipped`, `succeeded`, `warning`, `timed_out`, and `failed`.
- Missing context status in older Runtime State snapshots should be treated as compatible absence; current snapshots render disabled or inapplicable context as `skipped`.
- The top-level `context_diagnostics` list summarizes recent persisted diagnostics.

Context Diagnostics are Runtime Diagnostics written under ignored Runtime Home state:

```text
.symphony/state/context-diagnostics/*.json
```

Diagnostic files are pruned to the Runtime State diagnostic retention cap (currently 100). They may include:
- diagnostic id and creation time;
- issue identifier, Stage Agent, and attempt number;
- Agent Context Snapshot enabled/rendered-byte/truncation metadata;
- Context Command name, cwd kind, exit code or signal, duration, timeout flag, stdout/stderr byte counts, truncation flag, and redacted error text.

Diagnostics intentionally do not persist:
- the full rendered Agent Prompt;
- full Stage Goal Handoff content;
- full Context Command stdout or stderr;
- `GITHUB_TOKEN` or `GH_TOKEN` values;
- Local Environment contents from `.symphony/.env`;
- Runtime Contract modifications.

There is no accepted Runtime Settings option in this release that persists full Context Command stdout. Diagnostic records keep `stdoutPersisted` false by default.
