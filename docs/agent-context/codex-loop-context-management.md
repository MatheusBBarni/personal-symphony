# Codex Loop Context Management Analysis

Date: 2026-05-05

## Purpose

This document analyzes `compozy/codex-loop` with one question in mind: how does it manage context across repeated Codex work, what tools does it use, and does it compress context in the harness or leave that to the model?

It is written as a planning artifact for Personal Symphony. It does not change the Runtime Contract yet. Any implementation that introduces new Runtime Settings, Runtime State files, or domain language should update `CONTEXT.md` and add an ADR under `docs/adr/`.

## Executive Findings

`codex-loop` does not implement full transcript compression in its harness. It keeps compact loop state in local JSON, then uses Codex lifecycle hooks to inject a new continuation prompt when Codex stops too early.

The harness does perform bounded context packaging. It stores the original task prompt, the latest assistant message, loop counters, timing, goal verdict metadata, and optional local command output. It does not summarize the full conversation or reconstruct prior turns.

For goal-based loops, `codex-loop` uses an LLM twice: first as an independent reviewer, then as a private structured-output interpreter. That is semantic judgment and verdict extraction, not general conversation compression.

The strongest transferable idea for Symphony is not Codex global hooks. Symphony already owns the agent launch harness, Agent Worktrees, Runtime State, and Agent Prompt composition. The transferable idea is a bounded, deterministic context snapshot that is generated by the harness immediately before launching or retrying an agent.

## What Codex Loop Does

Activation is explicit. A loop starts only when the first user prompt line contains a `[[CODEX_LOOP ...]]` header. The `UserPromptSubmit` hook parses that header, resolves a workspace root, supersedes older active loops for the same Codex `session_id`, and writes a `LoopRecord` under `${CODEX_HOME}/codex-loop/loops/`.

State is compact. `LoopRecord` stores fields like `task_prompt`, `activation_prompt`, `continue_count`, `last_assistant_message`, goal settings, and last goal verdict metadata. It does not store full conversation history.

Continuation happens through the `Stop` hook. When Codex stops, the hook resolves the active loop by `session_id`, updates `last_assistant_message` and counters, checks the limiter, and either marks the loop complete or returns hook JSON with `decision: "block"` and a generated `reason`. Codex treats that reason as the next continuation instruction.

`pre_loop_continue` is a synchronous harness-side context hook. It runs only after `codex-loop` has already decided to continue. The command receives structured JSON on stdin and through env vars, stdout is appended to the next continuation prompt, stderr is discarded, failures become short warnings, and output is capped by `max_output_bytes`.

Goal loops run an independent confirmation flow. The default confirmation command is `codex exec` with a configurable model and reasoning effort. It returns normal prose. Then `codex-loop` runs a fixed `codex exec --output-schema` interpreter to convert that prose into `{ completed, confidence, reason, missing_work, next_round_guidance }`.

Observability is deliberately small. Goal attempts append metadata to `${CODEX_HOME}/codex-loop/runs.jsonl`, but the README states that full task prompts, assistant messages, confirmation prompts, reviewer text, interpreter prompts, and `pre_loop_continue` output are not stored in that log.

## Tool Inventory

- Codex plugin lifecycle hooks: `plugins/codex-loop/hooks/hooks.json` registers `UserPromptSubmit` and `Stop`.
- Go CLI hook handlers: `codex-loop hook user-prompt-submit` and `codex-loop hook stop`.
- Local JSON state: `${CODEX_HOME}/codex-loop/loops/*.json` and `${CODEX_HOME}/codex-loop/runs.jsonl`.
- Runtime TOML config: global `${CODEX_HOME}/codex-loop/config.toml` plus nearest project `codex-loop.toml`.
- External local commands: `[pre_loop_continue].command` and `[goal].confirm_command`.
- Command parsing: shell-like strings are parsed to argv with `mvdan.cc/sh/v3/shell`, but executed without an implicit shell.
- LLM calls: `codex exec` for independent goal confirmation and fixed structured interpretation.
- Bounded buffers: captured command output is truncated by `max_output_bytes`.
- Plugin skill docs: the `codex-loop` skill teaches installation, activation, status, and config behavior.
- Development memory ledgers: `.codex/ledger/*` files preserve agent-session implementation memory, but they are not used by the runtime continuation flow.

## Harness vs Model Compression

`codex-loop` relies on Codex itself for normal session context and any model/provider-level compaction. There is no harness-level rolling summary of the transcript.

The harness adds a small amount of fresh context at continuation time:

- original task text;
- latest assistant message from the `Stop` payload;
- loop mode, counters, timing, and rapid-stop escalation state;
- goal confirmation verdict and reviewer text when applicable;
- optional `pre_loop_continue` stdout.

The model is used for two specific purposes:

- goal confirmation: inspect the Workspace Repository in a separate `codex exec` run and write prose;
- goal interpretation: convert reviewer prose into schema-valid verdict JSON.

The closest thing to compression is user-controlled `pre_loop_continue`: a script can summarize git status, test output, build status, or a checklist, and the harness injects that bounded stdout. The harness does not decide what that summary means.

## Implications For Symphony

Symphony should not copy `codex-loop`'s global Codex hook installation as the primary design. Codex hooks are useful for a single interactive Codex session. Symphony is already the harness that dispatches agents into Agent Worktrees, writes the prompt, captures stdout/stderr, controls retry, and owns Runtime State.

The equivalent Symphony design should be harness-level and Workspace Repository scoped:

- generate bounded context before agent launch or retry;
- inject it into the Agent Prompt;
- optionally allow a trusted local command to generate additional context;
- persist small diagnostics in Runtime State or ignored Runtime Home files;
- keep Runtime Contract files user-editable and deterministic.

The design should preserve existing concepts:

- Runtime Settings configure behavior.
- Runtime State records current orchestration activity.
- Agent Prompt remains the main task instruction.
- Stage Goal Handoff remains per-stage and supplements, not replaces, the Agent Prompt.
- Agent Worktrees remain the execution boundary.

## Recommended Direction

Build an opt-in harness-level context snapshot for Symphony agent launches and retries. Treat `codex-loop`'s `pre_loop_continue` as the model: structured input, explicit cwd, timeout, stdout-only prompt injection, bounded output, warning-on-failure, and no hidden mutation of Runtime Contract files.

Do not start with LLM transcript summarization. The first useful version should be deterministic and local:

- issue identifier, title, current status, attempt, labels, blockers;
- stage agent name and target stage transition;
- Agent Worktree path and Task Branch;
- git status summary from the Agent Worktree;
- recent stdout/stderr tail from the previous attempt when retrying;
- last known Goal Usage if Stage Goal Handoff is enabled;
- optional command-generated context.

Add LLM-based completion review only as a separate feature. It is closer to `codex-loop` goal confirmation than to context compression, and it changes stage completion semantics enough to deserve its own ADR.

## Issue Candidates

### 1. Define Symphony Context Snapshot Semantics

Create an ADR and glossary update for candidate terms such as `Agent Context Snapshot` and `Context Command` if those names are accepted.

Acceptance criteria:
- The ADR states that context generation is harness-level, not a Codex lifecycle hook.
- The ADR defines what belongs in Runtime Settings, Runtime State, Agent Prompt, and ignored Runtime Home files.
- The ADR explicitly says the snapshot supplements the Agent Prompt and Stage Goal Handoff.
- `CONTEXT.md` contains accepted terms and avoid-list wording.

### 2. Add Runtime Settings For Optional Context Commands

Extend `.symphony/settings.json` parsing with an opt-in context command configuration. Do not change Runtime Contract defaults without operator approval.

Candidate shape:

```json
{
  "stageAgents": {
    "stages": [
      {
        "states": ["Todo"],
        "agent": "engineer",
        "context": {
          "command": [".symphony/scripts/agent-context.sh"],
          "cwd": "agentWorktree",
          "timeoutMs": 30000,
          "maxOutputBytes": 12000
        }
      }
    ]
  }
}
```

Acceptance criteria:
- Missing `context` means disabled.
- `command` is an argv array, not a shell string.
- `cwd` is constrained to `workspaceRepositoryRoot` or `agentWorktree`.
- Invalid config creates a Readiness Gap before dispatch.
- Tests cover parsing, defaults, disabled config, invalid cwd, invalid command, and stage-specific override behavior.

### 3. Implement Deterministic Context Snapshot Rendering

Add a pure renderer that builds a bounded markdown section before launch.

Acceptance criteria:
- Snapshot includes issue metadata, attempt, stage agent, Task Branch, Agent Worktree path, and current status.
- On retry, snapshot includes a bounded tail or summary of previous stdout/stderr.
- Snapshot is appended after Stage Goal Handoff and stage agent instructions, under a stable heading.
- Output has deterministic ordering and size caps.
- Tests cover initial launch, retry launch, Stage Goal Handoff coexistence, and max-size truncation.

### 4. Implement Context Command Execution

Run the optional context command synchronously before the prompt is written.

Acceptance criteria:
- The command receives structured JSON on stdin.
- The same JSON is written to a temp file and exposed as an env var path.
- Only stdout is injected into the Agent Prompt.
- Stderr is captured for diagnostics but not injected into the prompt by default.
- Timeout, non-zero exit, missing executable, and oversized output produce a bounded warning section instead of blocking dispatch.
- Command execution cannot run outside the selected Workspace Repository or Agent Worktree cwd.
- Tests use real temp scripts and isolated Runtime Home paths.

### 5. Persist Small Context Diagnostics

Record enough information to debug context generation without logging sensitive prompts wholesale.

Acceptance criteria:
- Runtime State shows whether context generation succeeded, was skipped, timed out, or failed.
- Ignored Runtime Home diagnostics may include command name, exit code, duration, truncation flag, and output byte count.
- Full stdout is not persisted unless a setting explicitly enables it.
- No secret values from `GITHUB_TOKEN`, `GH_TOKEN`, or local `.env` contents are written.

### 6. Add Readiness And Dashboard Surfacing

Expose context command misconfiguration before dispatch and runtime failures during orchestration.

Acceptance criteria:
- Readiness Gaps explain exactly which stage context command is invalid.
- The Web Dashboard can show context status per running or retrying task without becoming a primary metric.
- Context failures do not move a task to retry by themselves unless the future ADR explicitly chooses stricter behavior.

### 7. Consider Independent Stage Completion Review

Evaluate a separate feature inspired by `codex-loop` goal confirmation: after an agent exits successfully, run a read-only reviewer before Stage Commit or status transition.

Acceptance criteria for the design issue:
- Decide whether this is per-stage Runtime Settings or a separate command mode.
- Decide whether failed confirmation retries the task, moves it to attention, or adds reviewer guidance to the next attempt.
- Decide whether review output is interpreted by schema, like `codex-loop`, or by a deterministic external tool.
- Add an ADR before implementation because this changes runtime completion semantics.

### 8. Update Documentation And Tests

Document context behavior after the architecture is accepted.

Acceptance criteria:
- `docs/agent-context/architecture.md` names the new context path at a high level.
- Runtime Settings examples are secret-free.
- Backend tests cover config parsing, prompt composition, command execution, Runtime State exposure, and retry behavior.
- Focused backend tests run before final handoff; broader `pnpm test` runs for the completed slice.

## Non-Goals

- Do not install or mutate global Codex lifecycle hooks for Symphony context management.
- Do not store full Codex transcripts in the Runtime Contract.
- Do not expand full skill bodies into prompts; Stage Skill Load should keep using skill identifiers.
- Do not treat LLM review as a replacement for deterministic context snapshots.
- Do not auto-merge or clean up Task Branches differently as part of context management.

## Suggested Implementation Order

1. ADR and glossary update.
2. Runtime Settings parser and Readiness Gaps.
3. Deterministic snapshot renderer integrated into `compose_prompt`.
4. Optional context command runner.
5. Runtime State and dashboard status.
6. Separate design pass for independent completion review.
