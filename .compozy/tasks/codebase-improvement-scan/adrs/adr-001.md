# ADR-001: Use a Scoped Verified Backlog for Codebase Improvement

## Status

Accepted

## Date

2026-05-24

## Context

The codebase improvement idea targets the Product Repository for Personal Symphony. The user selected a V1 complete sweep across concrete defects, maintainability, and product polish, with maintainers and future agents as the primary beneficiaries.

Research found that the current verification baseline is green across documentation validation, frontend live-state tests, backend build, and backend tests. The same scan also found concentrated maintainer risk in large shared files, duplicated or narrow parsing logic, cross-surface Runtime State projection gaps, misleading dashboard copy, legacy-centered developer scripts, generated-artifact scan noise, ADR numbering drift, and unsafe control-flow or protocol surfaces.

External research reinforces the need for evidence-backed quality work rather than flat issue dumps. AI-assisted development increases code velocity, but industry reports from Sonar, Qodo, CodeScene, GitHub, and DORA emphasize verification, code-health prioritization, and explicit quality gates as the difference between useful acceleration and hidden maintenance debt.

The council debate surfaced one core tension: these findings share a boundary-hardening theme around Runtime Contract semantics under future-agent maintenance, but executing them as one broad refactor would be difficult to review and easy to partially complete without improving maintainer throughput.

## Decision

V1 will be framed as a scoped, verified codebase improvement backlog under a single maintainer-trust and Runtime Contract boundary-hardening umbrella. The idea should not authorize one broad cleanup branch or a large structural rewrite.

Each V1 backlog item must be independently reviewable and carry:

- A concrete defect, maintainability, or product-polish finding.
- Repo-local evidence.
- The affected product boundary or maintainer workflow.
- A measurable acceptance target.
- Required verification commands.
- A clear statement of whether it changes runtime semantics.

V1 should prioritize:

- Fast maintainer-trust fixes such as ADR numbering hygiene, generated-artifact scan guidance, misleading dashboard labels, and legacy-centered development script language.
- Guardrails that prevent future drift, especially docs/ADR validation and Runtime Contract terminology checks.
- Parser and Runtime Contract hardening where agent-authored files or Bootstrap defaults can drift.
- One cross-surface consistency slice, especially Web Dashboard vs Terminal Console Runtime State projection.
- One unsafe backend control-flow slice, such as replacing opaque impossible-state crashes with explicit errors.

Large structural changes, including broad splits of the backend test suite, major `orchestrator.ml` decomposition, HTTP/WebSocket server replacement, and wholesale Terminal Console rewrites, remain valid follow-up work but should be sequenced after characterization and scoped acceptance evidence.

## Alternatives Considered

### Alternative 1: Flat Complete Sweep

- **Description**: Treat all findings as one broad V1 cleanup effort.
- **Pros**: Captures the user's broad intent and could address many pain points at once.
- **Cons**: Creates an unreviewable scope across unrelated risk profiles and may hide unresolved semantic decisions behind mechanical cleanup.
- **Why rejected**: The council agreed that a flat sweep would be too hard to verify and too likely to become a partially completed maintenance epic.

### Alternative 2: Narrow Fast-Fix Bundle Only

- **Description**: Limit V1 to cheap, reversible fixes such as copy updates, ADR validation, generated-artifact scan cleanup, and one small defect.
- **Pros**: Easy to land, low risk, and quickly improves maintainer confidence.
- **Cons**: May leave the root ownership and Runtime Contract boundary problems intact.
- **Why rejected**: The codebase findings point to a shared boundary-hardening problem; V1 should preserve that architectural through-line even while delivering in small units.

### Alternative 3: Architecture Rewrite First

- **Description**: Start by splitting the largest hotspots and replacing broad shared modules before product-polish or guardrail fixes.
- **Pros**: Directly attacks the deepest maintainability problems.
- **Cons**: High review cost, high regression risk, and poor fit for an idea-stage V1 without fresh characterization.
- **Why rejected**: Current verification is green, so the right first move is measured hardening and backlog structure rather than a large rewrite.

## Consequences

### Positive

- Maintainers get a prioritized, evidence-backed backlog instead of a generic quality report.
- Future agents receive clearer boundaries, verification expectations, and safer scan inputs.
- Runtime Contract semantics stay central without forcing every structural fix into V1.
- Reviewability improves because each item must be independently testable.

### Negative

- Some deep hotspots remain out of scope for V1 implementation.
- The idea requires disciplined prioritization to avoid drifting back into a flat cleanup list.
- Writing acceptance evidence for each item adds upfront planning cost.

### Risks

- **Risk**: The backlog becomes too broad despite scoped delivery rules.
  **Mitigation**: Cap V1 to the highest-impact verified items and move structural refactors to V2+.
- **Risk**: Fast trust fixes ship without addressing the shared boundary issue.
  **Mitigation**: Tie each item to the affected Runtime Contract, Runtime State, tracker, frontend, TUI, docs, or maintainer workflow boundary.
- **Risk**: Refactors accidentally change runtime semantics.
  **Mitigation**: Require an explicit runtime-semantics flag and fresh verification evidence per backlog item.

## Implementation Notes

- The final idea should describe this as a backlog-generation and prioritization feature for maintainers, not a request to immediately implement every listed fix.
- PRD creation should preserve the verified-backlog shape: each downstream task should have a focused write scope, acceptance evidence, and required checks.
- Changes to Runtime Contract defaults, Task Branch cleanup, auto-merge defaults, npm package behavior, or large backend test structure still require the project-level ask-first rules.
