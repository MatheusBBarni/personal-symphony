# ADR-003: Use Non-Runnable Discovery Backlog in `_tasks.md` for MVP

## Status

Accepted

## Date

2026-05-24

## Context

The Codebase Improvement Scan PRD requires an Evidence-First Backlog with at least 15 findings. Each finding must include category, affected product boundary, priority, acceptance target, verification expectation, and runtime-semantics impact.

The technical design must choose where this backlog lives and how it relates to Compozy Task Step execution. The user selected `_tasks.md` as the primary output artifact, standard task-table shape plus per-finding detail sections as the representation, deferring a custom metadata validator to Phase 2, and treating MVP `_tasks.md` as non-runnable discovery output.

This decision intentionally separates backlog discovery from executable Compozy Task Steps. It avoids prematurely converting every finding into a runnable task before maintainers have reviewed prioritization, grouping, and runtime-semantics impact.

## Decision

For MVP, store the Evidence-First Backlog in `.compozy/tasks/codebase-improvement-scan/_tasks.md` as a non-runnable discovery artifact.

The file will contain:

- A standard-looking summary table for scanability.
- Per-finding detail sections below the table.
- Required finding metadata for every finding: stable id, title, category, boundary, priority, evidence, acceptance target, verification expectation, runtime-semantics impact, guardrail candidate flag, and deferred follow-up flag.
- Clear language that MVP `_tasks.md` is discovery output and should not be treated as an executable task list until Phase 2 conversion.

MVP validation will use a manual metadata checklist. `compozy tasks validate --name codebase-improvement-scan` is deferred until Phase 2, when selected findings are converted into executable `task_NN.md` files and a Compozy-compatible master task list.

## Alternatives Considered

### Alternative 1: Executable `_tasks.md` and `task_NN.md` Files Immediately

- **Description**: Convert every finding directly into runnable Compozy Task Steps during MVP.
- **Pros**: Enables immediate `compozy tasks validate` and downstream execution.
- **Cons**: Forces implementation sequencing before maintainers review the complete evidence-backed backlog.
- **Why rejected**: The user selected backlog quality as the primary outcome and chose a non-runnable discovery output for MVP.

### Alternative 2: Dedicated `_backlog.md`

- **Description**: Store findings in a separate `_backlog.md` file.
- **Pros**: Avoids ambiguity with Compozy's executable task artifacts.
- **Cons**: Adds another artifact outside the user's selected `_tasks.md` path and may be less visible in the standard Compozy workflow.
- **Why rejected**: The user selected `_tasks.md` as the primary artifact.

### Alternative 3: Custom Metadata Validator in MVP

- **Description**: Add a script that validates finding metadata completeness before any Compozy task validation.
- **Pros**: Gives deterministic validation for backlog quality.
- **Cons**: Adds new tooling before the first discovery backlog proves its shape.
- **Why rejected**: The user chose to defer the custom validator to Phase 2.

## Consequences

### Positive

- Maintainers can review the complete evidence-backed backlog before implementation decomposition.
- The MVP stays focused on discovery quality instead of execution readiness.
- Phase 2 can convert selected findings into executable Compozy Task Steps with better grouping and priority decisions.

### Negative

- MVP `_tasks.md` is intentionally not runnable by Compozy.
- Automated validation is weaker in MVP because custom metadata validation is deferred.
- The artifact name may confuse future agents unless the non-runnable status is explicit.

### Risks

- **Risk**: A future agent may run or validate the MVP `_tasks.md` as if it were executable.
  **Mitigation**: The TechSpec and `_tasks.md` must label the artifact as non-runnable discovery output and state that Phase 2 performs executable conversion.
- **Risk**: Manual validation misses required finding metadata.
  **Mitigation**: The TechSpec must include a required metadata checklist and completion criteria.
- **Risk**: Phase 2 conversion loses context from the discovery backlog.
  **Mitigation**: Each finding must use stable identifiers and complete per-finding detail sections.

## Implementation Notes

- Do not generate `task_NN.md` files during MVP unless the user explicitly changes direction.
- Do not claim `compozy tasks validate --name codebase-improvement-scan` passes for MVP discovery output.
- Phase 2 should create executable task files only after maintainer review of the discovery backlog.
