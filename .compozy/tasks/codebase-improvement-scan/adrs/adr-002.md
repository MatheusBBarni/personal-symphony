# ADR-002: Select Evidence-First Backlog PRD Approach

## Status

Accepted

## Date

2026-05-24

## Context

The PRD for the codebase improvement scan must translate the approved idea into a business-focused product requirements document. The approved idea defines a maintainer-facing complete-sweep backlog for the Personal Symphony Product Repository. It optimizes for concrete defects, maintainability risks, and product-polish gaps that make future maintainer and agent work slower, riskier, or more ambiguous.

During PRD clarification, the user selected backlog quality as the primary outcome, maintainers planning backlog work as the primary persona, and 15 or more evidence-backed findings as MVP success. These choices prioritize a high-quality planning artifact over immediate implementation speed.

The main product tension is whether the PRD should optimize for a complete evidence-backed backlog, a smaller first implementation wave, or a narrower Runtime Contract boundary-hardening program.

## Decision

Use the Evidence-First Backlog PRD approach.

The PRD will define an MVP that produces at least 15 prioritized findings. Each finding must be actionable for maintainers and include repo-local evidence, category, affected product boundary, priority, acceptance target, verification expectation, and runtime-semantics impact.

The PRD will not treat V1 as an implementation project or a broad cleanup branch. It will focus on creating the planning artifact that downstream TechSpec and task generation can use to produce independently reviewable Compozy Task Steps.

## Alternatives Considered

### Alternative 1: Trust-Fix Launch PRD

- **Description**: Focus the MVP on the first 5-8 highest-confidence fixes, such as ADR uniqueness, dashboard copy, generated-artifact scan hygiene, and legacy dev-script friction.
- **Pros**: Faster to implement and likely to produce visible progress quickly.
- **Cons**: Too narrow for the user's selected complete-sweep intent and weaker as a PRD foundation for downstream planning.
- **Why rejected**: The user selected backlog quality and 15 or more evidence-backed findings as MVP success.

### Alternative 2: Boundary-Hardening Program PRD

- **Description**: Focus the MVP on Runtime Contract and Runtime State drift prevention, with backlog findings only when tied to those boundaries.
- **Pros**: Strong architectural coherence and clear relationship to future-agent safety.
- **Cons**: May under-cover product polish, general maintainability, and non-runtime defects found during the sweep.
- **Why rejected**: The user selected a broader complete-sweep backlog, not a narrowed Runtime Contract-only program.

## Consequences

### Positive

- The PRD directly matches the user's selected outcome and persona.
- Maintainers get a broad planning artifact that can feed TechSpec and task generation.
- Downstream work can remain scoped because each finding carries evidence and acceptance expectations.
- Product polish and maintainability findings remain in scope alongside Runtime Contract boundary risks.

### Negative

- The MVP produces planning value before implementation value.
- The backlog may require careful prioritization to avoid overwhelming downstream task generation.
- Some urgent-looking fixes may wait until after PRD and TechSpec completion.

### Risks

- **Risk**: The backlog becomes a flat issue dump.
  **Mitigation**: Require priority, affected boundary, acceptance target, and verification expectation for every finding.
- **Risk**: The PRD drifts into implementation design.
  **Mitigation**: Keep technical implementation choices for TechSpec and focus the PRD on maintainer capabilities and product outcomes.
- **Risk**: The complete-sweep promise expands beyond reviewable scope.
  **Mitigation**: Treat V1 as discovery and prioritization, with implementation deferred to downstream tasks.

## Implementation Notes

- The PRD should keep the phrase "maintainer-facing complete-sweep backlog" and preserve the distinction between backlog discovery and implementation.
- The PRD should list the existing idea-scope ADR and this approach ADR.
- The PRD should not prescribe code structure, parser design, test strategy, or implementation sequence.
