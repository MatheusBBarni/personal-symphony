# ADR-001: Scope the Terminal Console Settings MVP

## Status

Accepted

## Date

2026-05-17

## Context

The Terminal Console currently treats `w` as a non-mutating Web Dashboard handoff aid. The proposed MVP asks the Terminal Console to add a settings menu for theme selection and numeric Web Dashboard port input, then make `w` start the Web Dashboard server if it is not already started.

The primary user is a solo local developer operating Symphony from a Workspace Repository. Research and council review showed that this improves the Terminal Console as the main local control surface, but it changes the contract from handoff guidance to a local service action. That change must stay separate from orchestration and task lifecycle semantics.

## Decision

Ship a narrow Terminal Console settings MVP:

- Add a settings menu that exposes only theme selection and `server.port`.
- Persist the port through existing Runtime Settings semantics instead of introducing a second settings store.
- Keep theme selection scoped to the Terminal Console product surface and reuse existing TUI theme primitives where practical.
- Change `w` from guidance-only to an idempotent Web Dashboard local service action: if the compatible dashboard server is already running for the current Workspace Repository and Runtime Home, report it; otherwise start it and show the dashboard URL.
- Document the Terminal Console boundary change as local service control, not orchestration state mutation.

## Alternatives Considered

### Alternative 1: Guidance-only Web Dashboard handoff

- **Description**: Keep `w` as a command-and-URL hint and require users to run `symphony --web --port <port>` outside the Terminal Console.
- **Pros**: Preserves the current non-mutating Terminal Console contract; avoids process ownership and port collision handling.
- **Cons**: Leaves the requested TUI-first setup pain unsolved; keeps dashboard startup as an external context switch.
- **Why rejected**: The feature's core value is making the Terminal Console a practical local cockpit. Guidance-only behavior does not validate that value.

### Alternative 2: General settings platform

- **Description**: Build a broader Terminal Console settings framework for many Runtime Settings and future options.
- **Pros**: Creates reusable UI and validation patterns for future configuration.
- **Cons**: Adds schema, migration, validation, persistence, and UI design work before there is evidence that broader settings belong in the Terminal Console.
- **Why rejected**: The MVP only needs theme and Web Dashboard port. A platform would delay learning and increase maintenance surface.

### Alternative 3: Live-only settings

- **Description**: Let the Terminal Console hold theme and port choices only in memory without writing Runtime Settings.
- **Pros**: Avoids editing Runtime Settings from the TUI.
- **Cons**: Creates a second behavior source that diverges from `.symphony/settings.json` and CLI `--port` expectations.
- **Why rejected**: It would be harder to explain and would create the second control plane the council warned against.

## Consequences

### Positive

- Reduces setup friction for solo developers who want to stay inside the Terminal Console.
- Makes Web Dashboard access discoverable and actionable from the same local surface.
- Keeps V1 small enough to test whether settings belong in the Terminal Console.

### Negative

- `w` now has a side effect: it may start a local HTTP service.
- The implementation must define idempotent server ownership, dashboard URL reporting, and port conflict behavior.
- The Terminal Console contract needs documentation updates because handoff guidance becomes local service control.

### Risks

- **Unsafe server attachment**: The TUI might mistake an unrelated listener on the configured port for Symphony. Mitigate by detecting only compatible dashboard servers tied to the current Workspace Repository and Runtime Home.
- **Network exposure**: Port configuration could accidentally expose runtime state. Mitigate by keeping V1 loopback-only and preserving existing dashboard auth behavior for non-loopback configurations.
- **Control-plane drift**: Future settings may be added casually. Mitigate by documenting that V1 covers only theme and `server.port`; additional settings require a separate product decision.

## Implementation Notes

- Keep product-specific Terminal Console behavior in `apps/backend/bin/terminal_console_tui.ml` and related backend runtime modules.
- Do not move product settings behavior into the reusable `apps/tui` package unless a later reusable toolkit need emerges.
- Add backend Terminal Console tests around settings menu state, theme selection, numeric port validation, `w` idempotency, port conflict behavior, and non-mutation of task lifecycle state.
- Update `CONTEXT.md` and, if needed, a project ADR when implementing this product contract change.
