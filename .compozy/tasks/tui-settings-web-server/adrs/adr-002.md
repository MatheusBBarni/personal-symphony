# ADR-002: Select Narrow Setup MVP Product Approach

## Status

Accepted

## Date

2026-05-20

## Context

The PRD flow for Terminal Console settings and Web Dashboard start evaluated three possible product approaches after codebase and market research:

- A narrow setup MVP centered on persistent Terminal Console appearance, persistent Web Dashboard port, and local dashboard start or reuse.
- A dashboard-first MVP centered on making `w` reliable before expanding settings.
- A broader local cockpit MVP that would add richer dashboard controls and more Runtime Settings coverage.

The primary user outcome selected for V1 is setup friction reduction for a solo local developer operating Symphony from a Workspace Repository. The user also selected persistent theme and port behavior, a start-or-reuse `w` action, loopback-only exposure from the Terminal Console, and a dedicated `s` shortcut for settings.

## Decision

Use the Narrow Setup MVP approach for the PRD:

- V1 optimizes for reducing setup friction inside the Terminal Console.
- The settings menu exposes persistent Terminal Console theme selection and persistent Web Dashboard port editing.
- The settings menu is opened with `s` and is visible in footer/help affordances.
- Pressing `w` starts or reuses a compatible loopback Web Dashboard for the current Workspace Repository and Runtime Home, then shows the dashboard URL.
- Terminal Console V1 does not edit non-loopback host exposure and does not become a general Runtime Settings editor.

## Alternatives Considered

### Alternative 1: Dashboard-First MVP

- **Description**: Prioritize `w` start, reuse, status, and failure handling first; keep settings limited to the dashboard port and defer theme persistence.
- **Pros**: Reduces launch risk and validates the most operationally visible behavior first.
- **Cons**: Leaves part of the setup-friction problem unresolved because users still cannot persist Terminal Console appearance from the console.
- **Why rejected**: The selected outcome is broader local setup friction reduction, not dashboard launch alone.

### Alternative 2: Local Cockpit MVP

- **Description**: Build a broader local control surface with settings, dashboard status, stop or restart controls, browser-open actions, and more Runtime Settings coverage.
- **Pros**: Creates a more complete operator cockpit and anticipates future workflow needs.
- **Cons**: Expands the MVP beyond the validated need and increases the risk of casual Runtime Settings scope creep.
- **Why rejected**: V1 should prove narrow setup value before adding more controls or a general settings platform.

### Alternative 3: Guidance-Only Terminal Console

- **Description**: Keep the Terminal Console read-first by showing commands and URLs without persisting settings or starting local services.
- **Pros**: Preserves the current non-mutating aid boundary.
- **Cons**: Keeps users switching to files and separate commands for the exact setup jobs this feature targets.
- **Why rejected**: It does not meet the selected setup-friction outcome.

## Consequences

### Positive

- Gives the Terminal Console a focused setup surface without turning it into a broad control plane.
- Lets solo local developers adjust the immediate operating experience and reach the Web Dashboard without leaving the console.
- Keeps the MVP small enough to validate before expanding local cockpit behavior.

### Negative

- Adds persistent settings behavior to a surface that was previously read-first.
- Changes `w` from handoff guidance to a local service action with user-visible side effects.
- Requires clear product language so users understand that task lifecycle state remains protected.

### Risks

- **Settings scope creep**: Future settings may be added without a product decision. Mitigate by documenting that V1 covers only Terminal Console theme and Web Dashboard port.
- **Unexpected exposure**: Users may expect host exposure controls in the settings menu. Mitigate by making V1 loopback-only and explicitly excluding host editing.
- **Ambiguous server reuse**: Users may not understand why Symphony refuses to attach to an unrelated process on the same port. Mitigate with explicit conflict and compatible-server messages.

## Implementation Notes

- Keep this ADR product-scoped; implementation details belong in the follow-up TechSpec.
- Update project-level product language during implementation if the Terminal Console definition changes from handoff guidance to local service control.
