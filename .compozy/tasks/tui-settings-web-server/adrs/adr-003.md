# ADR-003: Terminal Console Settings and Dashboard Service Architecture

## Status

Accepted

## Date

2026-05-20

## Context

The PRD requires a focused Terminal Console settings menu, persistent Terminal Console theme, persistent Web Dashboard port, and a `w` action that starts or reuses a compatible loopback Web Dashboard.

The existing Terminal Console is intentionally read-first. Its `w` key currently shows Web Dashboard handoff guidance only, and current domain docs say Terminal Console local aids must not change Runtime Contract files. The Web Dashboard server startup path currently lives in CLI mode branching and calls the blocking `Server.serve` loop directly. Runtime Settings already own `server.port`, while the Terminal Console theme is currently a product-specific hardcoded palette.

The technical design must preserve task lifecycle safety, avoid a broad Runtime Settings editor, keep non-loopback exposure outside V1, and make dashboard reuse distinguish Symphony dashboards from unrelated listeners.

## Decision

Use a narrow product-specific architecture:

- Persist Web Dashboard port by updating only `server.port` in the Runtime Contract at `.symphony/settings.json`.
- Persist Terminal Console theme in ignored Runtime Home UI state, not in the Runtime Contract.
- Add a focused settings modal to `apps/backend/bin/terminal_console_tui.ml` instead of creating a reusable settings framework in `apps/tui`.
- Extract dashboard service startup into a reusable backend service path that can run the Web Dashboard in-process on a background thread while sharing the current Terminal Console Runtime State handoff.
- Add a loopback-only dashboard identity endpoint so `w` can verify Workspace Repository, Runtime Home, dashboard mode, and auth requirements before reusing an existing server.
- Keep Terminal Console settings and `w` as local setup controls. They must not retry tasks, pause or resume dispatch, update tracker status, merge or push Task Branches, open pull requests, or mutate orchestration lifecycle state.

## Alternatives Considered

### Alternative 1: Store both port and theme in Runtime Settings

- **Description**: Add Terminal Console theme to `.symphony/settings.json` beside existing `server.port`.
- **Pros**: One persisted configuration file; easy to inspect and copy between repositories.
- **Cons**: Treats a local display preference as part of the repository-owned Runtime Contract and expands Runtime Settings scope for a UI-only concern.
- **Why rejected**: The PRD scopes theme to the Terminal Console product surface. Runtime Home UI state keeps that local preference out of the Runtime Contract.

### Alternative 2: Store both port and theme in local UI state

- **Description**: Avoid Runtime Contract writes from the Terminal Console and keep both values under ignored Runtime Home state.
- **Pros**: Preserves the previous read-first Runtime Contract boundary.
- **Cons**: Creates a second source of truth for Web Dashboard port that diverges from `symphony --web --port` and existing `server.port` semantics.
- **Why rejected**: The PRD explicitly expects the dashboard port to be a persistent Web Dashboard setting, and existing Runtime Settings already own that value.

### Alternative 3: Start a child `symphony --web` process

- **Description**: Pressing `w` spawns a separate CLI process for Web Dashboard mode.
- **Pros**: Keeps service ownership outside the Terminal Console process and reuses CLI mode behavior directly.
- **Cons**: Duplicates startup, creates separate Runtime State ownership, complicates process lifecycle, and can diverge from the in-process Terminal Console state the user is watching.
- **Why rejected**: Sharing the current Runtime State handoff gives `w` the dashboard view the user expects without launching another orchestration runtime.

### Alternative 4: Reuse by port only

- **Description**: If anything responds on the configured port, treat it as reusable.
- **Pros**: Simple check with minimal server changes.
- **Cons**: Unsafe and ambiguous; an unrelated local process could be mistaken for the Symphony Web Dashboard.
- **Why rejected**: The PRD requires compatible reuse for the current Workspace Repository and Runtime Home, so identity must be explicit.

## Consequences

### Positive

- Keeps V1 narrow while still meeting the persistent setup requirements.
- Reuses existing Runtime Settings ownership for dashboard port and avoids a duplicate port preference.
- Keeps local Terminal Console appearance out of the repository-owned Runtime Contract.
- Lets `w` serve the same Runtime State the Terminal Console is displaying.
- Makes port conflicts explainable by distinguishing compatible dashboard servers from unrelated listeners.

### Negative

- The implementation must add a safe, scoped Runtime Contract writer for `server.port`.
- The implementation must add new Runtime Home UI state for Terminal Console theme.
- The server startup path needs extraction before it can be called safely from the Terminal Console.
- Domain docs and project ADRs need updates because `w` becomes local service control and the settings menu can update one Runtime Contract field.

### Risks

- **Runtime Contract churn**: Rewriting `.symphony/settings.json` could disturb user formatting. Mitigate by using structured JSON parsing and preserving unrelated fields, with tests for unknown-field retention.
- **Thread ownership bugs**: An in-process server thread could block or crash the Terminal Console if not isolated. Mitigate by starting the blocking server loop only on a background thread and surfacing startup failures as status messages.
- **Incompatible reuse**: Identity checks could be too weak or too strict. Mitigate by matching normalized Workspace Repository and Runtime Home paths and treating mismatches as clear conflicts.
- **Scope drift**: A settings modal can invite extra Runtime Settings fields. Mitigate by limiting V1 to Terminal Console theme and `server.port`.

## Implementation Notes

- New backend source modules must be ReasonML (`.re`/`.rei`) unless editing existing OCaml files is unavoidable.
- Product-specific Terminal Console UI behavior belongs in `apps/backend/bin/terminal_console_tui.ml` or adjacent backend runtime code, not in the reusable `apps/tui` package.
- The implementation must add focused Alcotest coverage for settings persistence, theme loading, port validation, dashboard service start/reuse/conflict behavior, and non-mutation of task lifecycle state.
- Project-level documentation and ADRs should use the glossary terms Terminal Console, Web Dashboard, Runtime Home, Runtime Contract, Runtime Settings, Workspace Repository, and Live Dashboard Connection.
