# ADR-004: Readiness-First Queue Diagnostics

## Status

Accepted

## Date

2026-05-13

## Context

The approved PRD requires guided feedback when an operator passes bare Compozy slugs while the active tracker mode is not Compozy-backed. The current startup path reports queue parse problems before readiness and then uses **Readiness Gaps** for selected-tracker validation only after config load.

The technical question is where the new tracker-mismatch message should live. A parse-time error is earlier, but it cannot explain the active tracker kind because Runtime Settings have not been applied yet. A readiness-owned error has the full tracker context, but it moves the failure one phase later.

## Decision

Guided tracker-mismatch feedback for bare Compozy-style queue input will be produced in startup readiness after Runtime Settings load.

- Queue parsing will stay responsible only for structural input validity.
- Tracker-aware queue resolution will produce the canonical mismatch message when raw queue input requires Compozy-backed interpretation but the selected tracker kind is not `compozy_tasks`.
- The message will surface as a **Readiness Gap** before orchestration begins.

This keeps one canonical diagnostic path for the selected tracker context and aligns the new behavior with existing startup readiness reporting.

## Alternatives Considered

### Alternative 1: Parse-Time Queue Error

- **Description**: Reject bare Compozy-style slugs directly in `parse_ordered_queue_arg` before readiness state is built.
- **Pros**: Earlier failure and no readiness-phase queue mismatch branch.
- **Cons**: Cannot explain the actual tracker mismatch because the parser does not know the selected tracker context.
- **Why rejected**: The approved operator experience requires guided feedback tied to the active tracker mode.

### Alternative 2: Dispatch-Time Error

- **Description**: Accept the queue through startup and fail only when dispatch or candidate matching cannot resolve the raw entry.
- **Pros**: Minimal startup changes.
- **Cons**: Too late for an input-contract failure and inconsistent with current **Ordered Queue** validation semantics.
- **Why rejected**: Invalid queue input should block startup as a **Readiness Gap**, not fail mid-run.

## Consequences

### Positive

- Operators see the new mismatch error in the same reporting surface as other startup blockers.
- The diagnostic can reference the selected tracker kind and suggest the correct input style.
- The parser remains generic and simple.

### Negative

- Some inputs that previously failed as parse errors will now survive to readiness before failing.
- Queue validation becomes more dependent on the selected tracker's normalization rules.

### Risks

- Readiness and dispatch could diverge if they do not share the same resolution logic. Mitigation: reuse the same queue-resolution helper in readiness and orchestration.
- Error messages may become too generic if they are built from multiple call sites. Mitigation: keep one canonical tracker-mismatch message source in the queue-resolution layer.

## Implementation Notes

- Keep direct parse errors for empty entries, URLs, and cross-repository references.
- Report tracker mismatch and mixed-style Compozy input as readiness remediation, not parser remediation.
- Add end-to-end tests that verify the readiness message and confirm orchestration never starts in the mismatch case.
