# ADR-003: Tracker-Aware Ordered Queue Resolution

## Status

Accepted

## Date

2026-05-13

## Context

The approved PRD keeps the MVP narrow: bare **Compozy PRD Run** slugs are a shortcut only for `--queue` when `.symphony/settings.json` selects `tracker.kind = "compozy_tasks"`. The current implementation does the opposite of that boundary. `Ordered_queue.parse` canonicalizes selector forms early, stores only canonical `issue_identifier` values, and drives **Runtime State** and queue resume from those canonical identifiers.

The selected technical approach changes two assumptions:

1. **Tracker-aware normalization happens only after Runtime Settings load.**
2. **The queue should preserve the operator's original bare slug text in queue state rather than rewriting it to `compozy:<slug>` immediately.**

Those choices make the current queue representation too narrow for the new flow.

## Decision

The queue model will split raw queue input from resolved tracker identifiers.

- `Ordered_queue.parse` remains tracker-agnostic. It will continue rejecting structurally invalid entries such as empty values, URLs, and cross-repository references, but it will also accept opaque bare tokens without assigning them Compozy meaning.
- After Runtime Settings load, a shared tracker-aware resolution step will map raw queue entries to canonical identifiers by calling the selected tracker's normalization rules.
- The Compozy-backed **Issue Tracker** will accept either a legacy canonical selector (`compozy:<slug>`) or a bare slug during that resolution step, but the new MVP shortcut path requires bare-slug-only input when operators choose the shortcut style.
- **Runtime State** and persisted Ordered Queue state preserve the original queue text supplied by the operator.
- Queue validation, candidate matching, dispatch ordering, and issue lookup use ephemeral resolved canonical identifiers derived from the raw queue.

This decision refines ADR-001's earlier implementation note about persisted queue identity. Canonical Compozy identifiers remain the downstream issue identity for lookup, branch naming, and tracker behavior, but the queue state itself remains raw.

## Alternatives Considered

### Alternative 1: Canonicalize In `Ordered_queue.parse`

- **Description**: Extend the parser to recognize bare Compozy slugs and immediately rewrite them to `compozy:<slug>`.
- **Pros**: Simpler downstream state model and no extra queue-resolution phase.
- **Cons**: Pushes tracker-specific behavior into a generic parser and loses the original operator input before readiness or resume logic can inspect it.
- **Why rejected**: The selected approach keeps tracker meaning behind the selected **Issue Tracker** boundary.

### Alternative 2: Resolve Only Inside Tracker Lookup

- **Description**: Keep queue parsing and queue state unchanged, and let the Compozy tracker expand bare slugs only when `fetch_by_identifiers_detailed` runs.
- **Pros**: Minimal surface area at the tracker lookup boundary.
- **Cons**: Leaves queue resume, dispatch ordering, duplicate detection, and mismatch reporting without a shared normalized representation.
- **Why rejected**: The same raw-to-canonical mapping is needed by readiness, orchestration, and resume-sensitive queue logic.

## Consequences

### Positive

- The parser stays generic and does not become Compozy-specific.
- The product can preserve the exact queue input the operator typed, which matches the approved ad hoc terminal workflow.
- Downstream queue matching still uses canonical issue identifiers, preserving existing tracker and branch behavior.

### Negative

- Queue logic now needs a second representation: raw queue entries plus resolved canonical identifiers.
- Queue resume becomes intentionally input-style-sensitive. Restarting with `example-feature` is not the same queue run as restarting with `compozy:example-feature`.

### Risks

- Mixed raw and canonical Compozy selectors could create ambiguous queue behavior. Mitigation: reject mixed-style Compozy queue input in MVP.
- Duplicate detection must move partly into the tracker-aware resolution phase, because raw tokens such as `20` and `#20` or `MB-020` and `mb-20` normalize to the same canonical identifier. Mitigation: enforce duplicate checks on resolved identifiers after tracker normalization.

## Implementation Notes

- Extend `Ordered_queue.entry` to preserve raw queue text.
- Add a shared queue-resolution helper that returns raw-plus-canonical mappings for the selected tracker.
- Keep persisted Ordered Queue resume matching based on raw queue sequence.
- Keep downstream issue matching based on resolved canonical identifiers.
