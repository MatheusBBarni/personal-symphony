# ADR-004: Use the mb CLI as the minibeads integration boundary

## Status

Accepted

## Date

2026-05-08

## Context

The PRD requires Symphony to consume minibeads Local Issue Files and persist local status changes. Direct file parsing would give Symphony full control over frontmatter and Markdown edits, but it would also couple Symphony to minibeads storage details. minibeads exposes an `mb` command intended to operate on the local issue store.

The user selected CLI integration for V1 reads and writes. V1 also excludes local comments/notes because minibeads does not provide stable native comments semantics for this feature’s needs.

## Decision

The minibeads adapter will shell out to the `mb` CLI for issue discovery, issue lookup, readiness validation where possible, dependency/blocker data, and status updates.

Symphony will validate and normalize the data returned from `mb` into `Issue.t`. If `mb` output is missing required fields, reports invalid statuses, returns duplicate identifiers, or cannot read the local issue store, Symphony will surface deterministic Readiness Gaps or issue-level non-dispatchable errors.

V1 will not implement local comments/notes. The minibeads adapter will leave `Issue.comments` empty for local issues unless a later minibeads feature provides stable comment semantics.

## Alternatives Considered

### Alternative 1: Direct file parsing and frontmatter writes

- **Description**: Read and modify `.beads/issues/*.md` directly from Symphony.
- **Pros**: Full control over status updates and issue mapping.
- **Cons**: Couples Symphony to minibeads file internals and increases write-conflict risk.
- **Why rejected**: The selected V1 direction uses minibeads’ CLI as the integration boundary.

### Alternative 2: Hybrid CLI reads with direct status writes

- **Description**: Use `mb` for discovery but update status frontmatter directly.
- **Pros**: Can simplify status writes if CLI output lacks a needed operation.
- **Cons**: Splits ownership and can conflict with minibeads validation rules.
- **Why rejected**: V1 should keep one source of truth for local tracker mutation behavior.

## Consequences

### Positive

- Symphony depends on minibeads’ public command behavior rather than private file-editing details.
- Local tracker mutation semantics stay aligned with minibeads.
- Write-conflict handling can be concentrated around `mb` command failures.

### Negative

- V1 requires `mb` to be installed and available to the Symphony process.
- Tests need command stubs or a thin command runner abstraction.
- Some metadata may be unavailable until minibeads exposes it through stable CLI output.

### Risks

- **CLI output instability**: Mitigate by validating required fields and surfacing clear diagnostics.
- **Missing `mb` command**: Mitigate with a readiness gap explaining the installation/configuration requirement.
- **Incomplete comments support**: Mitigate by explicitly excluding local comments/notes in V1.

## Implementation Notes

- Prefer machine-readable `mb` output if available; otherwise define a minimal parser around stable CLI output only after confirming minibeads behavior.
- Keep command invocation rooted at the Workspace Repository.
- Treat all command output as untrusted input before mapping it into `Issue.t`.
