# ADR-006: Constrain V1 local identifiers and dashboard impact

## Status

Accepted

## Date

2026-05-08

## Context

Ordered Queue and Manual Task Merge currently parse GitHub-shaped numeric issue identifiers. The PRD requires local issue identifiers to work in operator flows, but V1 should remain tightly scoped. The user selected support for minibeads identifiers matching `mb-<number>` plus existing GitHub numeric identifiers.

The PRD also requires first-class local tracker visibility. During technical clarification, the user selected minimal dashboard change for V1: keep the Runtime State issue shape mostly unchanged, add tracker kind, and update dashboard wording rather than adding full local metadata rendering in V1.

## Decision

Ordered Queue and Manual Task Merge V1 will accept GitHub numeric identifiers and minibeads identifiers matching `mb-<number>`. URLs and cross-repository references remain invalid. Existence, terminal state, dispatchability, and merge eligibility are validated through the selected Issue Tracker.

Runtime State V1 will expose the selected tracker kind so Terminal Console and Web Dashboard surfaces can use tracker-neutral wording. The Web Dashboard will update labels and copy away from GitHub/project-specific language, but it will not add rich local metadata cards in V1.

## Alternatives Considered

### Alternative 1: Accept any non-empty tracker identifier

- **Description**: Let any non-empty string through initial parsing and rely on the selected tracker to validate it.
- **Pros**: Most flexible and future-proof.
- **Cons**: Larger validation surface and more risk for unsafe branch/path-derived identifiers.
- **Why rejected**: V1 should constrain local identifiers to the known minibeads shape.

### Alternative 2: Backend-rich Runtime State and dashboard rendering

- **Description**: Add tracker kind, labels, priority, blockers, and local issue file path to Runtime State and render all of them in the dashboard.
- **Pros**: Best operator visibility.
- **Cons**: Expands frontend scope beyond the selected V1 dashboard impact.
- **Why rejected**: The user selected dashboard wording and tracker kind only for V1.

## Consequences

### Positive

- Queue and merge selectors stay predictable for both GitHub and minibeads.
- Task Branch naming can use a narrower identifier normalization surface.
- Dashboard work stays scoped while removing misleading GitHub-specific copy.

### Negative

- Non-`mb-<number>` minibeads identifiers are out of V1 even if minibeads supports them later.
- Labels, priority, blockers, and local file paths will not receive expanded dashboard rendering in V1.

### Risks

- **Identifier mismatch with minibeads CLI output**: Mitigate by confirming `mb-<number>` from current minibeads behavior before implementation.
- **Operator visibility gap**: Mitigate by ensuring Runtime State still exposes existing issue state, errors, queue progress, and selected tracker kind.

## Implementation Notes

- Keep URL and cross-repository selector rejection.
- GitHub numeric selectors should continue accepting `20` and `#20`.
- minibeads selectors should normalize to the same canonical identifier that `mb` returns.
