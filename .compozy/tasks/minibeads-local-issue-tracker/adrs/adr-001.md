# ADR-001: Scope minibeads as an opt-in local tracker adapter

## Status

Accepted

## Date

2026-05-08

## Context

Personal Symphony currently uses the GitHub Tracker as the default Issue Tracker. Issue 68 proposes a minibeads-backed Local Issue Tracker for operators who do not want to use GitHub Issues, GitHub Projects, or GitHub API access.

The user selected an agent/operator workflow as the primary audience and a complete V1 scope covering issue lifecycle, labels, comments or notes, task links, and list/filter views. Research also showed that local Markdown trackers such as minibeads, issy, and flowtorio validate the repo-local issue-tracking pattern, while Linear and GitHub are moving issue workflows toward agent-driven execution.

The council surfaced two main tensions:

- A complete V1 must be usable enough for real operators, but it must not become a second project-management platform.
- Local Issue Files must enter Symphony through a shared Issue Tracker provider boundary, but they must also be treated as untrusted repository input.

## Decision

The minibeads Local Issue Tracker will be scoped as an opt-in Issue Tracker adapter, not a replacement for the GitHub Tracker and not a separate orchestration mode.

V1 will prove the full GitHub-free orchestration loop: Local Issue File discovery, lifecycle status mapping, dependency-aware readiness, dispatch into Stage Agents, Agent Prompt rendering, Task Branch naming, retries, Stage Commit, Stage Push, Task Branch Integration, and idempotent status writes back to the selected Local Issue File.

The V1 tracker experience will include the operator-visible metadata needed to manage this loop: labels, comments or notes, task links, and list/filter views. These fields must stay subordinate to Symphony's Issue Tracker contract and must not introduce independent project-management semantics.

The minibeads adapter must treat Local Issue Files as untrusted Workspace Repository input. It must validate frontmatter and Markdown structure, contain reads and writes to the selected local tracker root, sanitize issue identifiers before using them in paths or branch names, reject unsupported statuses deterministically, and avoid tracker status churn in unrelated Stage Commits.

## Alternatives Considered

### Alternative 1: Minimal local dispatch proof only

- **Description**: Support only local issue creation, active status, and dispatch.
- **Pros**: Smallest implementation surface and fastest proof of feasibility.
- **Cons**: Too thin for the user-selected V1; operators could not evaluate the real non-GitHub workflow.
- **Why rejected**: The local tracker must be usable enough to replace GitHub for agent/operator coordination, not only prove parsing.

### Alternative 2: Full local project-management platform

- **Description**: Build local tracker semantics that compete broadly with GitHub Issues, GitHub Projects, Linear, or Jira.
- **Pros**: Richer standalone product surface.
- **Cons**: High maintenance cost, semantic drift from Symphony's Runtime Contract, and unnecessary scope for issue 68.
- **Why rejected**: The product value is GitHub-free Symphony orchestration, not a general-purpose tracker.

### Alternative 3: Direct minibeads special path outside the Issue Tracker boundary

- **Description**: Add minibeads-specific code directly to orchestration, queue, merge, and dashboard paths.
- **Pros**: Could be faster for a one-off implementation.
- **Cons**: Creates parallel behavior and makes GitHub/local parity fragile.
- **Why rejected**: The Local Issue Tracker should strengthen the Issue Tracker abstraction and preserve one orchestration model.

## Consequences

### Positive

- Workspace Repository operators can run Symphony without GitHub API access.
- GitHub Tracker behavior remains the default and does not need migration.
- The Issue Tracker contract becomes clearer and less GitHub-shaped.
- Local Issue Files remain human-editable and reviewable in normal repository diffs.

### Negative

- The shared orchestration boundary needs refactoring before minibeads can be cleanly integrated.
- V1 still spans backend Runtime Settings, readiness, queue validation, manual merge validation, Runtime State, and dashboard views.
- Local Issue File status writes introduce repository churn that must be carefully isolated.

### Risks

- **Semantic drift**: Mitigate by normalizing all tracker behavior through the Issue Tracker contract.
- **Prompt or path injection from issue content**: Mitigate with strict parsing, path containment, identifier sanitization, and no execution from issue text.
- **Accidental GitHub regression**: Mitigate by keeping GitHub as the default and preserving existing GitHub Tracker tests.
- **Stage Commit pollution**: Mitigate by defining deterministic write locations and excluding unrelated tracker churn from Stage Commits.

## Implementation Notes

- Use the existing domain terms in `CONTEXT.md`: Workspace Repository, Runtime Home, Runtime Contract, Runtime Settings, Issue Tracker, GitHub Tracker, Local Issue Tracker, and Local Issue File.
- Treat `docs/adr/0023-minibeads-local-issue-tracker.md` as the Product Repository architecture decision already accepted for issue 68.
- Do not change Runtime Contract defaults in `apps/backend/lib/runtime_home.ml` without explicit approval.
- Do not overwrite existing `.beads/` content or existing Local Issue Files during Bootstrap.
