# ADR-002: Prioritize a first-class local tracker experience for V1

## Status

Accepted

## Date

2026-05-08

## Context

The idea phase established minibeads as an opt-in Local Issue Tracker for Workspace Repository operators who do not want GitHub Issues, GitHub Projects, or GitHub API access. During PRD clarification, the user confirmed that the primary V1 success signal is an end-to-end local run: one active Local Issue File can dispatch, progress, finish, and persist status without any GitHub settings or token.

The user also selected operator visibility and rich local issue metadata as secondary outcomes that should not be sacrificed. For GitHub behavior, the user selected a first-class tracker-choice stance: GitHub remains the default, but documentation and Runtime Settings should present minibeads as an equal first-class option through a clear settings property.

## Decision

The PRD will use the first-class local tracker experience approach for V1.

V1 must prove the GitHub-free orchestration loop, but the product experience should not stop at backend dispatch. The Local Issue Tracker must be understandable and operable through the user-facing Symphony workflow: clear tracker selection in Runtime Settings, documentation that treats minibeads as a first-class option, visible local issue state, blockers, errors, queue progress, and useful local issue metadata such as labels, comments or notes, task links, and priority.

GitHub remains the default Issue Tracker. minibeads is an equal first-class option when explicitly selected, not the new default and not a migration requirement.

## Alternatives Considered

### Alternative 1: End-to-end local run first

- **Description**: Make V1 acceptance center on one complete local run and keep visibility and metadata intentionally basic.
- **Pros**: Lowest scope risk and strongest validation of the core GitHub-free promise.
- **Cons**: Could ship a technically functional local tracker that still feels incomplete or hard to operate.
- **Why rejected**: The user selected a richer V1 experience that preserves operator visibility and metadata as required product outcomes.

### Alternative 2: Tracker choice and migration

- **Description**: Focus V1 on clear settings, documentation, and compatibility language for users moving from GitHub.
- **Pros**: Reduces adoption friction and communicates the new tracker model clearly.
- **Cons**: Underweights day-to-day local tracker operation and issue metadata.
- **Why rejected**: Tracker choice clarity is required, but not sufficient for the selected first-class local tracker experience.

## Consequences

### Positive

- Operators can evaluate minibeads as a real local tracker option, not only as a hidden dispatch backend.
- The Web Dashboard, Terminal Console, and documentation can communicate local tracker state in product language rather than GitHub-specific wording.
- Local Issue Files become a practical Workspace Repository workflow for agent/operator coordination.

### Negative

- V1 has a broader user-facing surface than a dispatch-only proof.
- Some local metadata and visibility requirements may need tight MVP boundaries to avoid becoming general project-management scope.

### Risks

- **Scope creep into a full tracker product**: Mitigate by tying every V1 capability to the Symphony orchestration loop.
- **GitHub default confusion**: Mitigate by documenting GitHub as the default and minibeads as an explicit first-class option.
- **Operator distrust if visibility is incomplete**: Mitigate by requiring clear local issue state, blockers, errors, and queue progress in V1.

## Implementation Notes

- PRD language should stay business-focused: user capabilities, outcomes, and visibility expectations.
- Technical implementation details belong in the later TechSpec.
- This ADR complements ADR-001, which scoped minibeads as an opt-in local tracker adapter.
