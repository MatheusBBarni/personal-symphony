# ADR-003: Introduce a shared Issue Tracker boundary

## Status

Accepted

## Date

2026-05-08

## Context

The PRD requires minibeads to behave as a first-class Local Issue Tracker while GitHub remains the default Issue Tracker. Existing orchestration code already injects candidate fetch and status update functions, but those functions are typed around `Github_tracker.t`. Ordered Queue, Manual Task Merge, readiness, poll retry behavior, and some terminal/dashboard copy also assume GitHub-specific identifiers or status semantics.

The internal `Issue.t` shape is already close to tracker-neutral and carries fields needed by both GitHub and minibeads: identifier, title, description, comments, priority, state, URL, labels, blockers, and timestamps.

## Decision

Introduce a shared `Issue_tracker` boundary that selects one concrete tracker adapter from Runtime Settings. The GitHub adapter will wrap existing `Github_tracker` behavior. The minibeads adapter will use the `mb` CLI for Local Issue File reads and writes.

The boundary must cover candidate fetches, issue lookup by identifier, status updates, readiness gaps, active-state checks, terminal-state checks, status order, identifier validation/normalization, and tracker poll error classification.

Orchestrator, Ordered Queue, Manual Task Merge, Runtime State population, and readiness code should depend on the selected tracker boundary rather than directly on `Github_tracker.t` where behavior must be shared.

## Alternatives Considered

### Alternative 1: Add a minibeads path beside GitHub code

- **Description**: Add conditional minibeads code directly inside orchestration, queue, merge, and readiness paths.
- **Pros**: Smaller initial refactor.
- **Cons**: Preserves GitHub coupling and creates parallel semantics.
- **Why rejected**: V1 must present minibeads as a first-class option without creating a second orchestration model.

### Alternative 2: Refactor only config and readiness first

- **Description**: Accept `tracker.kind = "minibeads"` and remove GitHub readiness gaps before integrating dispatch.
- **Pros**: Lower-risk first patch.
- **Cons**: Does not satisfy the PRD’s end-to-end local run requirement.
- **Why rejected**: The TechSpec needs a complete implementation path, not a partial preparatory change.

## Consequences

### Positive

- Shared orchestration paths become tracker-neutral.
- GitHub remains an adapter over existing tested behavior.
- minibeads can support dispatch, queue, merge, status transitions, and readiness through one contract.

### Negative

- Existing GitHub-shaped function signatures must change.
- Manual Task Merge and Ordered Queue need identifier parsing changes.

### Risks

- **GitHub regression**: Preserve existing tests and keep GitHub adapter behavior thin.
- **Over-abstraction**: Keep the boundary limited to operations required by current orchestration paths.

## Implementation Notes

- Do not introduce extra provider types that are not required by the PRD.
- Keep `Issue.t` as the common issue model unless implementation proves a field is missing.
- Preserve `tracker.kind = "github"` as the default.
