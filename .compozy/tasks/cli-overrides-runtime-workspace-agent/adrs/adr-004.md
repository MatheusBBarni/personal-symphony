# ADR-004: CLI Command Extraction for Override Testing

## Status

Accepted

## Date

2026-05-08

## Context

The PRD requires `symphony --help` coverage and clear unsupported-mode failures for runtime-only override flags. Current Cmdliner command construction lives in the executable entrypoint, while backend tests link the backend library. Testing help and parser behavior through the executable would exercise the real command but make tests depend on shelling out to a built binary.

## Decision

The CLI command construction will be factored into a backend library module that tests can call directly. The executable entrypoint will keep only process-level wiring, argv normalization, and `Cmd.eval'`.

Backend tests will call the factored command/module behavior to verify help output, unsupported-mode handling, duplicate flag behavior, and parse-time validation.

## Alternatives Considered

### Alternative 1: Shell Out To The Built Executable

- **Description**: Build the executable and run command-line invocations from backend tests.
- **Pros**: Exercises the actual binary end to end.
- **Cons**: Slower, more brittle, and harder to isolate expected parser behavior.
- **Why rejected**: Direct library tests are enough for parser/help behavior and fit the existing backend test style.

### Alternative 2: Manual Help Inspection

- **Description**: Rely on implementation review or manual `symphony --help` checks.
- **Pros**: No test harness changes.
- **Cons**: Does not satisfy the PRD's measurable help and unsupported-mode guarantees.
- **Why rejected**: The feature is user-facing CLI behavior and needs automated coverage.

## Consequences

### Positive

- Cmdliner help and failure behavior become testable without shelling out.
- The executable entrypoint becomes thinner.
- Future CLI behavior can reuse the same test surface.

### Negative

- The backend library or test stanza needs an explicit Cmdliner dependency.
- Refactoring command construction has a small blast radius around startup.

### Risks

- Tests may diverge from the actual executable if the entrypoint adds behavior outside the factored module. Mitigation: keep argv normalization and evaluation thin and avoid duplicate command definitions.

## Implementation Notes

- Move Cmdliner term construction from `apps/backend/bin/main.ml` into a backend module.
- Keep executable-specific `Sys.argv` normalization and `Cmd.eval'` in `main.ml`.
- Add focused backend tests for help text and unsupported-mode failure wording.
