# ADR-002: Full Issue-66 Runtime Override Scope

## Status

Accepted

## Date

2026-05-08

## Context

The PRD needs to choose the product approach for Runtime Settings Invocation Overrides. The approved idea targets issue 66 and lists five runtime-only flags: polling interval, Agent Worktree root, global concurrency, max turns, and retry backoff cap.

Discovery confirmed that most target fields already have observable runtime behavior. `agent.maxTurns` is the main risk because enforcement is unclear, but the selected product direction is to satisfy the full issue-66 scope and treat user-visible max-turn behavior as part of the implementation slice rather than deferring the flag.

## Decision

The PRD will use the Full Issue-66 Runtime Overrides approach. MVP scope includes all five flags:

- `--polling.intervalMs`
- `--workspace.root`
- `--agent.maxConcurrentAgents`
- `--agent.maxTurns`
- `--agent.maxRetryBackoffMs`

The product promise emphasizes automation ergonomics: scripts, scheduled runs, and maintainer dogfooding can tune one `symphony` process without editing the Runtime Contract. Unsupported command modes must fail clearly. MVP discoverability is limited to `symphony --help` wording for the new flags.

## Alternatives Considered

### Alternative 1: Runtime-Real Subset First

- **Description**: Ship only the overrides with already-observable behavior, then add `--agent.maxTurns` later.
- **Pros**: Reduces risk of exposing a misleading flag.
- **Cons**: Leaves issue 66 partially satisfied and splits a small feature across multiple releases.
- **Why rejected**: The selected product direction is full issue-66 coverage, with any max-turn behavior gap closed in the same implementation slice.

### Alternative 2: Diagnostics-Led Override Experience

- **Description**: Ship all five flags plus startup visibility for effective override values.
- **Pros**: Improves operator confidence and debugging.
- **Cons**: Expands MVP beyond the selected discoverability level and risks turning a narrow override feature into a diagnostics feature.
- **Why rejected**: Help text is sufficient for MVP discoverability; effective-config diagnostics remain a V2 opportunity.

## Consequences

### Positive

- The PRD fully satisfies issue 66's requested flag set.
- Operators get a complete, consistent one-run override surface.
- Maintainers avoid partially implemented user-facing scope.

### Negative

- The implementation must ensure `--agent.maxTurns` maps to real user-visible behavior.
- The release has less room to defer edge cases around max-turn semantics.

### Risks

- A shipped but ineffective max-turn flag would damage trust. Mitigation: acceptance criteria must require observable max-turn behavior.
- Help-only discoverability may be too sparse for some users. Mitigation: keep examples as a Phase 2 option if support questions appear.

## Implementation Notes

- Keep this ADR product-scoped. Implementation details belong in the future TechSpec.
- The PRD should state the user-facing behavior and acceptance criteria, not prescribe the internal design.
