# ADR-001: Narrow Runtime Settings Invocation Overrides

## Status

Accepted

## Date

2026-05-08

## Context

Issue 66 asks Symphony to support command-line overrides for selected Runtime Settings values used by one `symphony` process. The target users are automation authors and Product Repository maintainers who need to tune a run without editing the Workspace Repository Runtime Contract in `.symphony/settings.json`.

The council agreed that command-line overrides are useful only when they are process-local, non-persistent, clearly documented, and behaviorally truthful. The main risk is semantic drift: `--workspace.root` could be mistaken for a Workspace Repository selector, and `--agent.maxTurns` would be misleading if the parsed Runtime Settings field is not enforced by orchestration.

## Decision

V1 will keep a fixed allowlist of Runtime Settings Invocation Overrides for issue 66:

- `--polling.intervalMs`
- `--workspace.root`
- `--agent.maxConcurrentAgents`
- `--agent.maxTurns`
- `--agent.maxRetryBackoffMs`

Each shipped override must affect real runtime behavior for the current process only, must not rewrite `.symphony/settings.json`, and must not change Bootstrap defaults. Workspace Repository root validation remains earlier than override application. The implementation should normalize CLI values into a small typed override record at the Runtime Settings load boundary rather than mutating config fields across orchestration call sites.

If `agent.maxTurns` is not currently enforced, V1 must either make that behavior real before exposing `--agent.maxTurns` or defer that flag from the shipped override set.

## Alternatives Considered

### Alternative 1: Generic Dot-Path Runtime Settings Overrides

- **Description**: Add a generic mechanism that maps arbitrary nested CLI keys to Runtime Settings fields.
- **Pros**: Extensible and avoids adding a new parser term for each future setting.
- **Cons**: Creates a broad configuration platform, increases validation burden, and risks exposing Runtime Contract semantics that should remain repository-owned.
- **Why rejected**: V1 needs a narrow operational tuning surface, not a general Runtime Settings mutation language.

### Alternative 2: Persistent Settings Rewrite

- **Description**: Treat CLI values as updates to `.symphony/settings.json`.
- **Pros**: Future runs would naturally reuse the values.
- **Cons**: Violates the current-invocation requirement, creates repository churn, and risks committing local machine paths or temporary tuning.
- **Why rejected**: The feature exists specifically to avoid editing the Runtime Contract for one-off automation runs.

### Alternative 3: Ship All Five Flags Even If Some Are Unenforced

- **Description**: Expose the full issue-66 flag list immediately and rely on later work to close behavioral gaps.
- **Pros**: Matches the issue text quickly and gives users a complete-looking interface.
- **Cons**: Creates a false operational contract when a flag is accepted but ignored.
- **Why rejected**: Runtime Settings Invocation Overrides must be truthful. Tests must prove every shipped override changes effective behavior.

## Consequences

### Positive

- Automation authors can tune one run without dirtying Runtime Settings.
- Maintainers get a small, testable pattern for future invocation overrides.
- The Runtime Contract remains repository-owned and stable.

### Negative

- V1 requires focused CLI, config, help, and runtime behavior tests.
- `agent.maxTurns` may force a small behavior fix before the full flag set can ship.
- Future override requests will still require explicit product decisions.

### Risks

- Users may misunderstand `--workspace.root` as a Workspace Repository selector. Mitigation: help and docs must state that root validation still uses the current Workspace Repository before overrides are applied.
- Unsupported modes could accidentally accept runtime-only flags. Mitigation: test that `init`, `update`, and legacy positional `WORKFLOW.md` mode do not accept these overrides for V1.
- Invalid numeric values could be silently defaulted. Mitigation: CLI override parsing must reject zero, negative, decimal, empty, and non-numeric values before dispatch.

## Implementation Notes

- Parse runtime-only flags in `apps/backend/bin/main.ml`.
- Apply typed overrides at or immediately after `Config.from_settings_file`.
- Reuse the Runtime Settings path resolver for `--workspace.root`.
- Use strict positive-integer validation for integer overrides.
- Add help output wording that says each flag overrides `.symphony/settings.json` for the current invocation only.
