# ADR-003: Post-Load Runtime Override Application

## Status

Accepted

## Date

2026-05-08

## Context

The TechSpec must choose where Runtime Settings Invocation Overrides become part of the effective runtime configuration. The existing startup flow validates the Workspace Repository root, bootstraps the Runtime Home, loads `.symphony/settings.json`, and then uses the resulting config for readiness, Manual Task Merge, Web Dashboard, Terminal Console, and orchestration.

The PRD requires all five issue-66 flags to be accepted for the default runtime command. It also requires `.symphony/settings.json` preservation, clear unsupported-mode failure, help text coverage, and current-invocation behavior.

## Decision

Runtime Settings Invocation Overrides will be parsed by the default command and applied after `Config.from_settings_file` returns by copying the loaded `Config.t` with selected fields replaced. This keeps config-file loading unchanged and keeps Runtime Settings parsing separate from CLI invocation state.

The runtime command will pass the post-load effective config to existing readiness, Manual Task Merge, Web Dashboard, Terminal Console, and orchestration paths. The implementation will not add generic dot-path overrides or modify Runtime Settings files.

`--agent.maxTurns` will override the effective `agent.max_turns` field in the same post-load copy. This TechSpec will not add a retry-stop behavior change; that behavior remains a follow-up concern even though the PRD identifies it as a product risk.

## Alternatives Considered

### Alternative 1: Apply Overrides Inside `Config.from_settings_file`

- **Description**: Extend Runtime Settings loading to accept a typed optional override record and construct the final effective config in one place.
- **Pros**: Centralizes Runtime Settings and invocation precedence at the config boundary.
- **Cons**: Couples config-file loading to CLI invocation concerns.
- **Why rejected**: The selected technical direction keeps Runtime Settings loading unchanged and applies runtime-only values in the CLI startup layer.

### Alternative 2: Apply Overrides At Runtime Use Sites

- **Description**: Check override values directly where polling, Agent Worktree placement, concurrency, retry behavior, and Manual Task Merge use config.
- **Pros**: Minimizes changes to config loading and startup flow.
- **Cons**: Scatters precedence rules across orchestration and merge code.
- **Why rejected**: Runtime consumers should continue receiving one effective config object.

### Alternative 3: Implement Max-Turn Retry Stop Now

- **Description**: Treat `agent.maxTurns` as an enforced retry cap and stop scheduling retries once the configured cap is reached.
- **Pros**: Fully closes the PRD risk that `--agent.maxTurns` lacks observable runtime behavior.
- **Cons**: Changes retry semantics beyond override plumbing and may need separate behavioral review.
- **Why rejected**: The selected technical direction is to make the override effective in config now and defer retry-stop behavior.

## Consequences

### Positive

- Runtime Settings parsing remains stable.
- All existing runtime consumers receive one effective config value.
- The implementation stays narrow and avoids a generic override platform.

### Negative

- Override application lives outside the Runtime Settings parser, so future override fields must preserve the startup-layer copy pattern.
- `--agent.maxTurns` will not gain new retry-stop behavior in this TechSpec.

### Risks

- The PRD requires every shipped override to have observable user-facing behavior, while this decision leaves max-turn enforcement unchanged. Mitigation: call out the gap in the TechSpec risks and keep follow-up behavior explicit.
- Post-load copying can drift if `Config.t` grows. Mitigation: isolate copying in a small helper rather than ad hoc record updates in several branches.

## Implementation Notes

- Define a small runtime override type near CLI startup code or a backend module used by startup.
- Build an effective config by copying `Config.t` after settings load.
- Do not write `.symphony/settings.json`.
- Keep Workspace Repository root validation before settings load and override application.
