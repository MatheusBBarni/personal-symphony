# ADR-001: Adopt Parity-Gated Backend Terminal Console JSX Migration

## Status

Superseded by ADR-002

## Date

2026-05-21

## Context

Symphony already has a reusable **TUI Toolkit Package** with a `Tui.Jsx` namespace. The backend **Terminal Console** currently consumes the TUI package through direct `Tui.Components` and `Tui.Patterns` calls in `apps/backend/bin/terminal_console_tui.ml`.

The idea under evaluation is to rewrite backend Terminal Console UI authoring to use the existing JSX syntax from the TUI package. The primary user is the Symphony maintainer. The primary value is maintainability: make Terminal Console layout and view changes easier to read, review, and modify while preserving operator behavior.

The main tension is scope. A complete rewrite would dogfood the public package API on the most important internal surface, but calling a broad behavior-preserving rewrite a Quick Win is risky unless parity can be proven cheaply. The Terminal Console has operator muscle memory, keyboard interactions, resize behavior, modal flows, settings behavior, visual hierarchy, and safe-aid boundaries that must not drift.

## Decision

Adopt `Tui.Jsx` as the target authoring model for backend Terminal Console UI surfaces, but execute it as a parity-gated staged migration rather than a big-bang rewrite.

The desired end state is full backend Terminal Console JSX coverage for existing UI surfaces. The migration must preserve current operator workflows, shortcuts, states, visual hierarchy, Runtime State semantics, settings behavior, and safe-aid boundaries. Any behavior change is out of scope for this idea.

V1 must include an initial representative Terminal Console slice that proves JSX readability, rendered parity, and package ergonomics before expanding to the remaining surfaces. Expansion may proceed only when the slice keeps existing tests and preview output stable enough to make rollback cheap.

## Alternatives Considered

### Alternative 1: Big-Bang Complete Rewrite

- **Description**: Convert every backend Terminal Console UI surface to JSX in one implementation pass.
- **Pros**: Delivers authoring-model convergence quickly; fully dogfoods `Tui.Jsx`; avoids long-lived dual idioms.
- **Cons**: High regression surface; expensive parity proof; poor fit for Quick Win ambition; harder rollback.
- **Why rejected**: The council found that exact behavior preservation across a large terminal surface is too easy to underestimate.

### Alternative 2: Single-Screen Pilot Only

- **Description**: Convert one representative slice and stop, leaving most backend Terminal Console views on direct component calls.
- **Pros**: Low risk; fast learning; cheap rollback.
- **Cons**: Leaves the main maintainability pain mostly intact; risks a permanent split authoring model.
- **Why rejected**: The goal is full backend dogfooding of the package JSX API, not another curated example.

### Alternative 3: Keep Direct Component Calls

- **Description**: Keep backend Terminal Console authoring unchanged and reserve JSX for package examples.
- **Pros**: No migration risk; no test churn.
- **Cons**: Fails to prove `Tui.Jsx` on a real product surface; leaves dense view composition in place; weakens docs credibility.
- **Why rejected**: The existing JSX package needs production pressure to validate its usefulness.

## Consequences

### Positive

- Gives Symphony one preferred authoring model for new Terminal Console UI work.
- Dogfoods the reusable TUI package without creating a second renderer or runtime tree.
- Keeps Terminal Console runtime semantics and package ownership boundaries intact.
- Creates measurable maintainability evidence before broad migration.

### Negative

- The backend may temporarily contain both direct component calls and JSX-authored views.
- The migration needs parity gates that may slow perceived progress.
- Full conversion remains larger than a simple documentation or example update.

### Risks

- **Rendered parity drift**: mitigate with existing Terminal Console tests, fixture rendering checks, and preview comparisons.
- **Operator muscle-memory regressions**: treat shortcut, modal, resize, and focus drift as release blockers.
- **Package boundary pressure**: backend must consume `Tui.Jsx` without adding backend-specific semantics to the reusable package.
- **Dual idioms linger**: require a tracked path from the first slice to full backend Terminal Console coverage.

## Implementation Notes

- Preserve `Tui.Node.t` as the only rendered tree shape.
- Preserve `apps/tui` as the reusable package and `apps/backend` as the product-specific Terminal Console owner.
- Do not add persisted Runtime Settings, Runtime State fields, lifecycle mutations, or new safe-aid behavior as part of this rewrite.
- Use the existing Terminal Console test area in `apps/backend/test/test_backend.ml` as the behavioral contract.
