# ADR-002: Select Complete Backend Terminal Console JSX Rewrite

## Status

Accepted

## Date

2026-05-21

## Context

ADR-001 recommended a parity-gated staged migration toward full backend Terminal Console JSX coverage. That recommendation reduced regression risk but did not match the preferred product direction after the opportunity scan.

The selected direction is the original idea: complete the backend Terminal Console rewrite to the existing `Tui.Jsx` authoring model as the V1 scope. The business goal remains maintainability for Symphony maintainers. The operator-facing contract remains strict behavior preservation.

## Decision

Rewrite all existing backend Terminal Console UI surfaces to use the JSX syntax from the reusable **TUI Toolkit Package** in V1.

The rewrite must preserve current operator workflows, shortcuts, states, visual hierarchy, Runtime State semantics, settings behavior, and safe-aid boundaries. It must not add new Runtime State fields, persisted settings, lifecycle mutations, or new Terminal Console product behavior.

The implementation may be broken into reviewable commits or task steps, but the idea scope is complete backend Terminal Console UI coverage, not a pilot.

## Alternatives Considered

### Alternative 1: Parity-Gated Staged Migration

- **Description**: Start with one representative slice, then expand only after parity proof.
- **Pros**: Lower regression risk; cheap rollback; useful learning gate.
- **Cons**: Leaves the main maintainability pain in place longer; risks a permanent split authoring model.
- **Why rejected**: The chosen product direction prioritizes full authoring-model convergence in V1.

### Alternative 2: Pilot Only

- **Description**: Convert one backend surface and stop.
- **Pros**: Smallest delivery scope.
- **Cons**: Does not dogfood the package across the real Terminal Console; insufficient for the requested complete rewrite.
- **Why rejected**: The idea is specifically to rewrite the backend TUI surface, not add another example.

### Alternative 3: Keep Direct Component Calls

- **Description**: Leave backend Terminal Console views on direct `Tui.Components` calls.
- **Pros**: No regression risk from migration.
- **Cons**: Preserves dense view composition; weakens `Tui.Jsx` credibility as the recommended authoring model.
- **Why rejected**: The existing package JSX API needs production use in the backend Terminal Console.

## Consequences

### Positive

- Establishes one preferred authoring model for backend Terminal Console UI work.
- Fully dogfoods `Tui.Jsx` against a real, high-pressure product surface.
- Makes docs/examples more credible because the product consumes the same API.
- Removes long-lived dual idioms from the backend Terminal Console once V1 is complete.

### Negative

- Larger V1 than the council recommended.
- Higher parity burden across tests, previews, keyboard behavior, modal flows, resize behavior, and visual hierarchy.
- More review effort because the expected user-visible output is intentionally unchanged.

### Risks

- **Behavior drift**: keep existing Terminal Console tests passing and add focused parity checks where JSX changes expose gaps.
- **Visual drift**: compare representative preview output before and after the rewrite.
- **Scope creep**: reject UX redesign, Runtime State changes, new settings, and new safe-aid behavior from V1.
- **Package boundary leakage**: consume `Tui.Jsx` from backend without adding backend-specific semantics to `apps/tui`.

## Implementation Notes

- Preserve `Tui.Node.t` as the only rendered tree shape.
- Treat direct component calls as the lower-level package API, but use `Tui.Jsx` for backend Terminal Console view composition.
- Keep product-specific Terminal Console logic in `apps/backend`.
- Use backend Terminal Console tests in `apps/backend/test/test_backend.ml` as the primary behavior contract.
