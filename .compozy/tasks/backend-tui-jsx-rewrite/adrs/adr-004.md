# ADR-004: Implement Terminal Console View Rewrite As Reason JSX With Preserved Module Contract

## Status

Accepted

## Date

2026-05-22

## Context

The PRD requires complete `Tui.Jsx` coverage for existing backend Terminal Console UI construction while preserving operator-visible behavior and visual hierarchy. The current implementation is `apps/backend/bin/terminal_console_tui.ml`, an OCaml module that exposes the public `Terminal_console_tui` module consumed by `main.ml`, `terminal_console_runtime.ml`, `terminal_console_preview.ml`, and backend tests.

The current view construction uses direct `Tui.Components` calls for rich text lines, modals, header, tabs, active panel, scroll box, footer, and root layout. The reusable TUI Toolkit Package already exposes `Tui.Jsx` wrappers that return the same `Tui.Node.t` tree.

## Decision

Implement the rewrite using literal Reason JSX tags and preserve the existing `Terminal_console_tui` module name and public functions.

The implementation should replace the current OCaml implementation with a Reason-authored module for the same Dune module slot. It should keep callers stable by preserving the exposed types and functions used by runtime wiring, preview code, and tests. Product-specific Terminal Console behavior stays in `apps/backend`; reusable JSX wrapper additions belong in `apps/tui` only when they map directly to existing TUI primitives.

Primary parity evidence must combine focused backend Alcotest coverage with before/after Terminal Console preview output. Verification is backend-first, with TUI package test/build required only when `apps/tui` wrapper changes are introduced.

## Alternatives Considered

### Alternative 1: Use `Tui.Jsx.*.make` From The Existing OCaml File

- **Description**: Keep `terminal_console_tui.ml` and replace direct `Components.*` calls with `Tui.Jsx.*.make` calls.
- **Pros**: Lowest churn; preserves all OCaml syntax and module shape.
- **Cons**: Does not deliver literal JSX syntax; weaker readability improvement against the PRD promise.
- **Why rejected**: The selected technical direction requires literal Reason JSX tags.

### Alternative 2: Split A New Reason View Module Behind An OCaml Wrapper

- **Description**: Add a Reason view module and leave `terminal_console_tui.ml` as a compatibility wrapper.
- **Pros**: Lower conversion risk; isolates JSX view construction.
- **Cons**: Adds a long-lived module boundary and can preserve dual authoring inside the backend Terminal Console shell.
- **Why rejected**: The selected direction preserves the existing module name while making the shell implementation itself Reason-authored.

### Alternative 3: Redesign Views To Fit Current JSX Surface

- **Description**: Adjust Terminal Console layout where the existing JSX wrappers cannot represent current direct calls exactly.
- **Pros**: Avoids expanding the TUI package wrapper surface.
- **Cons**: Violates strict operator-visible parity and risks layout drift.
- **Why rejected**: Missing wrappers should be added narrowly when they map to existing primitives; Terminal Console behavior must not adapt to API gaps.

## Consequences

### Positive

- Delivers the requested literal JSX syntax for backend Terminal Console UI construction.
- Preserves existing backend callers and tests through the same module contract.
- Fully dogfoods the public `Tui.Jsx` API on the product Terminal Console.
- Keeps product-specific behavior out of the reusable TUI package.

### Negative

- Whole-module Reason conversion has more syntax churn than a call-site-only rewrite.
- Existing tests may require small syntax-driven updates if type names or access paths change.
- Missing wrapper support can expand the `apps/tui` change surface.

### Risks

- **Module contract drift**: mitigate by preserving type/function names consumed by `main.ml`, `terminal_console_runtime.ml`, `terminal_console_preview.ml`, and tests.
- **Behavior drift from syntax conversion**: mitigate with focused Terminal Console Alcotest coverage and before/after preview output.
- **Package boundary leakage**: only add JSX wrappers that delegate to existing reusable primitives; do not introduce Terminal Console-specific wrappers in `apps/tui`.
- **Over-broad verification**: keep backend verification primary, but run TUI package checks when wrapper changes touch `apps/tui`.

## Implementation Notes

- Keep `Terminal_console_model` projection and Runtime State shaping unchanged.
- Keep interaction update logic, safe-aid dispatch, settings save behavior, and runtime handoff behavior unchanged.
- Convert view construction helpers such as line nodes, modals, footer, tabs, header, active panel, scroll box, and root layout to literal JSX tags.
- If Dune module naming requires file renaming from `.ml` to `.re`, preserve the module name `Terminal_console_tui` in `apps/backend/bin/dune`.
- Do not change Runtime Contract defaults, Web Dashboard handoff semantics, or Terminal Console safe-aid semantics.
