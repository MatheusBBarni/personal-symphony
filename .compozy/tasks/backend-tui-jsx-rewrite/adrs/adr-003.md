# ADR-003: Select Complete Coverage With Strict Parity PRD Approach

## Status

Accepted

## Date

2026-05-21

## Context

The Backend TUI JSX Rewrite idea already selected complete backend Terminal Console JSX coverage as V1 scope. During PRD clarification, the primary product promise was narrowed to maintainability for Symphony maintainers, with review readability as the most important user capability.

The strongest constraint is that operators must see no behavior or visual hierarchy changes. The rollout should support reviewable increments, but the PRD should only claim success when all existing backend Terminal Console UI construction is covered by `Tui.Jsx`.

## Decision

Use the **Complete Coverage With Strict Parity** product approach for the PRD.

The PRD will define V1 as a complete rewrite of existing backend Terminal Console UI construction to `Tui.Jsx`, delivered in reviewable increments. The headline success metric is 100% JSX coverage of existing backend Terminal Console UI construction. Acceptance requires preserving current operator-visible behavior and visual hierarchy.

## Alternatives Considered

### Alternative 1: Reviewability-First Migration

- **Description**: Prioritize the highest-density view areas first and treat full coverage as a later follow-up.
- **Pros**: Lower short-term risk; validates the readability value quickly.
- **Cons**: Leaves dual authoring idioms in the backend Terminal Console and conflicts with the selected complete V1 scope.
- **Why rejected**: The user selected complete V1 coverage as the product direction.

### Alternative 2: Package-Dogfooding Showcase

- **Description**: Frame the PRD primarily around proving the reusable TUI package JSX API and improving docs/examples credibility.
- **Pros**: Strengthens the public package story and validates `Tui.Jsx` under production pressure.
- **Cons**: Makes package credibility the primary promise instead of maintainer reviewability.
- **Why rejected**: The selected product promise is maintainability, not external package positioning.

## Consequences

### Positive

- Aligns the PRD with the approved idea and ADR-002.
- Gives maintainers a clear end state: no split backend Terminal Console authoring model.
- Keeps operator-visible stability as a first-class requirement.
- Allows implementation to be sliced without weakening the V1 success claim.

### Negative

- Larger PRD scope than a pilot or reviewability-first migration.
- Success requires broad parity review even when the intended operator-visible result is no change.
- The maintainer benefit may be harder to demonstrate until full coverage is complete.

### Risks

- **Coverage ambiguity**: define coverage as existing backend Terminal Console UI construction, not all TUI package usage.
- **False progress**: reviewable increments should not be presented as product completion until full coverage is reached.
- **Regression pressure**: operator-visible drift must block acceptance even if JSX coverage is complete.

## Implementation Notes

- Product requirements should stay focused on what maintainers can do and what operators must continue to experience.
- Technical implementation choices belong in the future TechSpec.
- Existing idea ADRs remain valid context for scope and trade-offs.
