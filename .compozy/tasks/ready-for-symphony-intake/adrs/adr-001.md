# ADR-001: Add explicit tracker-driven ready-for-symphony admission

## Status

Superseded by ADR-002

## Date

2026-05-15

## Context

Symphony already has a continuous poll loop in a **Workspace Repository**. When the orchestrator is running, it re-fetches candidates from the selected **Issue Tracker** on every polling interval and can admit newly active work without restarting the process.

The current product gap is not process persistence. The gap is admission semantics. GitHub-backed discovery is driven by GitHub Project status, not by an explicit operator-controlled readiness marker. Compozy-backed discovery is driven by runnable `task_NN.md` state and **Compozy PRD Run Lifecycle**, not by an explicit operator-controlled readiness marker. The **Ordered Queue** is currently a launch-scoped operator input and is intentionally not inferred from tracker state.

The user wants one explicit `ready-for-symphony` concept that works with the single selected tracker for a **Workspace Repository**:

- GitHub Tracker: a `ready-for-symphony` label
- Compozy-backed **Local Issue Tracker**: a `ready-for-symphony` marker in `.compozy/tasks/<slug>/_tasks.md`

The decision must preserve existing **Task Branch**, **Agent Worktree**, stage, retry, and polling semantics, and it must not turn V1 into a broad queue redesign.

## Decision

V1 will add `ready-for-symphony` as an explicit candidate-admission gate inside the selected tracker adapter.

- For the **GitHub Tracker**, a work item is newly admissible only when it is otherwise dispatchable under existing GitHub Project status rules and it carries the `ready-for-symphony` label.
- For the **GitHub Tracker**, the readiness label name should be configurable in `settings.json`, with `ready-for-symphony` as the default value.
- For the Compozy-backed **Local Issue Tracker**, a **Compozy PRD Run** is newly admissible only when it is otherwise runnable under existing task-step and lifecycle rules and the first line of `.compozy/tasks/<slug>/_tasks.md` is `ready-for-symphony`.
- The marker controls first admission into orchestration only. After a work item is admitted, existing tracker state, retries, stage transitions, and completion behavior remain the governing lifecycle semantics.
- `--queue` remains a separate higher-precedence operator filter. V1 does not auto-build, persist, or merge an **Ordered Queue** from tracker markers.
- The Compozy `_tasks.md` marker is admission intent only. It must not become a second source of truth for task-step execution order, run progress, retry state, or completion semantics.
- Starting with no ready work is a valid healthy idle state. Absence of ready-marked work must not be treated as a startup readiness gap by itself.

## Alternatives Considered

### Alternative 1: Keep implicit readiness only

- **Description**: Continue relying on existing GitHub Project status and Compozy runnable task-step detection without an explicit `ready-for-symphony` gate.
- **Pros**: No new Runtime Contract concept. No new tracker metadata to maintain.
- **Cons**: Does not solve the operator problem. Readiness remains implicit and tracker-specific, and users still need status choreography or manual queue input to control admission cleanly.
- **Why rejected**: The product need is an explicit, legible admission signal that does not require restarting Symphony or rebuilding an **Ordered Queue** manually.

### Alternative 2: Auto-build an Ordered Queue from tracker markers

- **Description**: Treat ready markers as a dynamic queue source and create or extend the **Ordered Queue** automatically as tracker items become ready.
- **Pros**: Gives a unified operator-visible list and a path to future prioritization.
- **Cons**: Changes queue identity, resume semantics, precedence rules, skip behavior, and UI expectations. Couples tracker-specific readiness markers to a load-bearing orchestration model.
- **Why rejected**: This is too broad for V1 and turns a narrow admission improvement into a queue-system redesign.

## Consequences

### Positive

- Gives operators one explicit readiness contract per selected tracker.
- Preserves the existing continuous poll loop and restartless intake behavior once the runtime is healthy.
- Keeps tracker-specific logic at the tracker boundary instead of spreading it into orchestration and queue state.
- Preserves the single-tracker-per-**Workspace Repository** model.

### Negative

- Introduces one more operator-maintained marker that can become stale.
- Requires clear documentation for when the marker is consulted and when it is ignored.
- For Compozy, adds one more run-level artifact that must be kept conceptually distinct from lifecycle and task-step state.

### Risks

- **Hidden queue behavior**: Operators may expect ready markers to define ordering, not just eligibility.
  Mitigation: keep `--queue` as explicit higher-precedence filtering and document that markers do not create queue order.
- **Stale ready markers after restart or manual edits**: An item may look ready when existing lifecycle state already disqualifies it.
  Mitigation: existing active and terminal lifecycle semantics dominate stale readiness in both trackers.
- **Compozy double-truth drift**: `_tasks.md` could be misused as lifecycle state.
  Mitigation: scope `_tasks.md` strictly to admission intent and keep execution truth in `task_NN.md` plus lifecycle state.

## Implementation Notes

- Update the **Runtime Contract** documentation to define `ready-for-symphony` as first-admission intent, not ongoing lifecycle control.
- GitHub tracker admission should remain status-aware; the label augments dispatchability rather than replacing Project status.
- Compozy tracker admission should remain runnable-state-aware; the first line of `_tasks.md` augments PRD-run eligibility rather than replacing **Compozy PRD Run Lifecycle**.
- The configurable GitHub readiness label should default to `ready-for-symphony` in `settings.json`.
- The runtime should treat “no ready work yet” as valid **Orchestration Idle** state rather than as a readiness failure.
