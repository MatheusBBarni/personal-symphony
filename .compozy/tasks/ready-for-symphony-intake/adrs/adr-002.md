# ADR-002: Use a standard Symphony-ready status convention across trackers

## Status

Accepted

## Date

2026-05-15

## Context

During PRD creation, the product direction changed from an explicit marker-based admission model to a status-driven intake model. The user wants Symphony to start newly eligible work without restart, but they do not want operators to manage a separate readiness marker such as a GitHub label or a line in `_tasks.md`.

The selected **Issue Tracker** for a **Workspace Repository** should be enough to tell Symphony when work is ready to start. That means the MVP needs one clear status convention that works for both the **GitHub Tracker** and the Compozy-backed **Local Issue Tracker**, while preserving the existing poll loop, **Task Branch**, **Agent Worktree**, stage, retry, and **Ordered Queue** semantics.

The product must optimize for one outcome first: Symphony starts newly eligible work within one polling interval without restart.

## Decision

V1 will use a standard Symphony-specific ready status convention across trackers as the primary control for first admission into orchestration.

- Symphony will define one user-facing ready status concept, expressed as a standard Symphony-ready status.
- The selected tracker decides start timing through status alone; Symphony does not require a separate readiness marker in V1.
- GitHub-backed workflows and Compozy-backed workflows should both expose the same product concept of “ready for Symphony,” even if project-specific mapping is required.
- When no work is in the Symphony-ready status, the runtime remains in valid **Orchestration Idle** state rather than failing readiness.
- `--queue` remains a separate operator-controlled filter and is not replaced by tracker status.

## Alternatives Considered

### Alternative 1: Marker-based readiness gate

- **Description**: Use explicit readiness markers such as a GitHub label and a first-line `_tasks.md` marker to admit work.
- **Pros**: Very explicit operator intent, easy to understand in isolation, minimal dependence on existing status meanings.
- **Cons**: Adds a second admission control beside project status, creates drift risk, and makes the product feel less status-driven.
- **Why rejected**: The user prefers status alone as the visible control for when work starts.

### Alternative 2: Existing-status-only compatibility

- **Description**: Let each project use whatever statuses it already considers dispatchable, without a standard Symphony-ready convention.
- **Pros**: Lowest adoption friction for existing projects.
- **Cons**: Weakens predictability, keeps tracker behavior inconsistent across repositories, and makes product messaging less clear.
- **Why rejected**: The MVP needs a standard Symphony mental model for automatic intake.

## Consequences

### Positive

- Gives operators one consistent way to reason about when Symphony will start work.
- Removes the need for separate readiness markers in routine workflows.
- Supports the primary success goal of restartless automatic start with clear status-based control.
- Creates a stronger cross-tracker product story for GitHub-backed and Compozy-backed workflows.

### Negative

- Requires projects to adopt or map to a Symphony-ready status convention.
- May require documentation and migration guidance for projects with entrenched status meanings.
- Raises product expectations that tracker status alone should fully explain start behavior.

### Risks

- Projects may use status vocabularies that conflict with the Symphony-ready convention.
  Mitigation: allow project-specific mapping while keeping the Symphony concept stable.
- Operators may expect status alone to define ordering as well as eligibility.
  Mitigation: keep `--queue` as an explicit separate filter and document that status controls eligibility, not ordering.
- Runtime behavior may be harder to explain if active, terminal, or stage-driven states override apparent readiness.
  Mitigation: make Runtime State explain why a status-qualified item is not dispatchable.

## Implementation Notes

- This ADR supersedes the marker-based admission assumption from ADR-001.
- The PRD should stay focused on product behavior and operator expectations, not on implementation mechanics.
- The exact configured mapping and wording of the Symphony-ready status can be refined later if needed, but the MVP product concept is status-driven intake.
