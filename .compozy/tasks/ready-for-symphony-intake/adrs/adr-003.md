# ADR-003: Put Symphony-ready status at the tracker boundary with exact-match first-admission semantics

## Status

Accepted

## Date

2026-05-15

## Context

The PRD selected a status-driven intake model. The MVP must start newly eligible work within one polling interval without restart while preserving the existing **Task Branch**, **Agent Worktree**, stage, retry, and **Ordered Queue** behavior.

The current architecture already has a stable tracker boundary in `Issue_tracker`. The `Orchestrator` depends on tracker adapters for candidate fetch, readiness gaps, identifier normalization, and active or terminal semantics. GitHub candidate discovery already reads GitHub Project status through `Github_tracker.issue_from_project_node`, while Compozy candidate discovery already maps a **Compozy PRD Run** to an `Issue.t` through `Issue_tracker.compozy`.

The open technical question is where to normalize the new Symphony-ready status rule. The user selected a tracker-owned setting, exact-match ready status for GitHub first admission, no startup readiness gap when nothing is ready, and queue entries that must still satisfy the ready rule before first admission.

## Decision

V1 will add a tracker-owned ready-status setting and enforce Symphony-ready exact-match semantics at the tracker boundary for first admission.

- Runtime Settings will add a dedicated ready-status field for tracker-backed intake.
- Tracker adapters will use that field when deciding whether a candidate is eligible for first admission.
- For GitHub, the Symphony-ready project status replaces the current broader active-state dispatchability rule for first admission. A GitHub issue must have the exact configured ready status to become a newly admissible candidate.
- For queue-driven runs, listed entries must still satisfy the Symphony-ready rule before first admission. `--queue` constrains selection and ordering, but it does not bypass intake eligibility.
- When the selected tracker has no Symphony-ready work, startup remains valid **Orchestration Idle** state and must not emit a readiness gap solely because nothing is ready.
- Existing active, terminal, retry, and stage-driven semantics continue to govern work after admission unless a later implementation explicitly changes that contract.

## Alternatives Considered

### Alternative 1: Reuse activeStates with no dedicated ready-status field

- **Description**: Treat the Symphony-ready state as just another member of `activeStates` and avoid a separate config field.
- **Pros**: Small config surface and minimal new parsing logic.
- **Cons**: Blurs “eligible to start now” with “active or dispatchable in a broader sense,” preserves ambiguity, and weakens the exact-match rule the user selected.
- **Why rejected**: The MVP needs a narrower, explicit first-admission control than the existing active-state set.

### Alternative 2: Filter after fetch inside Orchestrator

- **Description**: Keep tracker adapters broad and let `Orchestrator` apply the ready-status rule after candidate fetch.
- **Pros**: Centralizes some policy in one place.
- **Cons**: Duplicates tracker semantics, weakens the selected tracker boundary, complicates queue and readiness interactions, and makes tracker-specific behavior harder to test in isolation.
- **Why rejected**: The existing architecture already concentrates candidate-admission semantics in tracker adapters.

## Consequences

### Positive

- Keeps the new intake rule in the same boundary that already owns tracker-specific candidate semantics.
- Gives GitHub first-admission behavior an exact-match ready rule that is easy to reason about and test.
- Preserves the current role of `--queue` as a filter and ordering tool rather than an eligibility override.
- Avoids treating “nothing ready yet” as a startup failure.

### Negative

- Adds new tracker configuration that operators must understand.
- Makes migration more explicit for projects that currently rely on broad active-state dispatchability.
- Requires careful separation between first-admission semantics and post-admission lifecycle semantics.

### Risks

- Existing projects may expect prior active-state behavior to continue unchanged.
  Mitigation: document the ready-status field and keep compatibility discussion explicit in docs and runtime messaging.
- Queue users may expect listed items to dispatch even when not ready.
  Mitigation: preserve the rule that queue membership does not bypass intake eligibility.
- Readiness and stage semantics may drift if later code paths re-check different status sets.
  Mitigation: keep first-admission checks centralized in tracker adapters and cover the boundary with integration tests.

## Implementation Notes

- `Config.tracker` should gain a dedicated ready-status field rather than overloading `activeStates`.
- `Runtime_readiness` and `Runtime_policy` should treat “no ready work” as valid idle state.
- Any Runtime State explanation of “not dispatchable” should distinguish missing ready status from later lifecycle or stage constraints.
