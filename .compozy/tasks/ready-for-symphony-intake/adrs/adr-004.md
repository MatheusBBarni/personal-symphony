# ADR-004: Read Compozy Symphony-ready status from _tasks.md while keeping task-step state separate

## Status

Accepted

## Date

2026-05-15

## Context

The PRD requires the same Symphony-ready product concept across the **GitHub Tracker** and the Compozy-backed **Local Issue Tracker**. For Compozy, the current system already has two technical layers:

- `Compozy_tasks_tracker` derives **Compozy Task Step** progress from `task_NN.md` frontmatter.
- `Compozy_lifecycle` persists run-level lifecycle and pull-request readiness metadata in the **Runtime Home**.

The user selected `_tasks.md` as the technical home for the Compozy-ready status instead of task-step frontmatter or lifecycle `dispatch_state`. The design must preserve the existing split between task-step execution truth and run-level orchestration state while exposing a clear run-level intake source.

## Decision

V1 will read the Compozy Symphony-ready status from `.compozy/tasks/<slug>/_tasks.md` as a run-level intake source, while keeping task-step execution state and lifecycle state in their current roles.

- `_tasks.md` will provide the Compozy-ready status used for first admission into orchestration.
- `task_NN.md` frontmatter remains the authoritative source for **Compozy Task Step** execution progress.
- `Compozy_lifecycle.dispatch_state` remains the run-level execution and stage-routing state after admission.
- The Compozy tracker adapter will combine `_tasks.md` readiness with existing runnable-run checks before returning newly admissible candidates.
- `_tasks.md` must not become a substitute for task-step status, retry counters, failure state, or PR-readiness metadata.

## Alternatives Considered

### Alternative 1: Store the ready status in Compozy lifecycle dispatch_state

- **Description**: Reuse `Compozy_lifecycle.dispatch_state` as the source of the Symphony-ready status.
- **Pros**: Keeps run-level status in one runtime-owned place.
- **Cons**: Weakens the local-tracker artifact model, hides readiness in Runtime Home metadata, and blurs first-admission intent with post-admission execution state.
- **Why rejected**: The user selected a repository-owned Compozy artifact rather than runtime metadata as the intake source.

### Alternative 2: Derive readiness only from task_NN.md frontmatter

- **Description**: Infer Compozy-ready status from task-step state alone and avoid `_tasks.md`.
- **Pros**: Fewer files involved in candidate selection.
- **Cons**: Blurs run-level intake with step-level execution truth and makes it harder to express a single PRD-run readiness concept.
- **Why rejected**: The user selected `_tasks.md` as the run-level source, and the current architecture already uses task files for execution state.

## Consequences

### Positive

- Preserves a clear run-level intake artifact for Compozy-backed tracking.
- Avoids overloading task-step frontmatter with run-level orchestration meaning.
- Lets the adapter combine repository-owned readiness with existing lifecycle-aware candidate logic.

### Negative

- Adds another file that must stay semantically distinct from lifecycle and task-step state.
- Requires parser and validation logic for `_tasks.md`.
- Creates more cross-checking between run-level readiness and other Compozy state surfaces.

### Risks

- Operators may treat `_tasks.md` as a complete lifecycle summary rather than only an intake source.
  Mitigation: document the boundary clearly and keep runtime projections explicit about which state comes from where.
- `_tasks.md` readiness could drift from lifecycle or step progress.
  Mitigation: use `_tasks.md` only for first admission and continue to rely on lifecycle and task-step state after admission.
- Parsing `_tasks.md` may become brittle if the file format is underspecified.
  Mitigation: define a small, explicit ready-status parsing rule and cover malformed-file cases with tests.

## Implementation Notes

- Prefer a minimal parser in `Compozy_tasks_tracker` that reads run-level readiness from `_tasks.md` without disturbing existing task-step parsing.
- Runtime State should continue to project Compozy progress and lifecycle separately from intake readiness.
- If `_tasks.md` is missing or malformed, the tracker should surface a deterministic readiness or candidate-exclusion outcome instead of guessing.
