# ADR-001: Cursor Harness As A Bounded Multi-Harness Extension

## Status

Accepted

## Date

2026-05-14

## Context

Symphony already has an accepted Runtime Contract for named `Agent Harness` definitions under `harnesses`, logical
agents under `agents`, and stage routing under `stageAgents`. The current implementation supports `codex`, `claude`,
and `pi`, with selected-Harness readiness, provider-specific auth checks, structured output handling where needed, and
Bootstrap defaults that preserve the provider-neutral model.

Workspace Repository operators who already use Cursor CLI now need provider choice inside the same Runtime Contract.
Current Cursor docs describe `cursor-agent` as a beta CLI that supports non-interactive `--print` automation,
structured output including `stream-json`, project rules via `AGENTS.md` and `.cursor/rules`, authentication through
browser login or `CURSOR_API_KEY`, permission controls, and direct file edits in scripted mode with `--force`.

The product decision is whether to treat Cursor as a bounded new Harness inside the current model, or to expand scope
into a larger provider-capability redesign before validating actual operator demand.

## Decision

Symphony will treat Cursor CLI as a first-class `Agent Harness` with `kind: "cursor"` inside the existing
multi-Harness Runtime Contract.

V1 scope is intentionally bounded. It should cover the common day-to-day Harness path needed by operators already using
Cursor CLI:

- selected-Harness readiness and install checks
- authentication readiness through supported Cursor login or API-key paths
- non-interactive command rendering for Cursor CLI
- structured output observation using Cursor's documented print-mode output formats
- Runtime State and log visibility consistent with other Harnesses
- Bootstrap and documentation examples that preserve the existing `harnesses` / logical `agents` split

V1 will not introduce Cursor-specific orchestration concepts above the Harness boundary. Cursor permission modes,
`--force`, approval semantics, or background-agent concepts remain Harness-local behavior unless they later prove to be
shared product concepts across more than one provider.

## Alternatives Considered

### Alternative 1: Add Cursor As A Generic Command-Only Compatibility Path

- **Description**: Let operators point a generic command at Cursor CLI without introducing `kind: "cursor"` or
  Cursor-specific readiness and output handling.
- **Pros**: Smallest short-term surface area and least parser work.
- **Cons**: Pushes provider-specific behavior into undocumented command strings, weakens readiness, and makes Cursor
  support feel fragile.
- **Why rejected**: Symphony already distinguishes Harness semantics by `kind`; hiding Cursor behind a generic command
  would regress clarity and observability.

### Alternative 2: Build A Broader Harness Capability Layer Before Adding Cursor

- **Description**: Delay Cursor until Symphony first introduces generic provider capability abstractions for
  permissions, tool access, background execution, and richer structured output.
- **Pros**: Could reduce future abstraction churn if many providers need the same controls.
- **Cons**: Turns a quick-win operator request into a larger platform project, delays learning, and risks designing
  abstractions that only Cursor needs.
- **Why rejected**: The current Runtime Contract is already strong enough to validate Cursor demand without paying the
  cost of a broader redesign first.

## Consequences

### Positive

- Preserves the accepted boundary where `harnesses` own provider execution concerns.
- Expands operator choice for Workspace Repositories already standardized on Cursor CLI.
- Exercises the existing multi-Harness model with another real provider.
- Keeps the path compatible with Bootstrap, Runtime State, and logical-agent routing already in place.

### Negative

- Adds another provider-specific readiness and output-observation surface to maintain.
- Requires careful documentation so Cursor support does not look like a promise of full product-feature parity.
- May expose gaps in current Runtime State naming or shared test coverage for new Harness onboarding.

### Risks

- **Beta CLI drift**: Cursor CLI behavior or output format may change while the CLI is still documented as beta.
  Mitigation: keep parsing defensive, rely on documented print-mode formats, and preserve raw logs.
- **Unsafe automation assumptions**: Cursor documents strong non-interactive write and shell capabilities. Mitigation:
  keep secrets out of Runtime Settings, scope readiness to selected Harnesses, and prefer safe documented defaults over
  implicit approval bypasses.
- **Scope creep into provider-specific features**: Background-agent semantics, enterprise controls, or approval modes
  could leak into generic Runtime Settings too early. Mitigation: keep those concerns inside the Cursor Harness unless a
  second provider proves the abstraction.

## Implementation Notes

- Prefer a documented non-interactive Cursor command shape over ad hoc shell wrappers.
- Keep Cursor loop behavior conservative in V1; do not assume parity with Codex `Harness Loop` behavior without
  explicit evidence.
- Treat Cursor auth and readiness the same way other Harnesses are treated: selected-Harness only, no secret values in
  Runtime Settings, and clear remediation for missing setup.
- Preserve existing `Workspace Repository`, `Runtime Contract`, `Agent Worktree`, and `Task Branch` semantics.
