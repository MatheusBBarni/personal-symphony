# ADR-003: Native Cursor Harness Technical Design

## Status

Accepted

## Date

2026-05-15

## Context

The PRD establishes Cursor as a stable first-class `Agent Harness` available to any `Logical Agent` role. The
existing codebase already supports provider-specific Harness kinds for `codex`, `claude`, and `pi`, with shared
selection through `harnesses`, role overrides through `agents`, selected-Harness readiness, shell-based prompt launch,
and Runtime State Harness identity.

The core technical decision is whether Cursor should be implemented as a native Harness kind inside those seams, as a
lighter PI-style compatibility path with fewer provider-specific behaviors, or only after a broader generic Harness
capability refactor.

The codebase exploration shows that the current architecture is already designed for bounded provider-specific behavior
inside `Config` and `Orchestrator`. It also shows specific landmines: launch is stdin-only and non-TTY, selected
Harnesses currently require `model` and `reasoningEffort`, and loop-enabled non-Codex Harnesses need explicit
readiness protection rather than inheriting Codex assumptions.

## Decision

Implement Cursor as a native `kind: "cursor"` Harness inside the existing `Agent Harness` model.

This design will:

- add Cursor as an allowed Harness kind in `Config`
- define a Cursor default command and default loop behavior
- use selected-Harness readiness for Cursor install and authentication
- reuse existing `harnesses -> agents -> stageAgents` resolution without introducing new role-specific logic
- preserve existing launch, Runtime State, and `Agent Worktree` / `Task Branch` semantics unless Cursor needs a
  provider-local renderer or parser extension

The implementation will stay within the current architecture instead of introducing a generic provider-capability
framework. Cursor-specific behavior remains provider-local in the same style as Claude and PI.

## Alternatives Considered

### Alternative 1: Minimal PI-Style Compatibility Path

- **Description**: Add Cursor as a basic Harness kind with install/auth readiness and standard shell launch, but defer
  richer provider-local handling.
- **Pros**: Lowest immediate implementation surface and easiest to land quickly.
- **Cons**: Weakens the stable first-class support goal, under-specifies observability, and creates a greater chance of
  papering over Cursor-specific requirements.
- **Why rejected**: The selected product direction requires stable first-class support, and the existing architecture is
  already strong enough to support a more explicit design.

### Alternative 2: Generic Harness Capability Refactor Before Cursor

- **Description**: Introduce new generic abstractions for auth, output contracts, loop capabilities, and command modes,
  then add Cursor on top.
- **Pros**: Could reduce duplication if many future Harnesses share the same new concerns.
- **Cons**: Larger refactor, slower delivery, and likely premature abstraction for a still-bounded provider addition.
- **Why rejected**: Violates YAGNI for the current feature and delays direct delivery of the approved Cursor support.

## Consequences

### Positive

- Keeps Cursor inside established provider seams rather than creating a parallel integration model.
- Reuses existing Runtime Contract, launch, readiness, and Runtime State infrastructure.
- Minimizes architectural churn while still allowing provider-local behavior where needed.

### Negative

- Adds one more provider-specific branch inside already important backend modules.
- Inherits current Harness-contract assumptions such as required execution defaults and stdin-based launch.

### Risks

- **stdin launch mismatch**: Cursor may not behave correctly under Symphony's current shell-redirection launch path.
  Mitigation: verify the documented non-interactive command shape early and keep the renderer/provider logic local.
- **Contract drift**: Cursor may need provider-specific behavior that does not fit the current generic fields cleanly.
  Mitigation: scope the first implementation narrowly and document any required field semantics explicitly.
- **Module concentration risk**: `config.ml`, `orchestrator.ml`, and `test_backend.ml` are already dense. Mitigation:
  use targeted changes and targeted tests rather than refactoring the shared modules during this feature.

## Implementation Notes

- Prefer PI as the baseline pattern for kind/default/readiness structure.
- Borrow Claude patterns only where Cursor also needs provider-local structured output handling.
- Avoid introducing new directories or packages unless the existing backend modules prove insufficient.
