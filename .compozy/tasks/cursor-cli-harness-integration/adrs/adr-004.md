# ADR-004: Cursor Output, Readiness, And Loop Contract

## Status

Accepted

## Date

2026-05-15

## Context

The technical clarification phase established four important implementation constraints:

1. Cursor should use `stream-json` as the canonical V1 output contract.
2. Cursor authentication readiness should be driven by the Cursor CLI itself, not only by env or file heuristics.
3. The product should support both non-`--force` and `--force` command shapes in docs and Bootstrap examples.
4. Cursor should support `loop.enabled` and `loop.command` in V1 when operators install the supporting Cursor plugin
   and configure the loop entry command explicitly.

The current codebase already treats Claude as the main structured-output example and Codex as the main loop/readiness
example. It also limits extra goal readiness checks to Codex today, which means a naive loop-enabled Cursor Harness
would inherit prompt-prepending behavior without adequate protection.

## Decision

Cursor V1 will use the following technical contract:

- `stream-json` is the primary structured-output mode for live Cursor activity.
- Raw stdout and stderr logs remain the durable fallback when structured parsing is incomplete or unavailable.
- Cursor selected-Harness readiness will call the Cursor CLI itself for auth or status validation, instead of relying
  primarily on static env/file checks.
- Cursor supports `loop.enabled` and `loop.command`, but the loop is operator-configured and only considered supported
  when the required Cursor plugin/command path is present.
- Bootstrap and documentation may show both non-`--force` and `--force` command shapes, but the spec keeps direct
  write posture explicit instead of hiding it behind one implied default.

## Alternatives Considered

### Alternative 1: JSON-Only Or Raw-Log-Only Cursor Observation

- **Description**: Treat `json` or raw logs as the only supported V1 contract and defer `stream-json`.
- **Pros**: Simpler parser surface and less provider-specific live activity logic.
- **Cons**: Gives up the richest documented Cursor output path and weakens Runtime State parity with structured
  provider observation.
- **Why rejected**: The user selected `stream-json` first, and the current architecture already has a precedent for
  provider-local structured parsing.

### Alternative 2: Static Auth Heuristics And Disabled Loop Support

- **Description**: Reuse only env/file auth checks and disable Cursor loop support entirely in V1.
- **Pros**: Lower implementation complexity and fewer provider-specific probes.
- **Cons**: Fails the chosen technical direction, misses the actual CLI-owned auth signal, and ignores the explicit
  plugin-backed loop support available to operators.
- **Why rejected**: The selected approach is to trust the Cursor CLI as the source of readiness truth and to carry
  forward the existing `loop.enabled` / `loop.command` product model.

## Consequences

### Positive

- Aligns the implementation with documented Cursor behavior rather than inventing a weaker generic approximation.
- Preserves strong raw-log fallback while still giving Runtime State a structured first path.
- Keeps the current loop configuration model consistent across providers.

### Negative

- Adds provider-specific parsing and CLI probing logic to shared backend modules.
- Makes the loop readiness problem more complex than a loop-disabled PI-style integration.

### Risks

- **CLI-probe fragility**: Cursor status/auth commands may change. Mitigation: isolate the probe logic, keep it
  defensive, and preserve clear remediation.
- **Loop false-positive risk**: A configured loop command may exist without a functioning plugin-backed loop flow.
  Mitigation: add explicit readiness validation for loop-enabled Cursor Harnesses before dispatch.
- **Dual command-example ambiguity**: Showing both `--force` and non-`--force` shapes can confuse operators.
  Mitigation: document the distinction clearly and make the consequences of each shape explicit.

## Implementation Notes

- Extend the current Claude-style activity update path only as far as Cursor's documented `stream-json` shape justifies.
- Add Cursor-specific loop readiness rather than reusing Codex-only goal assumptions.
- Keep static env/file checks as optional fallback diagnostics if useful, but not as the primary success condition for
  auth readiness.
