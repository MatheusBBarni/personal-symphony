# ADR-004: Persist task-step progress in Compozy task files

## Status

Accepted

## Date

2026-05-08

## Context

The PRD requires one Compozy PRD run to show progress across its `task_NN.md` files. V1 must preserve restart-friendly progress and make Compozy task artifacts the tracker surface for this workflow.

There are two candidate storage locations: Symphony-owned state under `.symphony/state/` or Compozy task file frontmatter. Symphony state is already used for runtime projections such as Ordered Queue state, but the user selected direct task-file progress because Compozy task files are the tracker artifacts for this feature.

## Decision

V1 will persist task-step progress by updating Compozy task file frontmatter directly.

Each task file's frontmatter will carry the task-step status needed by the Compozy PRD-run path. Symphony will update that frontmatter as task steps start, complete, retry, or reach the configured retry limit. Runtime State may project this progress for terminal and dashboard visibility, but the Compozy task files are the authoritative task-step progress store for V1.

Writes must be scoped to the selected `.compozy/tasks/<task_name>/` directory and must preserve user-authored task body content.

## Alternatives Considered

### Alternative 1: Store progress only under `.symphony/state/`

- **Description**: Leave Compozy task files untouched and persist progress in Symphony runtime state files.
- **Pros**: Avoids modifying repository-owned task files during execution.
- **Cons**: Splits tracker truth from the Compozy artifacts and weakens local tracker replacement confidence.
- **Why rejected**: The user selected Compozy task file frontmatter as the progress store.

### Alternative 2: Hybrid state plus final frontmatter updates

- **Description**: Keep authoritative runtime progress under `.symphony/state/` and update task files only at final boundaries.
- **Pros**: Reduces task-file churn during retries.
- **Cons**: Makes restart and inspection semantics less direct.
- **Why rejected**: The selected model is simpler for operators: task files show the current task-step state.

## Consequences

### Positive

- Compozy task files remain the visible tracker source for task-step progress.
- Restart can recover progress by reading task frontmatter.
- Operators can inspect task-step state in normal repository files.

### Negative

- Execution mutates repository-owned Compozy task files.
- Status writes can introduce local changes during task execution.
- The implementation must preserve frontmatter and task body formatting carefully.

### Risks

- User edits during execution can conflict with status updates.
- Agent work may accidentally include status churn in unrelated commits unless the execution flow controls when task files are staged.

## Implementation Notes

- Update only frontmatter keys needed for task-step status and retry counts.
- Preserve the Markdown body exactly where practical.
- Report malformed or missing frontmatter as a readiness or attention condition instead of launching unclear work.
