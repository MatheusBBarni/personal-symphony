# ADR-001: Scope Compozy tasks as a local tracker adapter

## Status

Accepted

## Date

2026-05-08

## Context

Personal Symphony currently uses the **GitHub Tracker** as the default **Issue Tracker**, with GitHub Issues as issue records and GitHub Projects statuses as dispatch state. The proposed `compozy-tasks-run-integration` idea lets a Symphony operator use Compozy task files under `.compozy/tasks/<slug>/task_NN.md` as repository-owned local issue records for the main orchestration lifecycle.

The V1 ambition is a quick win: replace the external tracker dependency for the core task lifecycle without changing **Runtime Contract** defaults, packaged behavior, **Task Branch** cleanup, auto-merge defaults, or the broader project-management model.

The Product Repository already has accepted language and architecture work for **Local Issue Tracker** support, including the minibeads Local Issue Tracker ADR and specification. Compozy task files overlap with that direction but introduce a specific identity risk: names such as `task_01.md` are only unique inside one Compozy workflow directory and cannot safely serve as global task identifiers.

## Decision

V1 will frame Compozy task files as a Compozy-backed **Local Issue Tracker** adapter that uses Compozy task files as **Local Issue Files** for Symphony's existing main task lifecycle.

The **GitHub Tracker** remains the default **Issue Tracker**. Compozy-backed local tracking is opt-in through **Runtime Settings** and must not change Bootstrap defaults in `runtime_home.ml`.

V1 must define stable, unique Compozy-backed issue identifiers before using task files for **Ordered Queue** entries, **Task Branch** naming, **Runtime State**, status transitions, or **Manual Task Merge** validation. The identifier must include enough workflow context to avoid collisions between separate Compozy workflows that each contain `task_01.md`.

V1 must reuse the existing **Local Issue Tracker** direction where practical, especially the shared tracker boundary, tracker-neutral lifecycle semantics, selected-tracker queue validation, and dashboard wording work already identified for minibeads.

## Alternatives Considered

### Alternative 1: Directly dispatch `.compozy/tasks` without a tracker boundary

- **Description**: Add a special path that reads Compozy task files and feeds them into orchestration separately from the GitHub Tracker.
- **Pros**: Fastest path to a demo and fewer immediate backend abstractions.
- **Cons**: Preserves GitHub-shaped coupling, creates duplicated lifecycle behavior, and makes status transitions, queue validation, and merge validation harder to reason about.
- **Why rejected**: It would likely become a second orchestration path instead of a real **Issue Tracker** adapter.

### Alternative 2: Replace the GitHub Tracker with Compozy tasks

- **Description**: Make Compozy task files the preferred or default tracker model for Symphony.
- **Pros**: Strong local-first positioning and simpler setup for Compozy users.
- **Cons**: Breaks existing Workspace Repositories, violates the current default tracker contract, and changes more product semantics than the quick-win V1 requires.
- **Why rejected**: The **GitHub Tracker** must remain the default and existing behavior must not regress.

### Alternative 3: Build a full local project-management layer

- **Description**: Treat `.compozy/tasks` as a full replacement for Issues/Projects, including assignment, comments, rich filtering, history, cross-workflow planning, and tracker sync.
- **Pros**: More complete user-facing tracker experience.
- **Cons**: Expands V1 into a platform feature and competes with the existing minibeads Local Issue Tracker plan.
- **Why rejected**: It does not fit the selected quick-win scope.

## Consequences

### Positive

- Symphony can validate local-first orchestration from Compozy task files without requiring GitHub API access.
- The feature aligns with existing **Local Issue Tracker** terminology instead of creating a separate task-tracking vocabulary.
- Stable identifiers become an explicit V1 requirement before task files affect branches, queues, status, or dashboard state.

### Negative

- V1 is larger than a naive file-reader integration because it needs selected-tracker behavior and identifier rules.
- The implementation must avoid duplicating or conflicting with the minibeads Local Issue Tracker architecture.
- Some Compozy workflow features remain out of scope even if the files contain useful metadata.

### Risks

- Raw task prose and frontmatter are untrusted **Workspace Repository** input and must be parsed, validated, and mapped deterministically.
- Tracker status writes can pollute unrelated work if write locations and commit behavior are not constrained.
- A too-GitHub-shaped abstraction could make Compozy support appear local while retaining hidden GitHub assumptions.

## Implementation Notes

- Treat the first implementation as a tracker adapter, not a generic Compozy workflow runner.
- Preserve the existing **Stage Agent**, **Agent Prompt**, **Task Branch**, retry, **Stage Commit**, **Stage Push**, **Task Branch Integration**, and **Runtime State** semantics.
- Keep full project-management behavior, tracker sync, and Runtime Contract default changes out of V1.
