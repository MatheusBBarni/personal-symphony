# ADR-003: Add a narrow Compozy tracker path

## Status

Accepted

## Date

2026-05-08

## Context

The PRD requires Symphony to run a Compozy PRD directory as one user-facing work item while keeping every `task_NN.md` step in the same **Agent Worktree** and **Task Branch**. The Product Repository has a broader minibeads Local Issue Tracker plan that introduces a shared `Issue_tracker` boundary, but this feature's selected technical direction is a narrower V1 path.

The current backend still routes orchestration, readiness, Ordered Queue, and Manual Task Merge through GitHub-shaped code. A full shared tracker abstraction would be cleaner long term, but it would expand this PRD-run feature beyond the selected V1 scope.

## Decision

V1 will add a narrow Compozy-specific tracker path beside the existing GitHub path instead of introducing a full shared `Issue_tracker` abstraction.

Runtime Settings will accept an opt-in Compozy tracker kind and Compozy-specific settings. GitHub remains the default. GitHub-only readiness gaps must not block Compozy tracker runs. The Compozy path may reuse existing `Issue.t`, **Agent Worktree**, **Task Branch**, **Runtime State**, and launch machinery, but it may add Compozy-specific orchestration flow where a PRD run contains multiple task-step launches.

The design must keep the GitHub path behaviorally unchanged and must not change Bootstrap defaults.

## Alternatives Considered

### Alternative 1: Shared `Issue_tracker` boundary

- **Description**: Add a selected tracker interface that wraps GitHub and provides a Compozy adapter through the same contract.
- **Pros**: Cleaner long-term architecture, aligns with minibeads, reduces future duplicated tracker logic.
- **Cons**: Larger refactor before validating PRD-run execution semantics.
- **Why rejected**: The user selected the narrow Compozy special path for V1.

### Alternative 2: In-memory Runtime override

- **Description**: Convert Compozy PRD runs into temporary `Issue.t` values without tracker settings or persisted local task updates.
- **Pros**: Smallest backend change.
- **Cons**: Does not provide tracker replacement confidence, persisted task progress, or restart-friendly execution.
- **Why rejected**: The PRD requires Compozy-backed tracking, visible progress, and persisted state.

## Consequences

### Positive

- V1 can focus on Compozy PRD-run execution without first completing the broader tracker abstraction.
- Existing GitHub behavior can remain isolated and easier to regression-test.
- The TechSpec can describe concrete Compozy task-step behavior directly.

### Negative

- Some tracker duplication is accepted for V1.
- Future unification with minibeads may require refactoring the Compozy path into a shared tracker boundary.
- Ordered Queue and Manual Task Merge support for Compozy may be narrower than the eventual selected-tracker model.

### Risks

- The Compozy path could become a long-lived parallel orchestration model if not documented as a V1 compromise.
- GitHub-specific assumptions may leak into Compozy execution if the special path is not clearly contained.

## Implementation Notes

- Keep `tracker.kind = "github"` as the default.
- Prefer small Compozy-specific modules over broad rewrites of GitHub code.
- Document any intentionally duplicated behavior so future tracker unification can find it.
