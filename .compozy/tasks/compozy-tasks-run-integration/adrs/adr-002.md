# ADR-002: Treat a Compozy PRD run as the local issue

## Status

Accepted

## Date

2026-05-08

## Context

The idea phase scoped `compozy-tasks-run-integration` as a Compozy-backed **Local Issue Tracker** for Symphony's existing orchestration lifecycle. During PRD clarification, the user clarified that Compozy separates work by PRD directory under `.compozy/tasks/<task_name>/`, and the task files inside that directory are part of the same issue-level work item.

The user also clarified that each `task_NN.md` prompt should include the PRD and TechSpec context from `_prd.md` and `_techspec.md`. The desired V1 behavior is not one Symphony issue per Compozy task file. The desired behavior is one user-facing unit of work for the PRD run, with all task files running in the same **Agent Worktree** and **Task Branch** context.

## Decision

V1 will treat `.compozy/tasks/<task_name>/` as the user-facing Compozy-backed local issue identity.

The PRD run owns one Symphony work item, one **Agent Worktree**, and one **Task Branch**. Its `task_NN.md` files execute as ordered steps within that work item. Each task-step prompt must include the PRD and TechSpec context from `_prd.md` and `_techspec.md` when those files exist.

Runtime and dashboard surfaces should present the PRD run as the primary unit of work, with progress across its task files. V1 may expose task-step progress as supporting detail, but individual task files are not separate Symphony issues.

## Alternatives Considered

### Alternative 1: Individual task files as issues

- **Description**: Treat each `task_NN.md` file as its own Symphony issue, worktree, and Task Branch.
- **Pros**: Maps closely to the existing one-issue-per-task lifecycle.
- **Cons**: Splits one Compozy PRD across multiple worktrees and branches, conflicts with the user's same-worktree requirement, and weakens PRD-level continuity.
- **Why rejected**: The user explicitly wants tasks from one PRD to share the same worktree.

### Alternative 2: Imported PRD summary issue

- **Description**: Treat `_prd.md` and `_techspec.md` as one synthetic issue and use task files only as optional prompt context.
- **Pros**: Simple user-facing identity and minimal task progress surface.
- **Cons**: Loses the value of Compozy task decomposition and makes per-task progress difficult to inspect.
- **Why rejected**: The user wants each task prompt to include task-specific content plus PRD and TechSpec context.

## Consequences

### Positive

- The user-facing unit of work matches the Compozy workflow directory and the user's mental model.
- All task files for a PRD share one **Agent Worktree** and **Task Branch**, preserving continuity across the PRD run.
- The PRD and TechSpec remain first-class context for every task-step prompt.

### Negative

- V1 must track progress within a PRD run, not just one issue status.
- Failure, retry, and attention states need clear user-facing wording when they occur at a task-step inside a PRD run.
- The approach differs from the existing GitHub issue-per-task assumption and needs careful product documentation.

### Risks

- Operators may confuse Compozy task-step progress with separate issue records unless the UI and documentation clearly distinguish the PRD run from its task files.
- A long PRD run can keep one worktree active for longer than a smaller issue-level task, increasing the need for clear progress and interruption behavior.

## Implementation Notes

- Keep this ADR product-scoped. Technical sequencing, prompt composition, and state persistence belong in the TechSpec.
- Use the existing glossary terms in `CONTEXT.md`, especially **Local Issue Tracker**, **Local Issue File**, **Agent Worktree**, **Task Branch**, and **Runtime State**.
