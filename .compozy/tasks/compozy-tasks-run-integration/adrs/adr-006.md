# ADR-006: Configure task-step retries in Compozy tracker settings

## Status

Accepted

## Date

2026-05-08

## Context

The PRD requires task-step progress to remain visible across a Compozy PRD run. During technical clarification, the user selected this failure behavior: when a middle task step fails, Symphony should retry that task step up to a configurable limit, then move to the next task step after the limit is reached.

The retry limit is specific to Compozy task-step execution and should not change the global agent retry/backoff policy for GitHub Tracker runs.

## Decision

V1 will add a Compozy tracker Runtime Settings field for the per-task-step retry limit, such as `tracker.compozy.maxTaskStepRetries`.

When a task step fails, Symphony retries the same task step until the task-step retry count reaches the configured limit. After the limit is reached, Symphony records the step as skipped or failed in task file frontmatter and advances to the next runnable task file in the same PRD run. The PRD run reaches final success only if the configured completion semantics allow skipped or failed-over-limit steps.

The GitHub Tracker retry behavior remains unchanged.

## Alternatives Considered

### Alternative 1: Reuse global agent retry behavior

- **Description**: Use existing global retry/backoff settings for Compozy task-step retries.
- **Pros**: No new setting.
- **Cons**: Does not let operators tune Compozy step progression separately from agent retry behavior.
- **Why rejected**: The user requested a setting in `settings.json` for this task-step retry count.

### Alternative 2: Stage-level retry setting

- **Description**: Add a retry limit to each Stage Agent mapping.
- **Pros**: More flexible by stage.
- **Cons**: Over-scopes V1 and changes stage semantics for non-Compozy runs.
- **Why rejected**: The requirement is specific to Compozy task-step execution.

## Consequences

### Positive

- Operators can prevent one failed task step from blocking the whole PRD run indefinitely.
- The setting is scoped to Compozy-backed local tracking and does not change GitHub behavior.
- Retry counts can be persisted in task file frontmatter with the task-step status.

### Negative

- Advancing after a failed-over-limit task may produce partial PRD-run completion.
- The final PRD-run status must clearly distinguish fully completed runs from runs with skipped or failed steps.

### Risks

- Automatically continuing after failures can hide important broken work if the dashboard and terminal output do not make skipped steps visible.
- A poor default retry count could either stall progress or skip too aggressively.

## Implementation Notes

- Choose a conservative default in the TechSpec and document it.
- Persist retry count and final step state in task file frontmatter.
- Surface skipped or failed-over-limit steps in Runtime State.
