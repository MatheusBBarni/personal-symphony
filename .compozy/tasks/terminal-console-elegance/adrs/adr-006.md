# ADR-006: Preserve 80x24 support with compact single-column mode rendering

## Status

Accepted

## Date

2026-05-13

## Context

The current **Terminal Console** explicitly supports a minimum size of 80 columns by 24 rows. The redesign adds explicit top-level modes and a richer structured detail model, which creates pressure to either raise the minimum viable terminal size or degrade aggressively below wide layouts.

The user selected preserving the existing minimum-size contract and collapsing each mode into a compact single-column layout rather than requiring a larger terminal.

## Decision

The redesigned **Terminal Console** will preserve 80x24 support.

At or near the minimum size, each top-level mode should render in a compact single-column layout that preserves the selected mode’s core information hierarchy. Secondary detail remains in the same mode but collapses beneath primary content rather than requiring a multi-column split.

The redesign must not require a larger terminal than the current documented minimum to be usable.

## Alternatives Considered

### Alternative 1: Hide secondary detail entirely at minimum size

- **Description**: Keep shared chrome and mode content but suppress the detail pane until the terminal grows.
- **Pros**: Simplest compact rendering; reduced crowding.
- **Cons**: Makes the minimum-size experience materially less capable; weakens the curated-detail MVP promise.
- **Why rejected**: The MVP still needs nearby routine detail, even in compact form.

### Alternative 2: Raise the minimum supported size

- **Description**: Increase the required minimum and show a resize-required screen below it.
- **Pros**: Simplifies layout design; preserves richer wide-mode composition.
- **Cons**: Breaks an existing operator contract; reduces usability in smaller terminals and multiplexers.
- **Why rejected**: The redesign should improve the default Terminal Console without narrowing where it can be used.

## Consequences

### Positive

- Preserves the current documented terminal-size contract.
- Keeps the redesign usable in smaller terminals and multiplexed workflows.
- Forces the mode models to have a coherent compact form instead of relying on wide layout only.

### Negative

- Compact layouts will need careful prioritization to avoid crowding.
- Some wide-mode affordances will have to collapse or stack.
- Rendering logic becomes more nuanced than a wide-only design.

### Risks

- **Clutter at minimum size**: too much content may still compete vertically.
  Mitigation: keep strict per-mode priority ordering and defer secondary context within the same column.
- **Behavior drift**: compact and wide layouts may diverge too much over time.
  Mitigation: keep both layouts driven by the same shared chrome and mode records.
- **Testing burden**: minimum-size behavior needs more explicit coverage.
  Mitigation: add targeted render tests for compact mode layouts alongside current minimum-size tests.

## Implementation Notes

The resize-required screen should remain only for terminals smaller than the established minimum.
