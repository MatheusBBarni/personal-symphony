# ADR-001: Scope the Terminal Console elegance redesign as a two-mode presentation refactor

## Status

Accepted

## Date

2026-05-13

## Context

Personal Symphony already has a Mosaic-backed **Terminal Console**, but the current experience flattens distinct operator moments into one noisy surface. The same six panels render together for readiness-blocked startup and active orchestration, and `Tab` changes focus rather than meaning. The result is technically functional but visually crowded and hard to scan.

The user requested a more elegant **Terminal Console** with stronger information hierarchy, with the highest priority on startup/readiness and active-run monitoring. Research across `gh-dash`, Textual, `k9s`, and Ratatui showed consistent patterns: mutually exclusive top-level views, contextual footer help, progressive density, and a secondary detail pane instead of a single wall of prose.

The redesign must preserve existing Personal Symphony constraints:

- **Runtime State** remains the visible source of truth.
- The **Terminal Console** remains read-first and non-mutating.
- `--web`, `--once`, manual merge, Runtime Contract defaults, package behavior, and orchestration semantics stay unchanged.
- Terminal constraints such as 80x24 minimum size and ASCII-safe rendering remain in force.

## Decision

The **Terminal Console** elegance redesign will be scoped as a **two-mode presentation refactor** over existing **Runtime State** rather than as a broad console rewrite.

V1 will introduce two top-level **Terminal Console** modes, one for startup and **Readiness Gaps** and one for active-run monitoring. These modes may surface as user-facing tabs, but they must behave as pure presentation lenses over the same Runtime State snapshot, not as new orchestration states or control paths.

The redesign will stay primarily inside the Mosaic presentation layer, with only narrow projection/model additions where the current shape is too weak for clean hierarchy. Those additions are limited to stable, tab-specific presentation structure such as readiness remediation detail, selected-task detail, and grouped active-run summary data. The redesign must preserve a global attention model by carrying urgent out-of-view signals into the header, tab labels, or equivalent summary affordances so the inactive mode never becomes a blind spot.

A secondary detail pane is in scope only for curated, sanitized, read-only detail already derived from Runtime State or from explicit existing safe-aid inspection flows. It must not expose raw secrets, token values, `.env` contents, full prompts, unbounded diagnostics, or anything that implies new mutating controls.

## Alternatives Considered

### Alternative 1: Cosmetic restyle of the current six-panel layout

- **Description**: Keep the current always-visible panel structure and improve borders, spacing, labels, and typography only.
- **Pros**: Lowest implementation risk; minimal test impact; no new interaction model.
- **Cons**: Leaves the current hierarchy problem in place; keeps `Tab` as focus-only navigation; unlikely to solve the user's core complaint.
- **Why rejected**: The problem is not only visual polish. The information model is overloaded, so styling alone would produce prettier clutter.

### Alternative 2: Broad Terminal Console rewrite with richer controls and new console semantics

- **Description**: Rebuild the Terminal Console around a new interaction model, deeper preview/navigation patterns, and a wider command surface.
- **Pros**: Highest ceiling for future command-center ambitions; could enable deeper parity with the Web Dashboard.
- **Cons**: Expands the implementation blast radius; risks a second orchestration path; slows validation of the actual user complaint; increases trust and disclosure risk.
- **Why rejected**: The requested improvement is elegance and scanability, not a new orchestration surface. Broadening scope would blur learning and threaten existing runtime boundaries.

## Consequences

### Positive

- Aligns the Terminal Console structure with operator intent: “can it run?” versus “what is happening now?”
- Preserves existing runtime and packaging behavior while allowing a materially better default experience.
- Keeps V1 mostly reversible because the primary changes remain in the presentation layer.
- Creates a disciplined path for future refinements without committing to a broader console platform.

### Negative

- The redesign introduces mode switching, which can hurt scanability if cross-tab alerts are weak.
- Some small projection/model additions are still required to avoid building fragile hierarchy from string blobs.
- A secondary detail pane creates pressure to expand disclosure unless scope is enforced tightly.

### Risks

- **Cross-tab fragmentation**: operators may miss urgent signals hidden behind the inactive mode.
  Mitigation: carry urgent counts and status into persistent global summary affordances.
- **Renderer-only special cases**: too much logic in Mosaic could make future refinement harder.
  Mitigation: add thin presentation boundaries only where the current projection is structurally insufficient.
- **Disclosure drift**: richer detail panes may surface sensitive or misleading content.
  Mitigation: limit details to sanitized, bounded, read-only Runtime State summaries and existing safe-aid paths.

## Implementation Notes

This ADR defines product scope for the idea stage. Exact tab labels, pane composition, keyboard affordances, and projection shapes belong in later PRD and TechSpec work.
