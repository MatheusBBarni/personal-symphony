# ADR-003: Ship the Terminal Console redesign as the default experience

## Status

Accepted

## Date

2026-05-13

## Context

The PRD clarification round surfaced a rollout decision that materially affects product positioning. The redesign could ship behind a temporary preview period, coexist long-term with the current experience, or replace the current default behavior once ready.

The user selected immediate default rollout rather than a temporary opt-in path. This matters because the redesign is not being framed as an optional theme or side experiment. It is intended to become the primary **Terminal Console** experience for the heavy daily operator.

## Decision

The PRD will assume the redesigned **Terminal Console** ships as the default experience once it is ready.

The product should be designed and evaluated as the main local orchestration surface rather than as a preview-only branch. Success metrics, onboarding expectations, and risk mitigation should therefore assume broad default exposure.

## Alternatives Considered

### Alternative 1: Temporary opt-in or preview rollout

- **Description**: Release the redesigned **Terminal Console** behind a temporary flag or preview period first.
- **Pros**: Safer learning loop; lower disruption risk; easier rollback if adoption is poor.
- **Cons**: Weakens product commitment; slows measurement at scale; encourages the redesign to be treated as experimental instead of core.
- **Why rejected**: The user chose to treat the redesign as the intended default experience, not a side path.

### Alternative 2: Long-term dual experience

- **Description**: Keep the current and redesigned Terminal Console experiences available indefinitely.
- **Pros**: Maximum operator choice; lowest forced-change risk.
- **Cons**: Splits product attention; complicates documentation and support; weakens the clarity of the default product story.
- **Why rejected**: Long-term dual modes would fragment the product and undercut the redesign’s purpose.

## Consequences

### Positive

- Clarifies that the redesign must be good enough to represent the default Personal Symphony experience.
- Strengthens adoption measurement because usage is not limited to self-selected preview users.
- Forces the PRD to treat trust, clarity, and discoverability as first-class product concerns.

### Negative

- Raises the bar for launch quality and operator confidence.
- Increases the user-facing impact of any usability mistakes in the redesign.
- Reduces flexibility to treat rough edges as preview-only debt.

### Risks

- **Adoption shock**: some existing users may prefer the current behavior.
  Mitigation: keep the redesign predictable, legible, and obviously safer than a generic dashboard refresh.
- **Default-quality pressure**: the MVP may carry too much expectation for one release.
  Mitigation: keep scope disciplined around hierarchy and live monitoring rather than adding broad capabilities.
- **Support ambiguity**: if the redesign is too different, docs and expectations may lag.
  Mitigation: align terminology and product flows tightly with existing **Terminal Console** language and behavior.

## Implementation Notes

This ADR chooses the rollout posture for PRD planning. It does not require a specific implementation switch or flag behavior.
