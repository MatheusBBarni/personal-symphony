# ADR-005: Replace string-packed Terminal Console summaries with structured mode-specific records

## Status

Accepted

## Date

2026-05-13

## Context

The current **Terminal Console** projection encodes important UI information as display text. Examples include summary lines and `task_row.detail`, which Mosaic later re-parses to build secondary views such as task detail and compact summaries.

That shape was acceptable for the initial rich-console rollout, but it fights the current redesign. The new PRD requires stronger hierarchy, explicit top-level modes, and a curated detail pane. Those requirements are hard to satisfy cleanly if the renderer must keep interpreting preformatted strings.

The user selected structured mode-specific detail records rather than keeping string-based summaries for MVP.

## Decision

The redesign will replace string-packed summary and detail fields with structured mode-specific records in `Terminal_console_model.ml`.

Required changes include:

- replace generic summary line lists with structured chrome and mode-summary fields
- replace `task_row.detail : string option` with typed active-mode detail records
- introduce structured readiness-detail content rather than requirement/remediation strings being the only modeled unit
- keep sanitization at projection time so structured fields remain safe to render directly

The renderer may still format text for display, but it should not recover product meaning by splitting strings.

## Alternatives Considered

### Alternative 1: Keep formatted detail strings and reorganize them in Mosaic

- **Description**: Preserve existing strings and make the renderer responsible for grouping and emphasis.
- **Pros**: Lower migration cost; fewer type changes; easier short-term patching.
- **Cons**: Keeps parsing and display semantics entangled; weak foundation for explicit mode models and curated details.
- **Why rejected**: It would perpetuate the main coupling that the redesign is supposed to remove.

### Alternative 2: Hybrid approach with structured top-level summaries but string detail records

- **Description**: Add structure only for mode summaries while leaving selected detail mostly string-based.
- **Pros**: Smaller migration than full detail restructuring; some hierarchy benefits.
- **Cons**: Leaves the detail pane brittle and under-modeled; splits the model philosophy awkwardly.
- **Why rejected**: The curated detail pane is part of MVP, so detail shape needs to be first-class, not leftover formatting.

## Consequences

### Positive

- Makes hierarchy and detail behavior explicit in the projection layer.
- Simplifies renderer logic and removes reverse-engineering from strings.
- Supports cleaner tests around content meaning instead of line formatting alone.

### Negative

- Requires broader type updates than a renderer-only redesign.
- Increases migration work for existing tests and helpers.
- Makes the projection API more verbose.

### Risks

- **Schema sprawl**: too many record variants could overcomplicate the model.
  Mitigation: model only shared chrome, active-mode content, readiness-mode content, and bounded detail records needed for MVP.
- **Formatting regressions**: line-level output could change unintentionally during migration.
  Mitigation: keep selected legacy render assertions where they still protect user-visible behavior.
- **Sanitization gaps**: structured fields may bypass existing text cleanup if not projected centrally.
  Mitigation: keep all field construction behind projection helpers that sanitize before storing.

## Implementation Notes

This ADR does not require Runtime State schema changes. The structured records should be derived from existing Runtime State content.
