# ADR-004: Redesign the Terminal Console around explicit mode models over the existing in-process seam

## Status

Accepted

## Date

2026-05-13

## Context

The existing **Terminal Console** already has a clean runtime seam: `main.ml` selects the runtime path, `Terminal_console_runtime` owns readiness-versus-orchestrator startup, and `Terminal_console_model` projects **Runtime State** into a Mosaic-facing snapshot. The current weakness is not runtime wiring but the projected model shape and renderer assumptions.

Today the projection is flat and string-heavy. `Terminal_console_model.t` exposes a single `mode` string plus always-present buckets for active work, readiness, queue, and Compozy progress. `Terminal_console_mosaic` then renders the same six-panel surface regardless of operator moment and re-parses text fields such as summary lines and task detail strings.

The user selected a deeper redesign than a presentation-only tweak. The design therefore needs explicit top-level mode models rather than continuing to infer startup/readiness and active-run meaning from one flat projected snapshot.

## Decision

The redesign will keep the existing in-process seam:

`Runtime_state -> Terminal_console_model -> Terminal_console_mosaic`

but replace the projected model shape with an explicit mode-modeled snapshot.

The new projection should expose:

- a shared chrome model for heading, status, footer context, and mode labels
- an explicit body variant for the selected top-level mode
- structured per-mode content models instead of string-packed summaries
- existing safe aids and last-error information without moving orchestration logic into the projection

This keeps runtime handoff and orchestration ownership unchanged while allowing the renderer to switch on explicit mode structure instead of hard-coded panels.

## Alternatives Considered

### Alternative 1: Keep the current flat snapshot and do most redesign work only in Mosaic

- **Description**: Retain the current `Terminal_console_model.t` shape and layer mode semantics in the renderer.
- **Pros**: Smallest code churn in the projection layer; lowest short-term migration effort.
- **Cons**: Preserves stringly coupling; keeps mode logic implicit; makes future refinement harder to test cleanly.
- **Why rejected**: The requested redesign is too deep for a renderer-only interpretation. The current model shape is one of the main causes of the existing clutter.

### Alternative 2: Introduce a new shared serializable snapshot now for both Terminal Console and Web Dashboard

- **Description**: Build a new cross-surface snapshot contract immediately and converge both terminal and browser rendering on it.
- **Pros**: Strong long-term consistency story; one future-facing view contract.
- **Cons**: Expands MVP blast radius into the Web Dashboard and shared API design; slows delivery; increases migration complexity.
- **Why rejected**: The MVP should improve the Terminal Console first. The projection may be shaped so a shared snapshot is possible later, but that convergence is not required now.

## Consequences

### Positive

- Keeps orchestration/runtime behavior stable while enabling a meaningful UI redesign.
- Makes top-level mode behavior explicit and testable in the projection layer.
- Reduces renderer coupling to string parsing and fixed panel assumptions.

### Negative

- Requires coordinated changes in both `terminal_console_model.ml` and `terminal_console_mosaic.ml`.
- Forces test updates across projection and render helpers.
- Adds a more opinionated projection contract that must stay aligned with **Runtime State**.

### Risks

- **Over-modeling**: the projection could become broader than MVP needs.
  Mitigation: keep the new shape narrowly focused on shared chrome plus two top-level mode bodies.
- **Migration churn**: existing tests may be brittle during the transition.
  Mitigation: migrate projection tests first, then adapt renderer tests around new mode-aware helpers.
- **Future mismatch**: a later shared snapshot may want slightly different boundaries.
  Mitigation: keep the projection structured and serializable-friendly without forcing browser convergence now.

## Implementation Notes

The runtime handoff in `Terminal_console_runtime` and the startup branch selection in `main.ml` should remain unchanged for MVP.
