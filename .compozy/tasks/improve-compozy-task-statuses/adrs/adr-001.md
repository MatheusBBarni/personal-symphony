# ADR-001: Represent Compozy lifecycle at PRD Run level

## Status

Accepted

## Date

2026-05-12

## Context

Symphony's Compozy-backed Local Issue Tracker treats one `.compozy/tasks/<task_name>/` directory as a Compozy PRD Run and treats `task_NN.md` files as Compozy Task Steps inside the same Agent Worktree and Task Branch. Current task-step statuses (`pending`, `in_progress`, `completed`, `failed`, `skipped`) expose execution progress but do not clearly show which Stage Agent is active, such as planner or reviewer. The Compozy tracker also has a no-op status update boundary, so stage-level transitions do not persist as Compozy lifecycle state.

Operators need trustworthy lifecycle visibility and one aggregate Batch Pull Request after the Compozy PRD Run finishes, without turning task steps into separate Symphony issues or creating per-step pull requests.

## Decision

Represent lifecycle status at the Compozy PRD Run level, not by overloading each Compozy Task Step as a separate issue. V1 should persist and expose run-level lifecycle phases for planning, execution, review, successful completion, blocked/attention states, failed states, and skipped states while preserving the existing task-step execution statuses.

Batch Pull Request creation remains aggregate-only in batch mode. A Compozy PRD Run is eligible for one Batch Pull Request only after the run completes successfully and final Task Branch Integration is safe. Failed, skipped, blocked, or attention states may be terminal or visible, but they do not imply pull-request readiness.

## Alternatives Considered

### Alternative 1: Add planner/reviewer statuses directly to every task step

- **Description**: Expand task-step frontmatter statuses with values such as `in_planning` and `in_review`.
- **Pros**: Simple surface change; status remains close to the existing task files.
- **Cons**: Blurs the boundary between Compozy PRD Run lifecycle and task-step execution; risks inconsistent counts and ambiguous current-step detection.
- **Why rejected**: Task steps are internal progress within one work item. Stage Agent state belongs to the run-level lifecycle.

### Alternative 2: Treat each Compozy Task Step as a separate Symphony issue

- **Description**: Dispatch and track every `task_NN.md` as its own issue-like unit.
- **Pros**: Reuses existing stage transitions and issue status machinery.
- **Cons**: Violates the Compozy PRD Run model, encourages per-step PRs, fragments Agent Worktree and Task Branch semantics, and increases operator noise.
- **Why rejected**: The product contract says task steps are not separate Symphony issues.

### Alternative 3: Keep current statuses and document expected behavior

- **Description**: Leave runtime semantics unchanged and clarify that `in_progress` covers planning, engineering, and review.
- **Pros**: Lowest implementation cost.
- **Cons**: Does not solve operator ambiguity or missing transition diagnostics.
- **Why rejected**: The user need is trustworthy lifecycle visibility, not better prose around ambiguous state.

## Consequences

### Positive

- Operators can distinguish run-level planning, execution, review, completion, and attention states.
- Existing task-step counts and current-step behavior remain stable.
- The one-Compozy-PRD-Run-to-one-aggregate-Batch-Pull-Request boundary stays intact.
- V1 can ship without changing automatic PR defaults or Protected Trunk Branch behavior.

### Negative

- Adds a second visible status layer: run lifecycle state and task-step execution state.
- Requires clear UI/API labeling to avoid treating run lifecycle as task-step progress.
- Requires transition tests around final completion, failed/skipped steps, retry loops, and PR handoff failures.

### Risks

- **Decorative status risk**: New labels could mislead operators if transition rules are vague. Mitigation: define allowed transitions and failure/attention meanings in the PRD/TechSpec.
- **PR readiness ambiguity**: "All steps finished" could be misread as PR-ready. Mitigation: define PR eligibility as successful run completion plus safe final integration.
- **Scope creep risk**: Lifecycle cleanup could grow into a configurable workflow platform. Mitigation: defer custom lifecycle schemas and analytics to V2+.

## Implementation Notes

- Preserve task-step statuses: `pending`, `in_progress`, `completed`, `failed`, and `skipped`.
- Add or update run-level lifecycle persistence and Runtime State exposure for planning/review visibility.
- Implement Compozy tracker status updates at the PRD Run boundary instead of leaving them as a no-op.
- Keep Batch Pull Request behavior disabled by default and aggregate-only in batch mode.
