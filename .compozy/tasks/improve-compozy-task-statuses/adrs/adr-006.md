# ADR-006: Reconcile Compozy lifecycle from task-step progress while keeping readiness separate

## Status

Accepted

## Date

2026-05-13

## Context

The updated PRD fixed the product scope around a cross-surface transition contract, but the implementation still needed a tighter technical contract. The remaining design questions were not about adding new modules. They were about how existing state sources should relate when they disagree.

The codebase already has three relevant layers:

- Compozy Task Step frontmatter for execution progress, current-step selection, and terminal counts
- Runtime Home lifecycle metadata for run-level lifecycle, dispatch state, stage agent, readiness, and concise reasons
- Pull-request records and Runtime State fields for Batch Pull Request handoff outcomes

The user approved four technical constraints for V1:

1. keep one extended `Runtime_state.compozy_progress` object instead of splitting surfaces across multiple payloads
2. treat Compozy Task Step progress as authoritative for current step and terminal counts
3. keep dispatch state configuration-driven for routing, but map it into a separate operator-facing lifecycle layer
4. keep Batch Pull Request handoff failure modeled as lifecycle `pr_handoff` plus readiness `handoff_failed`, with detailed failure context remaining in existing pull-request records

Without an explicit contract, the implementation risks making Runtime Home lifecycle metadata feel like an independent source of truth, which would let stale lifecycle data contradict the actual Compozy Task Step files.

## Decision

Implement the Compozy status contract by reconciling run-level lifecycle metadata from Compozy Task Step progress, not by letting lifecycle metadata override task-step truth.

The technical contract is:

- `Compozy_tasks_tracker` remains authoritative for `current_step`, `completed`, `failed`, `skipped`, and `total`
- `Compozy_lifecycle` persists the operator-facing run summary under Runtime Home and is allowed to enrich the run with `lifecycle_state`, `dispatch_state`, `stage_agent`, `pr_readiness`, and `reason`
- reconciliation must downgrade stale lifecycle metadata when task-step progress shows a failed, skipped, blocked, or otherwise non-ready terminal outcome
- `dispatch_state` remains the routing-facing configured status string and must not be conflated with `lifecycle_state`
- Batch Pull Request handoff stays represented as `lifecycle_state = pr_handoff`; success or failure is expressed through `pr_readiness` and `handoff_status`
- `Runtime_state.compozy_progress` remains the single cross-surface payload used by Runtime State, Terminal Console, and Web Dashboard

V1 will therefore tighten existing helpers and tests instead of introducing a new status service, extra Runtime State object, or separate handoff lifecycle branch.

## Alternatives Considered

### Alternative 1: Make Runtime Home lifecycle metadata authoritative on disagreement

- **Description**: Treat persisted lifecycle JSON as the source of truth even when task-step files imply a different terminal outcome.
- **Pros**: Simpler runtime reads and fewer reconciliation rules.
- **Cons**: Risks stale or misleading operator state after retries, manual task-file edits, restart recovery, or failed handoff paths.
- **Why rejected**: The user required no regressions in Compozy Task Step progress behavior, and task-step progress is the closest source to actual execution state.

### Alternative 2: Split lifecycle, dispatch, and readiness into separate Runtime State payloads

- **Description**: Expose multiple parallel objects instead of one extended `compozy_progress` record.
- **Pros**: Cleaner conceptual separation between layers.
- **Cons**: Larger surface-area change, more frontend churn, and higher risk of cross-surface drift.
- **Why rejected**: The codebase already renders the extended `compozy_progress` object across the Terminal Console and Web Dashboard, so preserving that shape is the most direct path to consistency.

### Alternative 3: Model handoff failure as its own terminal lifecycle state

- **Description**: Add a separate lifecycle state for failed Batch Pull Request handoff instead of keeping `pr_handoff`.
- **Pros**: Makes failed handoff visually obvious in a single field.
- **Cons**: Adds redundant vocabulary and blurs the distinction between lifecycle phase and readiness outcome.
- **Why rejected**: The existing model already separates run phase from PR readiness; keeping `pr_handoff` with `handoff_failed` preserves that boundary.

## Consequences

### Positive

- Current-step selection and task-step counts remain trustworthy and backward-compatible.
- The operator-facing lifecycle stays rich without becoming an uncontrolled second truth source.
- Terminal Console, Runtime State, and Web Dashboard can stay aligned through one shared payload.
- Batch Pull Request handoff semantics remain explicit without adding more lifecycle labels.

### Negative

- Reconciliation logic becomes more important and must be covered carefully in tests.
- Some states, such as retrying and handoff failure, depend on interpreting multiple fields rather than one label.
- Developers need discipline to avoid using `dispatch_state` as a shortcut for lifecycle state.

### Risks

- **Incomplete reconciliation** could leave stale ready or completed metadata visible after task-step failure.
  - **Mitigation**: add focused backend tests for stale metadata downgrade and non-ready terminal paths.
- **Surface copy drift** could still confuse operators even if the payload is correct.
  - **Mitigation**: keep one payload shape and add Terminal Console plus frontend live-state checks.
- **Handoff semantics confusion** could make `pr_handoff` seem successful when readiness failed.
  - **Mitigation**: require explicit readiness and handoff-status rendering whenever handoff metadata exists.

## Implementation Notes

- Reuse `Compozy_lifecycle.load_or_backfill_reconciled` as the Runtime Home entry point for Runtime State assembly.
- Preserve the existing lifecycle JSON schema and `Runtime_state.compozy_progress` shape unless a concrete implementation gap requires a narrowly scoped field addition.
- Prefer targeted additions to `apps/backend/test/test_backend.ml` and `apps/frontend/test/liveState.test.mjs` over new test harnesses.
