# ADR-002: Use full V1 operator trust as the PRD product approach

## Status

Accepted

## Date

2026-05-12

## Context

The PRD must turn the approved idea into a business-focused product scope. Operators running Compozy-backed Symphony workflows need to trust the visible state of a Compozy PRD Run at all times. They need to know whether the run is planning, executing, reviewing, blocked, completed, failed, skipped, or in pull-request handoff, and they need a clear reason when all Compozy Task Steps are terminal but the run is not ready for a Batch Pull Request.

The existing idea and ADR-001 already establish that lifecycle status belongs to the Compozy PRD Run, while Compozy Task Step statuses remain execution progress. The user selected all current operator surfaces for V1 visibility: Runtime State, Terminal Console, and Web Dashboard.

## Decision

The PRD will use the full V1 operator trust approach. V1 will require run-level lifecycle visibility across Runtime State, Terminal Console, and Web Dashboard; a distinct not-PR-ready reason for terminal but non-ready runs; preservation of existing Compozy Task Step progress semantics; and aggregate-only Batch Pull Request readiness for successfully completed and safely integrated Compozy PRD Runs.

The PRD will not include lifecycle analytics, configurable lifecycle schemas, or guided repair automation in V1.

## Alternatives Considered

### Alternative 1: Backend-first lifecycle foundation

- **Description**: Expose lifecycle status in Runtime State and Terminal Console first, then defer Web Dashboard changes.
- **Pros**: Smaller first release, easier initial validation, lower UI scope.
- **Cons**: Leaves one current operator surface ambiguous and fails the selected all-surface visibility requirement.
- **Why rejected**: The primary success criterion is trustworthy run state at all times. A partial-surface rollout weakens that promise.

### Alternative 2: Compozy run control plane

- **Description**: Add full lifecycle visibility plus history, transition timelines, bottleneck analytics, and guided repair actions.
- **Pros**: Strong differentiation and a clearer path to advanced orchestration observability.
- **Cons**: Too large for V1 and likely to delay the reliability fix.
- **Why rejected**: The immediate product need is lifecycle correctness and aggregate PR readiness, not an analytics or repair platform.

## Consequences

### Positive

- The PRD can state one clear operator promise: every Compozy PRD Run has a trustworthy visible lifecycle state.
- Runtime State, Terminal Console, and Web Dashboard remain aligned for Compozy-backed workflows.
- Pull-request readiness becomes explicit rather than inferred from task-step terminal states.
- V1 stays focused by excluding analytics, custom schemas, and repair controls.

### Negative

- V1 includes more surface-area work than a backend-only rollout.
- Product copy must carefully distinguish lifecycle state, task-step progress, and PR readiness.

### Risks

- **Scope creep**: All-surface visibility could expand into dashboard redesign. Mitigation: limit V1 to existing operator surfaces and required lifecycle fields.
- **Ambiguous readiness**: Users may still conflate terminal task steps with PR readiness. Mitigation: require a distinct not-PR-ready reason.
- **Overpromising automation**: Operators may expect repair controls. Mitigation: keep repair actions out of V1 and document diagnostics-only behavior.

## Implementation Notes

This ADR sets product scope only. Technical design belongs in the TechSpec.
