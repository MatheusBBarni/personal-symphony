# ADR-004: Treat Compozy statuses as an explicit transition contract

## Status

Accepted

## Date

2026-05-13

## Context

The existing Compozy lifecycle work already introduced run-level lifecycle metadata and related UI coverage, but the remaining operator pain is narrower and more concrete: the agent does not consistently communicate the full expected set of transitions in a way that operators can trust end-to-end.

Current behavior spans multiple status layers. Compozy Task Steps keep execution-focused statuses such as `pending`, `in_progress`, `completed`, `failed`, and `skipped`. Compozy PRD Run lifecycle metadata adds richer run states such as `in_planning`, `in_execution`, `in_review`, `blocked`, `completed`, `failed`, `skipped`, `not_pr_ready`, and `pr_handoff`. The Compozy-backed Local Issue Tracker also persists a dispatch-facing state, and Pull Request handoff readiness is a separate dimension again. Operators can become uncertain when these layers diverge or when one surface uses terms such as `Human attention`, `blocked`, `running`, or `completed` without making the boundary explicit.

The user clarified that the primary persona is the workflow operator watching an active Compozy PRD Run, that V1 should be a complete end-to-end feature rather than a minimal patch, and that success means the Terminal Console and Web Dashboard reflect correct transitions within one poll cycle.

## Decision

Treat the remaining Compozy task-status work as a transition-contract problem, not as a request to invent more raw statuses.

V1 will explicitly define and validate four connected layers:

1. **Compozy Task Step status** for step execution progress
2. **Compozy PRD Run lifecycle state** for operator-visible run phase
3. **Dispatch state** for tracker and Stage Agent routing semantics
4. **Pull Request readiness / handoff state** for aggregate Batch Pull Request eligibility

The product scope will require a complete, operator-trustworthy transition contract across these layers. It must define which transitions are expected, which component owns them, how they map onto current operator surfaces, and how attention-oriented outcomes such as merge attention or non-retryable completion failures should appear without implying successful completion or pull-request readiness.

V1 will preserve the existing architectural direction:

- task-step statuses remain execution-focused
- lifecycle state remains run-level
- Pull Request handoff remains aggregate-only in batch mode
- dispatch-facing states may remain configuration-driven

V1 will not introduce configurable lifecycle schemas or a new workflow platform abstraction.

## Alternatives Considered

### Alternative 1: Add more statuses until the gaps disappear

- **Description**: Expand the lifecycle vocabulary further and patch each missing scenario with another visible state.
- **Pros**: Easy to explain locally when one missing case appears.
- **Cons**: Increases label sprawl, does not solve ambiguity between step status, lifecycle state, and dispatch state, and risks decorative statuses.
- **Why rejected**: The core problem is unreliable meaning and mapping, not a shortage of labels.

### Alternative 2: Reduce scope to a regression-suite-only cleanup

- **Description**: Keep the current product definition unchanged and only add tests for missing transitions.
- **Pros**: Lowest delivery risk and fast implementation.
- **Cons**: Leaves operator-facing semantics underspecified and does not fully address trust across current surfaces.
- **Why rejected**: The user selected a complete end-to-end outcome for operators, not a backend-only hardening pass.

### Alternative 3: Build a full lifecycle history and repair control plane now

- **Description**: Expand V1 to include transition timelines, guided repair, and deeper observability.
- **Pros**: Higher differentiation and stronger long-term story.
- **Cons**: Larger scope, slower delivery, and distracts from the immediate correctness problem.
- **Why rejected**: The highest-leverage move is to make current status transitions trustworthy before adding advanced control-plane features.

## Consequences

### Positive

- Operators get a clearer answer to “what state is this run in and why?” without reading logs.
- Existing lifecycle code and tests can be tightened rather than replaced.
- The product language can distinguish execution progress, run phase, routing state, and PR readiness more consistently.
- Attention-oriented outcomes remain visible without pretending the run is complete or PR-ready.

### Negative

- V1 documentation and acceptance coverage become more explicit and therefore more demanding.
- Some current terms may need better operator-facing explanation even if the internal implementation remains similar.
- Multiple status layers remain in the system, so naming discipline matters.

### Risks

- **Semantic drift**: different surfaces could keep presenting the same underlying situation with slightly different language.
  - **Mitigation**: define one transition contract and require surface consistency tests.
- **Status conflation**: operators may still confuse dispatch state with lifecycle state.
  - **Mitigation**: document the layer boundaries and keep examples explicit.
- **Scope creep**: the transition-contract effort could expand into configurable workflows or analytics.
  - **Mitigation**: keep V1 focused on correctness, mapping, and visibility only.

## Implementation Notes

- This ADR updates the product framing for the idea and downstream PRD/TechSpec.
- The implementation should prefer extending current lifecycle semantics and tests over introducing new persistence models.
- The acceptance model should include transitions for planning, execution, review, retry, failure, skipped, blocked or human-attention outcomes, completion, not-PR-ready outcomes, and PR handoff outcomes.
