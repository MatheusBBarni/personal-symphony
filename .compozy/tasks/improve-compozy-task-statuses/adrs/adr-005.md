# ADR-005: Use a cross-surface transition contract as the PRD approach

## Status

Accepted

## Date

2026-05-13

## Context

The updated idea reframed `improve-compozy-task-statuses` as a transition-contract problem across four connected status layers: Compozy Task Step progress, Compozy PRD Run lifecycle state, dispatch state, and Pull Request readiness. The remaining PRD question was how to scope V1 around that insight.

The user clarified that the primary persona is the workflow operator watching an active Compozy PRD Run. The most important operator decision for V1 is active-state trust, but the operator also needs the full distinction between planning, executing, reviewing, and stalled or retrying states. The user selected perfect consistency across all current operator surfaces as the top experience priority and required that V1 preserve existing Compozy Task Step progress behavior without regressions.

This leaves three plausible product approaches:

1. a full transition-contract approach across all operator surfaces
2. an active-state-first approach that prioritizes in-flight run clarity
3. a PR-readiness-first approach that prioritizes end-of-run trust

## Decision

Use the cross-surface transition-contract approach for the PRD.

V1 will define one operator-trust contract across Runtime State, Terminal Console, and Web Dashboard. The product must make active-state distinctions clear, keep Pull Request readiness consistent with the visible run state, and preserve current Compozy Task Step progress semantics.

This approach sets the PRD scope around three product promises:

- the operator can tell whether a run is planning, executing, reviewing, retrying, stalled, blocked, completed, or in handoff
- the same run does not tell conflicting stories across different operator surfaces
- task-step progress remains stable and understandable while run-level trust improves

## Alternatives Considered

### Alternative 1: Active-state clarity first

- **Description**: Focus V1 on in-flight states such as planning, execution, review, retry, and stall, while leaving some end-of-run readiness semantics for later.
- **Pros**: Smaller and faster than the full transition-contract approach; directly improves the most common live-operator workflow.
- **Cons**: Weaker guarantee that visible run state and PR readiness stay aligned across all surfaces.
- **Why rejected**: The user explicitly prioritized cross-surface consistency and non-contradictory PR readiness, not just active-run clarity.

### Alternative 2: PR-readiness safety first

- **Description**: Focus V1 on terminal and handoff outcomes so blocked, failed, skipped, completed, and not-ready states cannot be misread at review time.
- **Pros**: Strong protection against false handoff confidence and bad review signaling.
- **Cons**: Under-serves operators during active runs, where most day-to-day monitoring happens.
- **Why rejected**: The user said active-state trust matters most and wants the operator to see all active distinctions clearly.

## Consequences

### Positive

- The PRD can define one clear operator promise instead of a set of unrelated status improvements.
- Runtime State, Terminal Console, and Web Dashboard are all first-class parts of V1 rather than follow-up surfaces.
- Active-state visibility and PR-readiness consistency stay connected instead of competing for scope.
- Existing Compozy Task Step progress remains protected as a product constraint.

### Negative

- V1 scope is broader than a narrowly targeted active-state or PR-readiness cleanup.
- Product wording must be disciplined so operators do not confuse task-step progress with run lifecycle or dispatch state.
- Documentation and acceptance criteria need to cover more scenarios.

### Risks

- **Surface drift**: one surface may lag the others in wording or timing.
  - **Mitigation**: require explicit cross-surface consistency success metrics.
- **Overloaded status language**: operator-facing labels may still blur lifecycle, dispatch, and readiness concepts.
  - **Mitigation**: define each layer’s meaning in the PRD and examples.
- **Regression pressure**: broader scope may tempt changes to current task-step semantics.
  - **Mitigation**: make “no regressions in Compozy Task Step progress behavior” a hard V1 constraint.

## Implementation Notes

- This ADR defines the PRD product approach only.
- The PRD should treat cross-surface consistency and PR-readiness alignment as core goals, not secondary polish.
- The downstream TechSpec should preserve the product boundary that task-step progress and run-level lifecycle are distinct layers.
