# ADR-003: Persist dispatch-aware Compozy lifecycle in Runtime Home

## Status

Accepted

## Date

2026-05-12

## Context

The TechSpec must implement the PRD requirement that every Compozy PRD Run exposes a trustworthy lifecycle state across Runtime State, Terminal Console, and Web Dashboard. Existing Compozy Task Step frontmatter stores step execution progress, and existing Runtime State exposes a `compozy_progress` object with current step and counts. The Compozy tracker adapter currently treats status updates as no-ops, so planner/reviewer transitions and pull-request readiness do not persist at the Compozy PRD Run boundary.

The chosen design must preserve Compozy Task Step statuses and counts, keep the Compozy-backed Local Issue Tracker free from GitHub API requirements, support restart recovery, and avoid creating per-step Symphony issues or per-step pull requests.

## Decision

Persist Compozy PRD Run lifecycle metadata under Runtime Home `.symphony/state/`, not inside task-step frontmatter and not as a new Git-tracked Compozy task file. The lifecycle store will be dispatch-aware: it can participate in Compozy PRD Run Stage Agent routing and readiness decisions while preserving Compozy Task Step frontmatter as the source of step execution progress.

Runtime State will extend the existing `compozy_progress` object with lifecycle fields instead of adding a separate top-level lifecycle object. The extended progress object will include the current lifecycle state, selected Stage Agent when known, PR readiness state, and concise reason text when the run is blocked or not PR-ready. Existing pull-request handoff records remain the detailed source for PR URL, head/base branch, status, and error; lifecycle mirrors readiness and handoff phase for operator clarity.

Existing Compozy PRD Runs without lifecycle metadata will use lazy backfill on first discovery. The backfill derives a safe lifecycle from current task-step progress and existing orchestration signals, then writes Runtime Home lifecycle metadata during normal polling.

## Alternatives Considered

### Alternative 1: Derive lifecycle only in Runtime State

- **Description**: Compute lifecycle from task-step progress, running rows, issue errors, integration attention, and pull-request handoff state without any persisted lifecycle metadata.
- **Pros**: Minimal storage changes and no new files.
- **Cons**: Weak restart continuity and no durable run-level lifecycle record for dispatch-aware routing.
- **Why rejected**: The selected approach requires dispatch-aware lifecycle and trustworthy state across restarts.

### Alternative 2: Persist lifecycle sidecar files in each Compozy PRD Run

- **Description**: Add a run-level metadata file under `.compozy/tasks/<slug>/`.
- **Pros**: Keeps lifecycle data near the Compozy PRD Run and can travel with task files.
- **Cons**: Adds runtime churn to Workspace Repository user data, risks accidental commits, and expands the Runtime Contract surface.
- **Why rejected**: Runtime lifecycle is orchestration state and belongs under Runtime Home.

### Alternative 3: Add a separate top-level `compozy_lifecycle` Runtime State object

- **Description**: Keep `compozy_progress` unchanged and expose lifecycle through a new optional Runtime State object.
- **Pros**: Strong separation between progress and lifecycle fields.
- **Cons**: Forces every consumer to join two Compozy-specific objects for one displayed PRD Run.
- **Why rejected**: Extending `compozy_progress` is smaller, preserves existing consumers that ignore unknown JSON fields, and keeps the dashboard panel cohesive.

### Alternative 4: Keep PR readiness only in existing pull-request records

- **Description**: Do not mirror PR readiness into Compozy lifecycle; rely on `pull_request` and `pull_requests` Runtime State fields.
- **Pros**: Avoids duplicating a status summary.
- **Cons**: Operators still need to correlate task progress, run state, and PR handoff state manually.
- **Why rejected**: The PRD requires a clear not-PR-ready state with a reason at the Compozy PRD Run level.

## Consequences

### Positive

- Compozy Task Step frontmatter remains focused on step progress.
- Runtime lifecycle metadata can survive process restarts without polluting user-authored Compozy task files.
- Runtime State, Terminal Console, and Web Dashboard can consume one extended `compozy_progress` object.
- PR readiness is visible at the run level while detailed handoff data remains in existing pull-request records.

### Negative

- Lifecycle and task-step progress now have separate persistence locations.
- Dispatch-aware lifecycle requires careful startup and lazy-backfill behavior to avoid stale routing.
- Frontend and backend parsers must remain compatible with older snapshots that lack lifecycle fields.

### Risks

- **Stale lifecycle metadata**: Runtime Home state may diverge from task files after manual edits. Mitigation: recompute or reconcile lifecycle from task-step progress during discovery and polling.
- **Routing ambiguity**: Dispatch-aware lifecycle could conflict with current task-step state. Mitigation: define precedence rules in the TechSpec and keep task-step progress authoritative for current-step selection.
- **Snapshot compatibility**: Older snapshots omit lifecycle fields. Mitigation: treat missing fields as compatible absence and derive fallback display text.

## Implementation Notes

This ADR sets the technical direction for the TechSpec. Exact type names, file names, and transition functions belong in the TechSpec and implementation tasks.
