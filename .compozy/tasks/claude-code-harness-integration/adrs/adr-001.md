# ADR-001: First-Class Harness Runtime Settings

## Status

Accepted

## Date

2026-05-08

## Context

Symphony currently separates logical Stage Agent behavior from execution behavior in code, but the Runtime Settings vocabulary is confusing. Logical Stage Agents such as `planner`, `engineer`, and `reviewer` are selected through `stageAgents.stages[].agent` and resolved to `.symphony/agents/*.md` instruction files. Execution tools such as Codex and PI are internally modeled as Agent Harnesses, but the Runtime Settings JSON currently uses `agents` for those harness definitions.

Issue 52 asks for Claude Code integration. The larger product need is not only adding Claude as another command string; it is clarifying the Runtime Contract so Workspace Repositories can define multiple execution harnesses such as Codex, PI, Claude, and future tools, then assign logical agents to those harnesses.

Claude Code does not provide Codex `/goal` semantics. Claude does provide non-interactive CLI and Agent SDK execution loops with controls for streaming output, turn limits, budget limits, permission modes, sessions, hooks, and tool access. V1 must avoid promising semantic parity where the underlying tools differ.

## Decision

V1 will introduce first-class `harnesses` Runtime Settings for execution adapters such as `codex`, `pi`, and `claude`.

Logical agents become Runtime Settings definitions under `agents`. A logical agent such as `planner` or `engineer` selects a named harness and may override per-agent execution settings such as `model`, `reasoningEffort`, `turnTimeoutMs`, `readTimeoutMs`, and `stallTimeoutMs`. Stages continue to select logical agents. Existing Runtime Settings using legacy top-level `codex` or current `agents.*` harness definitions remain supported only as migration input when unambiguous. If a Workspace Repository defines both new `harnesses` entries and legacy `agents.*` harness entries for the same runtime meaning, Symphony reports a readiness error that tells the user to move execution definitions to `harnesses`.

Harness loop behavior will be explicit and configurable per Harness through a `loop` object. `loop.enabled` controls whether Symphony sends a loop command to the Harness, and `loop.command` stores the command string, such as `/goal` for Codex. Claude Code support will ship as a bounded Claude Harness that does the same class of non-interactive task execution as `codex exec`; its V1 loop should be disabled unless the user configures a Claude-supported loop command in the future. V1 will use Claude CLI `stream-json` for execution and output observation. V1 will not claim Codex `/goal` parity and will not implement a custom Symphony loop solely to simulate `/goal`.

## Alternatives Considered

### Alternative 1: Add Claude Under Current `agents` Harness Settings

- **Description**: Keep using `agents.claude` as the Claude Harness definition.
- **Pros**: Smallest parser and documentation change; follows the current PI pattern.
- **Cons**: Preserves the naming collision between logical agents and execution harnesses; makes future provider support harder to explain.
- **Why rejected**: The user goal is explicitly to separate harness definitions from agent definitions, and the current vocabulary is the source of the product confusion.

### Alternative 2: Build A Claude Loop That Mimics Codex `/goal`

- **Description**: Implement a Symphony-owned loop for Claude so Claude tasks behave like Codex goal handoff.
- **Pros**: Could reduce behavioral differences between Codex and Claude for operators.
- **Cons**: High implementation and maintenance cost; risks inventing semantics before real Claude usage proves the need; expands retry, budget, prompt, and failure-handling surface area.
- **Why rejected**: V1 should validate Claude as a harness through native Claude controls first. Loop behavior is Harness-specific and should be explicit configuration, not hidden provider parity.

### Alternative 3: Require A Breaking Runtime Contract Migration

- **Description**: Remove support for legacy `codex` and current `agents.*` harness definitions.
- **Pros**: Simplifies the final schema.
- **Cons**: Breaks existing Workspace Repositories and violates compatibility expectations for Runtime Contract evolution.
- **Why rejected**: Existing Runtime Contracts must continue to load, and Bootstrap must remain idempotent.

## Consequences

### Positive

- Clarifies the boundary between logical Stage Agents and execution Harnesses.
- Enables Claude Code integration without treating Claude as a Codex clone.
- Preserves existing Workspace Repository Runtime Contracts.
- Creates a provider-neutral foundation for future harnesses.
- Lets future Harness loop commands be adopted through Runtime Settings without changing core semantics.

### Negative

- Runtime Settings parsing must distinguish new logical `agents` definitions from legacy harness-shaped `agents.*` input.
- Documentation must explain compatibility behavior clearly enough to avoid two parallel mental models.
- Some runtime state and dashboard labels may need follow-up cleanup where they still say `codex` for provider-neutral usage.

### Risks

- **Claude semantic drift**: Claude retries, sessions, limits, and loop support may behave differently from Codex. Mitigation: document Claude Harness semantics explicitly, default its loop to disabled, and expose deterministic failure states.
- **Configuration ambiguity during migration**: Users may define both `harnesses` and legacy `agents.*`. Mitigation: report a readiness error and require execution definitions to move to `harnesses`.
- **Expanded command execution surface**: Additional harnesses increase the risk of secret leakage or unsafe tool use. Mitigation: keep secrets out of Runtime Settings, preserve Agent Worktree isolation, and model harness limits such as timeouts, permissions, budget, and allowed tools.

## Implementation Notes

- Add `harnesses` parsing for execution definitions.
- Add `harnesses.<name>.loop.enabled` and `harnesses.<name>.loop.command` parsing.
- Add `agents` parsing for logical agent definitions shaped like:
  - `agents.<name>.harness`
  - `agents.<name>.model`
  - `agents.<name>.reasoningEffort`
  - `agents.<name>.turnTimeoutMs`
  - `agents.<name>.readTimeoutMs`
  - `agents.<name>.stallTimeoutMs`
- Preserve top-level `codex` compatibility.
- Treat current harness-shaped `agents.*` as legacy migration input; when it conflicts with `harnesses`, emit a readiness error instead of silently choosing precedence.
- Add Claude Harness readiness checks for executable/authentication expectations without storing secret values.
- Use Claude CLI `stream-json` for Claude Harness V1.
- Keep Bootstrap idempotent: create missing defaults without overwriting user-edited Runtime Contract files.
- Update `CONTEXT.md`, README Runtime Contract examples, and backend tests for compatibility and precedence.
