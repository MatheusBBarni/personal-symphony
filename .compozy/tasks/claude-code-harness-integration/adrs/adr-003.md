# ADR-003: Runtime Settings Resolution and Loop Semantics

## Status

Accepted

## Date

2026-05-08

## Context

The current backend treats top-level Runtime Settings `agents` as Agent Harness definitions. Stage Agent mappings can also carry `harness`, which selects the execution Harness directly. The new Runtime Contract must use `harnesses` for execution backends and `agents` for logical agent execution selection.

The current Stage Goal Handoff is stage-scoped and Codex-specific. It prepends `/goal` when `stageAgents.stages[].goal.enabled` is true and the selected Harness supports Codex goal handoff. The new Harness model introduces `loop.enabled` and `loop.command`, but operators still need to control loop handoff per stage without editing agent definitions each time they test a different model or Harness.

## Decision

Runtime Settings resolution will use this path:

1. `stageAgents.stages[].agent` selects a logical agent by name.
2. `agents.<name>` defines execution overrides for that logical agent.
3. `agents.<name>.harness` selects a Harness from `harnesses`.
4. Agent execution fields override Harness defaults field-by-field.
5. Missing agent execution fields inherit from the selected Harness.

Stage-level `harness` will be removed from the new Runtime Contract. Existing `stageAgents.stages[].harness` values are legacy input and should produce migration diagnostics instead of defining the new steady-state path.

Loop handoff remains gated by `stageAgents.stages[].goal.enabled`. When a stage enables goal handoff, Symphony checks the selected Harness. If the selected Harness has `loop.enabled: true` and a non-empty `loop.command`, Symphony prepends that loop command with Stage Goal Context. If the selected Harness has loop disabled or no usable command, Symphony silently runs the normal prompt without loop handoff.

## Alternatives Considered

### Alternative 1: Keep Stage-Level Harness Override

- **Description**: Let `stageAgents.stages[].harness` override `agents.<name>.harness`.
- **Pros**: Preserves the current explicit stage override behavior.
- **Cons**: Keeps two places where execution selection can happen and weakens the new logical agent boundary.
- **Why rejected**: The selected PRD goal is configuration clarity. Stages should route to logical agents, and logical agents should choose Harnesses.

### Alternative 2: Require Every Agent Field Explicitly

- **Description**: Treat missing `agents.<name>` execution fields as readiness errors.
- **Pros**: Makes resolved values obvious from the agent block alone.
- **Cons**: Duplicates model and timeout values across agents and makes common Harness defaults less useful.
- **Why rejected**: Field-by-field inheritance keeps the MVP smaller and reduces repetitive settings.

### Alternative 3: Block Dispatch When Stage Goal Is Enabled But Harness Loop Is Disabled

- **Description**: Treat `goal.enabled: true` with a non-loop Harness as a readiness error.
- **Pros**: Prevents accidental loss of loop handoff.
- **Cons**: Makes model or Harness experiments require stage edits and can block useful non-loop execution.
- **Why rejected**: Operators want to keep stage goal settings stable while testing agent models and Harnesses. Silent skip preserves dispatch when the selected Harness cannot satisfy loop handoff.

## Consequences

### Positive

- Stage mappings have one responsibility: route statuses to logical agents.
- Logical agents have one responsibility: select Harness and execution overrides.
- Harnesses have one responsibility: define provider command, defaults, and loop capability.
- Operators can test a different Harness on an agent without editing stage goal settings.

### Negative

- Silent loop skip can surprise operators who expected goal handoff.
- Legacy stage-level Harness configuration requires a migration path.

### Risks

- **Hidden loop disablement**: A stage may have `goal.enabled: true` but selected Harness loop disabled. Mitigation: include Harness and loop status in diagnostics or Runtime State where practical.
- **Migration friction**: Existing Runtime Settings with stage-level `harness` need remediation. Mitigation: readiness diagnostics should point to `agents.<name>.harness`.

## Implementation Notes

- Add a logical agent model separate from Agent Harness.
- Resolve selected Harness through stage agent name -> logical agent -> Harness.
- Merge agent overrides over Harness defaults field-by-field.
- Keep stage `goal.enabled` parsing.
- Replace hard-coded `/goal` with selected Harness `loop.command`.
- Skip loop handoff when stage goal is enabled but the selected Harness has loop disabled or an empty command.
