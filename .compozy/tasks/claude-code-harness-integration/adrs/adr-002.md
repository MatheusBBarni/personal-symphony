# ADR-002: Clarity-First PRD Scope

## Status

Accepted

## Date

2026-05-08

## Context

The approved idea establishes first-class `harnesses`, logical `agents` in Runtime Settings, explicit Harness loop configuration, and Claude Code execution through CLI `stream-json`. The PRD must choose the product posture for the first release.

The primary user outcome selected for the PRD is operator configuration clarity. Operators should be able to configure `planner`, `engineer`, and `reviewer` across different Harnesses without ambiguity. The MVP should keep logical agent definitions focused on Harness selection and execution overrides, while preserving stage routing and prompt files in their current product concepts.

## Decision

The PRD will use the Clarity-First Runtime Contract approach.

V1 will optimize for clear Runtime Settings language before broader Claude-specific functionality. It will introduce `harnesses` for execution backends and `agents` for logical agent execution selection. MVP logical agent definitions include only the Harness reference and execution overrides such as `model`, `reasoningEffort`, `turnTimeoutMs`, `readTimeoutMs`, and `stallTimeoutMs`.

Legacy harness-shaped `agents.*` settings will not silently keep running. They will produce a readiness error that blocks dispatch until the operator moves execution definitions to `harnesses`.

## Alternatives Considered

### Alternative 1: Compatibility-First Migration

- **Description**: Introduce `harnesses`, but allow legacy harness-shaped `agents.*` settings to keep running with warnings for one release.
- **Pros**: Reduces immediate migration friction for existing Workspace Repositories.
- **Cons**: Keeps two competing meanings for `agents` alive and delays the configuration clarity goal.
- **Why rejected**: The selected success metric is unambiguous mixed-Harness agent configuration, and warnings would preserve the ambiguity.

### Alternative 2: Claude-First Launch

- **Description**: Make Claude Code support the visible headline and change Runtime Settings only as much as required to run Claude.
- **Pros**: Faster visible delivery for issue 52.
- **Cons**: Risks shipping another provider-specific exception while leaving Runtime Contract confusion unresolved.
- **Why rejected**: The user selected configuration clarity as the first outcome, and the idea’s leverage comes from a provider-neutral Runtime Contract.

## Consequences

### Positive

- The PRD has a crisp user outcome: operators can read and edit Runtime Settings without confusing logical agents with execution Harnesses.
- Mixed-Harness planner/engineer/reviewer configuration becomes the central MVP workflow.
- Readiness diagnostics become a product migration tool instead of hiding ambiguous behavior.

### Negative

- Some existing Workspace Repositories may need manual settings edits before dispatch resumes.
- Claude Code may feel less headline-driven in the first release because the Runtime Contract refactor leads the scope.

### Risks

- Operators may perceive blocking readiness errors as too strict. Mitigation: make the remediation message specific and include before/after settings examples.
- The MVP may under-serve users who only want Claude support. Mitigation: include Claude Harness V1 in the same rollout, but keep it framed by the clearer Runtime Contract.

## Implementation Notes

- PRD language should stay focused on WHAT operators can configure and WHY it matters.
- TechSpec should decide exact Runtime State/dashboard naming changes.
- TechSpec should define the exact readiness error wording and legacy shape detection.
