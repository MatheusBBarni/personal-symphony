# ADR-001: Scope Mosaic Terminal Console as a Runtime State command center

## Status

Accepted

## Date

2026-05-12

## Context

Personal Symphony currently starts the **Terminal Console** by default in a **Workspace Repository**, while the **Web Dashboard** provides the richer live operational view over **Runtime State** through `GET /api/v1/state` and the **Live Dashboard Connection** at `/api/v1/state/live`. The current Terminal Console is mostly static text output, so a solo developer running active orchestration must often switch to the Web Dashboard or inspect Runtime Home files/logs to understand task progress and take common actions.

The proposed idea evaluates Mosaic (`invariant-hq/mosaic`) as an OCaml-native way to build a richer Terminal Console. Mosaic is young (`opam` package `mosaic.0.1.0`, created in 2025, roughly 76 GitHub stars) but provides a TEA runtime, widgets, Matrix terminal rendering/input, and Toffee layout. Broader TUI and AI-agent dashboard markets are active, so the differentiator is not a generic terminal UI; it is a Symphony-specific operational surface over **Runtime State**, **Ordered Queue**, **Compozy PRD Run** progress, **Agent Worktrees**, **Task Branches**, **Readiness Gaps**, and task execution details.

The council found consistent tension between the product need for common controls and the security/architecture risk of turning a UI idea into a second orchestration path. The **Live Dashboard Connection** is a server-to-client Runtime State stream, not a command channel. The idea must not change **Runtime Contract** defaults, **Task Branch** cleanup, auto-merge defaults, npm launcher/package behavior, or the tracker model.

## Decision

V1 will scope the Mosaic work as a read-first **Terminal Console** command center over shared **Runtime State**. It should render active-run state clearly and support only a narrow, allowlisted set of common controls when those controls can use existing or explicitly shared backend command semantics.

The Terminal Console must not become a parallel orchestrator. **Runtime State** remains the source of truth for visible state. Mutating controls must not use the **Live Dashboard Connection** as a command channel; they need explicit command boundaries with validation, root enforcement, confirmation for destructive or branch-affecting actions, secret redaction, terminal escape sanitization, and audit-friendly output. If a desired control requires new runtime semantics, it is out of V1.

Mosaic is treated as a reversible implementation choice behind the Terminal Console surface. User-facing product language should continue to use **Terminal Console** unless `CONTEXT.md` is intentionally updated later.

## Alternatives Considered

### Alternative 1: Read-only Mosaic Terminal Console only

- **Description**: Render Runtime State in Mosaic with no mutating controls.
- **Pros**: Lowest security and orchestration risk; validates Mosaic rendering and active-run comprehension quickly; avoids new command API design.
- **Cons**: Does not fully test the faster-operations KPI for common actions within five keystrokes; may not reduce Web Dashboard fallback enough.
- **Why rejected**: Too weak for the user-selected V1 scope and Strategic Bet, but its read-first sequencing should shape implementation.

### Alternative 2: Broad terminal command platform

- **Description**: Make the Terminal Console a full replacement for the Web Dashboard with extensive controls, configurable layouts, and orchestration actions.
- **Pros**: Strong ambition; could make Symphony feel terminal-native and highly differentiated.
- **Cons**: High risk of duplicating dashboard semantics, creating a second orchestration path, expanding attack surface, and coupling backend semantics to UI needs.
- **Why rejected**: Too broad for V1 and incompatible with the constraint to preserve Runtime Contract/default semantics.

### Alternative 3: Keep Terminal Console static and improve only the Web Dashboard

- **Description**: Avoid Mosaic and continue investing in the browser-based Web Dashboard.
- **Pros**: Lower dependency risk; Web Dashboard already consumes Runtime State; avoids terminal rendering/input complexity.
- **Cons**: Misses the terminal-native active-run workflow; preserves browser context switching for solo developers.
- **Why rejected**: Does not address the selected problem of faster terminal operations during active orchestration runs.

## Consequences

### Positive

- Gives solo developers a terminal-native operational surface during active orchestration.
- Reuses **Runtime State** rather than creating a competing dashboard state model.
- Keeps V1 focused on active-run speed while preserving Web Dashboard semantics.
- Creates a path to common controls without changing Runtime Contract defaults or orchestration behavior.

### Negative

- Adds a young Mosaic dependency and terminal UI testing burden.
- Requires careful command-boundary design before even small mutating controls ship.
- May duplicate some Web Dashboard presentation logic unless shared state formatting boundaries are defined.

### Risks

- **Terminal escape injection** from issue titles, task logs, branch names, or Agent Worktree output. Mitigation: sanitize untrusted strings before rendering.
- **Control-plane bypass** where keyboard actions mutate orchestration outside established validation. Mitigation: allowlisted commands only, shared backend semantics, confirmations, and root enforcement.
- **Mosaic maturity risk** from a small OCaml TUI ecosystem. Mitigation: keep Mosaic behind a reversible Terminal Console adapter and validate with a narrow slice.
- **Scope creep** into Web Dashboard replacement or plugin platform. Mitigation: keep full parity, custom layouts, theming, and broad configuration out of V1.

## Implementation Notes

- V1 should prioritize Runtime State summary, active task details, Ordered Queue progress, Compozy PRD Run progress, Readiness Gaps, token usage, and task errors.
- Candidate V1 controls should be limited to safe actions such as refresh/state reload, navigation/filtering, opening relevant paths or dashboard links, and only existing backend-supported orchestration commands that preserve current semantics.
- Controls that affect Task Branch integration, cleanup, auto-merge, tracker model, or Runtime Contract defaults are out of scope.
- The Web Dashboard remains the richer browser surface and fallback for deep inspection.
