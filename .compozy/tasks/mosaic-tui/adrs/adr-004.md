# ADR-004: Add Mosaic as the direct Terminal Console dependency

## Status

Accepted

## Date

2026-05-12

## Context

The PRD names Mosaic as the requested toolkit for the richer default **Terminal Console**. Mosaic is an OCaml-native terminal UI framework with a TEA runtime, widgets, Matrix terminal rendering/input, and Toffee layout. The Product Repository backend is OCaml/Dune, so Mosaic aligns with the existing backend language and avoids introducing a second runtime just for the terminal surface.

Current Product Repository dependencies do not include Mosaic. `dune-project` declares Dune language 3.14 and package dependencies limited to `ocaml`, `dune`, `yojson`, `cmdliner`, and `alcotest`. Mosaic `0.1.0` metadata requires `dune >= 3.19` and depends on `matrix`, `toffee`, `cmarkit`, and `tree-sitter`.

## Decision

The MVP will add Mosaic as a direct dependency of the backend executable path that owns the Terminal Console. The implementation plan must include the necessary Dune/opam metadata updates to make the dependency explicit and reproducible.

The TechSpec should treat Matrix and Toffee as transitive Mosaic dependencies unless implementation proves a direct dependency is required. It should not add alternate TUI frameworks.

## Alternatives Considered

### Alternative 1: Defer Mosaic behind a renderer boundary

- **Description**: Design pure projection/rendering boundaries first and postpone adding Mosaic until a later prototype.
- **Pros**: Reduces immediate build/dependency risk; allows validation of state projection without dependency upgrades.
- **Cons**: Delays the central toolkit choice and creates throwaway rendering work.
- **Why rejected**: The user selected direct Mosaic adoption for MVP.

### Alternative 2: Use Matrix only

- **Description**: Use Matrix terminal rendering/input directly instead of Mosaic widgets and TEA runtime.
- **Pros**: Lower-level control; potentially fewer abstractions.
- **Cons**: Gives up Mosaic's higher-level UI model and widgets; increases custom UI code.
- **Why rejected**: The PRD and user intent are for Mosaic, not a lower-level terminal toolkit.

### Alternative 3: Use a non-OCaml TUI framework

- **Description**: Build the Terminal Console in Ink, Bubble Tea, Textual, Ratatui, or another ecosystem.
- **Pros**: More mature ecosystems and larger communities.
- **Cons**: Adds cross-runtime packaging and process boundaries to an OCaml backend product.
- **Why rejected**: Adds avoidable integration complexity and conflicts with the Mosaic-specific request.

## Consequences

### Positive

- Keeps the Terminal Console implementation in the backend language.
- Uses a UI framework designed for typed model/update/view flows.
- Avoids a separate Node, Go, Python, or Rust terminal client.

### Negative

- Requires build metadata changes and likely a Dune version update.
- Adds young dependencies to the backend build path.
- May affect package build and release validation, so packaging impact must be checked before implementation lands.

### Risks

- **Dependency maturity**: Mitigate with a narrow MVP and pure projection tests that reduce direct UI coupling.
- **Build compatibility**: Mitigate by validating `pnpm backend:build`, `pnpm test`, and packaging commands after dependency changes.
- **Over-coupling to Mosaic APIs**: Mitigate by isolating Mosaic-specific rendering in Terminal Console modules.

## Implementation Notes

- Update Dune/opam metadata explicitly rather than relying on undeclared local packages.
- Keep Mosaic use out of core orchestration modules.
- Run package/build validation after dependency changes because distribution depends on the backend executable.
