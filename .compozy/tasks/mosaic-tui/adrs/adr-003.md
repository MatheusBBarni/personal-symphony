# ADR-003: Run Mosaic in-process with Orchestrator Runtime State callbacks

## Status

Accepted

## Date

2026-05-12

## Context

The current default `symphony` runtime selects `Cli_mode.Terminal_console`, prints a static terminal snapshot, then lets `Orchestrator.run_forever` own the foreground loop. Web Dashboard mode already proves a different runtime shape: it runs the orchestrator in a background thread and uses `Orchestrator.make ~notify_state` to publish **Runtime State** snapshots to another foreground surface.

The Mosaic Terminal Console needs an interactive foreground terminal loop while orchestration continues. The PRD requires the richer **Terminal Console** to become the default `symphony` experience, use **Runtime State** as the visible source of truth, and avoid task lifecycle mutation in MVP.

## Decision

The MVP will run Mosaic in-process as the foreground Terminal Console loop and run `Orchestrator.run_forever` in a background thread for normal orchestration. The Terminal Console will receive state through `Orchestrator.make ~notify_state` and an in-memory state handoff owned by the process.

For readiness-blocked runs, the Terminal Console will render the readiness Runtime State without starting orchestration, preserving the existing dispatch-blocking behavior. `--once` remains non-interactive and should not start Mosaic.

## Alternatives Considered

### Alternative 1: Separate terminal client connecting to local server

- **Description**: Start a local server and run a separate terminal client that consumes HTTP/WebSocket state.
- **Pros**: Reuses the Web Dashboard delivery model; decouples rendering from orchestration process internals.
- **Cons**: Adds a second process/client boundary for the default local experience; pressures `--web` semantics; more moving pieces for MVP.
- **Why rejected**: The default Terminal Console should remain a single `symphony` process and not require server/client orchestration for MVP.

### Alternative 2: Child process Terminal Console

- **Description**: Keep orchestration in the parent foreground process and launch a child process for Mosaic rendering.
- **Pros**: Isolates terminal rendering crashes from orchestration.
- **Cons**: Requires IPC, lifecycle supervision, and duplicated startup/error handling.
- **Why rejected**: Too much infrastructure for a read-first MVP.

### Alternative 3: Keep static Terminal Console foreground loop

- **Description**: Preserve current foreground orchestration loop and periodically print richer static summaries.
- **Pros**: Lowest architectural change.
- **Cons**: Does not deliver Mosaic interactivity or keyboard-first inspection.
- **Why rejected**: Fails the PRD requirement for a richer default Terminal Console.

## Consequences

### Positive

- Reuses the existing Runtime State notification seam.
- Keeps default `symphony` as a single-process local command.
- Lets Mosaic own terminal input/rendering while orchestration continues.
- Preserves readiness-blocked inspection behavior.

### Negative

- Requires careful thread-safe handoff between orchestration and the UI loop.
- Requires clean shutdown behavior so the terminal is restored when orchestration exits or the user quits.
- Introduces a new foreground event loop path in `main.ml`.

### Risks

- **Race conditions in state handoff**: Mitigate with a small synchronized state cell or queue and immutable Runtime State snapshots.
- **Terminal not restored after failure**: Mitigate by wrapping Mosaic startup/shutdown with cleanup and tests for signal/error paths where feasible.
- **Hidden lifecycle mutation**: Mitigate by keeping MVP key handlers limited to read/navigation/safe local aids.

## Implementation Notes

- Use `Orchestrator.make ~notify_state` as the only state update source for running orchestration.
- Keep `--web` semantics separate from the default Terminal Console.
- Keep `--once` as validate-and-exit output rather than interactive Mosaic.
