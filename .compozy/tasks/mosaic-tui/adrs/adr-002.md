# ADR-002: Make the read-first Terminal Console with safe local aids the MVP approach

## Status

Accepted

## Date

2026-05-12

## Context

The Mosaic Terminal Console PRD needs a product approach that turns the approved idea into a clear MVP. The idea and prior ADR established that the richer **Terminal Console** should use **Runtime State** as the visible source of truth, preserve existing orchestration semantics, and avoid becoming a parallel orchestrator.

Clarification during PRD creation narrowed the MVP:

- The richer Terminal Console should be the default mode when the user runs `symphony`.
- The home view should optimize for active work status at a glance.
- The primary MVP gate is understanding active orchestration state in under 15 seconds.
- The strongest MVP boundary is no task lifecycle mutation.
- V1 action aids should focus on reading, refreshing, navigating, filtering, and opening related surfaces.

## Decision

The PRD will use the **default read-first Terminal Console with safe local aids** approach.

The richer Terminal Console is the default user experience for normal `symphony` runs. It prioritizes active-run comprehension and provides safe local aids such as refresh, navigation, filtering, opening the Web Dashboard, and opening relevant local surfaces. MVP controls must not mutate task lifecycle state.

## Alternatives Considered

### Alternative 1: Default read-only observability console

- **Description**: Make the richer Terminal Console the default but exclude action aids beyond navigation.
- **Pros**: Lowest risk; simplest user promise; avoids ambiguity around controls.
- **Cons**: Weaker at reducing operational friction; less likely to reduce Web Dashboard fallback.
- **Why rejected**: The MVP should prove faster active-run operations, not only passive observability.

### Alternative 2: Limited task-action command center

- **Description**: Include safe local aids plus selected task lifecycle actions such as retry or pause/resume.
- **Pros**: Higher operational speed ceiling; closer to a full terminal command center.
- **Cons**: Contradicts the selected MVP boundary, increases trust and safety risk, and could become a second orchestration path.
- **Why rejected**: Too broad for MVP. Task lifecycle mutation belongs in a later phase after comprehension and safe-aid value are proven.

## Consequences

### Positive

- Aligns the MVP with the user's default-run expectation.
- Keeps the first release focused on active state comprehension.
- Provides practical terminal-local value without changing orchestration behavior.
- Preserves room for a broader command center after validation.

### Negative

- Some users may expect direct task actions from a command center and find MVP conservative.
- The Web Dashboard may remain necessary for deeper inspection or lifecycle actions.
- Safe local aids must be clearly labeled so users understand what the Terminal Console can and cannot change.

### Risks

- **Expectation mismatch**: Users may assume the default Terminal Console can mutate task state. Mitigation: explicit MVP messaging and clear disabled/deferred action labels.
- **Scope creep**: Safe local aids could expand into lifecycle actions. Mitigation: keep no task lifecycle mutation as a PRD non-goal.
- **Adoption risk**: Defaulting to the richer Terminal Console may disrupt users who prefer static output. Mitigation: keep the experience predictable and lightweight, with a clear fallback path if needed.

## Implementation Notes

This ADR is product-scope guidance only. Technical implementation details belong in the TechSpec.
