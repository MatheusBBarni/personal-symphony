# ADR-005: Use a pure Terminal Console view-model projection

## Status

Accepted

## Date

2026-05-12

## Context

**Runtime State** already contains the data needed by the MVP: running rows, retrying rows, issues, issue errors, status order, Readiness Gaps, usage totals, Ordered Queue progress, Compozy PRD Run progress, startup reconciliation, Task Branch integrations, context diagnostics, and global last error. The Web Dashboard has its own ReScript snapshot projection that turns Runtime State JSON into display-specific data.

The Mosaic Terminal Console needs a terminal-specific representation with sanitized text, prioritized active-run panels, keyboard focus state, filter/search state, and safe-aid availability. Rendering directly from `Runtime_state.t` would couple Mosaic views to orchestration data structures and scatter display rules across widgets.

## Decision

The MVP will introduce a pure Terminal Console view-model projection derived from `Runtime_state.t`. The projection will:

- sanitize untrusted display strings before rendering;
- classify active work, retrying work, attention conditions, readiness state, idle state, Ordered Queue entries, and Compozy PRD Run progress;
- precompute panel summaries and detail rows for Mosaic views;
- keep UI-only focus, filter, and selection state separate from Runtime State;
- avoid persistence and avoid changing Runtime State shape for MVP.

Mosaic views render the Terminal Console view model, not raw Runtime State.

## Alternatives Considered

### Alternative 1: Render directly from Runtime State

- **Description**: Have Mosaic views consume `Runtime_state.t` directly.
- **Pros**: Fewer types and less initial code.
- **Cons**: Couples UI widgets to orchestration state, scatters sanitization, and makes testing key display behavior harder.
- **Why rejected**: The MVP needs strong safety and comprehension guarantees; a projection layer keeps those rules explicit and testable.

### Alternative 2: Reuse the Web Dashboard JSON snapshot shape

- **Description**: Convert Runtime State to JSON and reuse frontend-style display shapes.
- **Pros**: Promotes parity with the Web Dashboard.
- **Cons**: Adds unnecessary JSON conversion inside the backend process and imports browser-specific presentation assumptions.
- **Why rejected**: The Terminal Console runs in-process and can use typed OCaml values directly.

### Alternative 3: Persist a Terminal Console state file

- **Description**: Store UI view state under Runtime Home so sessions resume panel/filter state.
- **Pros**: Could improve user continuity later.
- **Cons**: Adds storage semantics not required by MVP and expands Runtime Home state ownership.
- **Why rejected**: MVP should avoid new persistence and focus on active-run comprehension.

## Consequences

### Positive

- Keeps display rules pure and unit-testable.
- Centralizes terminal sanitization and state classification.
- Keeps Mosaic widgets thin and focused on layout/input.
- Avoids Runtime State schema changes for MVP.

### Negative

- Adds one translation layer between Runtime State and rendering.
- Requires keeping projection behavior aligned as Runtime State evolves.

### Risks

- **Projection drift**: Mitigate with tests using Runtime State fixtures for running, retrying, readiness-blocked, Ordered Queue, Compozy progress, and attention scenarios.
- **Over-modeling**: Mitigate by keeping only fields required by MVP panels and safe aids.
- **Sanitization gaps**: Mitigate by making all user/repository/agent-provided text pass through one projection boundary.

## Implementation Notes

- Keep the projection in backend code near Terminal Console modules, not in orchestration modules.
- Do not add persistence for filter/focus state in MVP.
- Treat issue titles, descriptions, branch names, task text, and agent messages as untrusted display input.
