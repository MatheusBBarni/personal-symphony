# ADR-001: Scope V1 Sandbox as an Optional Docker Execution Boundary

## Status

Accepted

## Date

2026-05-15

## Context

Personal Symphony currently launches the selected Agent Harness directly on the host inside an Agent Worktree in the Workspace Repository. For local developers running on personal laptops or workstations, that execution model creates trust friction because agent commands can affect the host machine directly.

The proposed feature adds sandboxing as an optional Runtime Settings capability in `.symphony/settings.json`. The user explicitly wants Docker-based isolation, wants the feature to remain optional because some operators run in VPS-style environments where local host protection matters less, and wants startup time to stay low by reusing sandbox state across feature runs.

The main forces in tension are:

- stronger isolation and smaller host blast radius for local use
- low activation energy and fast startup for repeated runs
- a Runtime Contract that stays explicit and understandable
- avoidance of hidden mutable container state that becomes support debt

## Decision

V1 will be scoped as one optional Docker sandbox provider that changes only Agent Harness execution, not orchestration ownership.

The Runtime Contract will expose a small explicit sandbox surface in Runtime Settings, with Docker as the only V1 provider. The sandbox will default to disabled. When enabled, Personal Symphony will launch the selected Agent Harness inside a Docker container while keeping orchestration and Task Branch coordination on the host.

Persistence will follow a constrained hybrid model:

- the Agent Worktree remains the authoritative writable repository state
- reusable cache state may persist in named Docker volumes
- container reuse is allowed only with explicit identity and reset rules
- mutable container root filesystem state is not treated as trusted durable state

The launch path will require explicit least-privilege controls, including bounded resources, minimal writable mounts, and allowlisted environment propagation.

## Alternatives Considered

### Alternative 1: No sandbox support

- **Description**: Keep direct host execution only.
- **Pros**: No new runtime complexity, no Docker dependency, fastest delivery.
- **Cons**: Does not address local trust concerns, keeps host blast radius unchanged, weakens appeal for cautious users.
- **Why rejected**: The feature exists to solve a real trust problem for local developers, and direct host execution does not solve it.

### Alternative 2: Fully persistent long-lived development container

- **Description**: Reuse one mutable container as a stable agent environment across runs.
- **Pros**: Fast warm starts, fewer repeated installs, familiar dev-container ergonomics.
- **Cons**: Hidden state drift, secret remanence, background-process accumulation, harder debugging, weaker Runtime Contract clarity.
- **Why rejected**: It introduces too much opaque state for V1 and makes the safety story weaker than the product promise implies.

### Alternative 3: Fresh ephemeral container on every run

- **Description**: Recreate the entire container environment from scratch for each agent run.
- **Pros**: Stronger determinism, less cross-run residue, simpler mental model.
- **Cons**: Slower startup, repeated dependency setup, worse local ergonomics, higher chance users disable the feature.
- **Why rejected**: It sacrifices too much usability for local workflows and undercuts the adoption goal.

## Consequences

### Positive

- Improves local trust by moving Agent Harness execution behind a container boundary.
- Preserves clear ownership: Personal Symphony still owns orchestration on the host.
- Keeps V1 narrow enough to ship and validate quickly.
- Retains performance wins through reusable cache state instead of rebuilding everything each run.

### Negative

- Introduces Docker as a new local prerequisite for users who enable sandboxing.
- Adds config parsing, bootstrap examples, and execution-path complexity.
- Creates some lifecycle burden around reuse, health checks, reset, and cleanup semantics.

### Risks

- A sandbox may look safer than it is if writable mounts, network access, or env propagation are too broad.
- Reused containers may accumulate hidden state unless reset and verification rules are explicit.
- Git worktree behavior may force wider mount access than the ideal least-privilege model.
- Resource limits that are too strict can break tasks; limits that are too loose weaken laptop safety.

## Implementation Notes

- Keep Docker as the only V1 provider.
- Separate generic sandbox intent from provider-specific Docker details.
- Make the current Agent Worktree the primary writable mount.
- Prefer named volumes for caches and tool state that are safe to reset.
- Treat container reuse as explicit Runtime-owned lifecycle, not accidental process reuse.
- Fail closed when required image, mount, or resource settings are invalid or incomplete.
