# ADR-004: Attach Sandboxing at the Launch Boundary With Reusable Repository-Scoped Containers

## Status

Accepted

## Date

2026-05-15

## Context

Personal Symphony already has a narrow execution seam: `Orchestrator.make` accepts a `launch` function, and `shell_launch` currently builds the host command that runs the selected **Agent Harness** in the **Agent Worktree**. The selected product behavior requires Docker-only sandboxing in V1, repository-level activation, reusable sandbox state, moderate runtime visibility, and a simple bootstrap command list that runs when the container is first created.

The user selected these technical directions:

- reuse a named container per **Workspace Repository**
- attach sandboxing by wrapping the existing `shell_launch` path rather than creating a new orchestration subsystem
- add moderate runtime visibility for sandbox enabled/provider/reuse outcome
- support a simple first-create bootstrap command list in V1

The key tension is whether to keep execution semantics close to the current launch contract or introduce a larger execution abstraction.

## Decision

V1 will attach sandboxing at the existing launch boundary by wrapping `shell_launch` with sandbox-aware command construction while preserving orchestrator ownership of worktree preparation, prompt files, session/log files, retries, and Task Branch semantics.

Sandbox reuse will be repository-scoped. Symphony will identify and reuse one named container per **Workspace Repository** when possible. That container remains the V1 warm-start unit, and a configured bootstrap command list runs only during first-create or explicit recreation. The **Agent Worktree** remains the authoritative repository state; sandbox reuse is an execution optimization, not a source of git truth.

Runtime visibility will be extended modestly: running-state payloads will include sandbox enabled/provider/reuse outcome, and readiness surfaces will report sandbox blocking when applicable.

## Alternatives Considered

### Alternative 1: Introduce a new launch subsystem or execution service

- **Description**: Create a new module hierarchy that fully abstracts host and sandbox execution behind a larger interface.
- **Pros**: Cleaner long-term abstraction, easier future provider expansion.
- **Cons**: More refactoring up front, larger test surface, greater risk of disturbing current orchestration semantics.
- **Why rejected**: It violates YAGNI for V1 and is unnecessary when the existing launch seam is already strong.

### Alternative 2: Recreate a fresh container each run and persist only cache volumes

- **Description**: Keep container identity ephemeral and only preserve volumes between runs.
- **Pros**: Cleaner trust boundary, reduced hidden container drift.
- **Cons**: Worse warm-start UX and weaker alignment with the selected repository-scoped reuse model.
- **Why rejected**: The chosen V1 favors faster repeat runs and named repository-scoped container reuse.

## Consequences

### Positive

- Minimizes disruption to current orchestration design.
- Preserves existing Agent Worktree, prompt archive, stdout/stderr, and retry semantics.
- Delivers the selected warm-start behavior with a focused implementation surface.

### Negative

- Keeps some Docker-specific behavior close to orchestrator launch code.
- Requires new runtime-state fields and dashboard projection work for sandbox visibility.
- Repository-scoped persistent containers introduce drift and lifecycle management concerns that V1 must constrain carefully.

### Risks

- Container reuse may hide stale state if config fingerprinting and recreation rules are weak.
- Bootstrap commands may become an unbounded mutation surface if they are not tightly scoped to first-create semantics.
- If sandbox command construction diverges too far from the existing host contract, log/session/retry behavior may regress.

## Implementation Notes

- Preserve the existing `launch` seam in `Orchestrator.make`.
- Keep prompt file creation and host-visible stdout/stderr files under the **Agent Worktree** contract.
- Add a repository-scoped container identity derived from the **Workspace Repository** and sandbox settings.
- Run configured bootstrap commands only on first container creation or explicit recreation.
- Extend runtime state and dashboard projection with sandbox summary fields rather than a full lifecycle history in V1.
