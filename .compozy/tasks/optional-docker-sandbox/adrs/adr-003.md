# ADR-003: Model Sandbox as a Repository-Owned Runtime Settings Block With Startup Readiness Gating

## Status

Accepted

## Date

2026-05-15

## Context

The Optional Docker Sandbox feature introduces a net-new execution concern to Personal Symphony. The current architecture already has clear repository-owned Runtime Settings parsing in `Config`, startup/runtime readiness aggregation in `Runtime_readiness`, readiness-based orchestration blocking in `Runtime_policy`, and a stable glossary that distinguishes **Logical Agent** from **Agent Harness**.

The selected product behavior requires sandboxing to be optional, repository-owned, and strictly blocking when enabled but unavailable. The user chose a minimal V1 Runtime Settings shape with `sandbox.enabled` as the main activation toggle. They also chose static readiness blocking as the primary enforcement path, but only when sandboxing is enabled.

The main design tension is whether to model sandboxing as a new Harness concept, a launch-only concern, or a top-level repository-owned runtime policy.

## Decision

V1 will model sandboxing as a top-level `sandbox` block in the **Runtime Settings**, activated by `sandbox.enabled`.

Static sandbox validation will be implemented in `Config.readiness_gaps` and surfaced through `Runtime_readiness.state`, so a sandbox-enabled **Workspace Repository** is blocked before orchestration starts when required settings or prerequisites are invalid. This preserves the existing readiness architecture and ensures terminal and web surfaces show the same blocking state.

The V1 settings shape will remain minimal and repository-owned. It will use a direct top-level block rather than a provider-abstraction hierarchy. Docker remains the only supported sandbox type in V1, but the field layout will stay compatible with a future expansion if needed.

## Alternatives Considered

### Alternative 1: Model sandboxing as a new Agent Harness kind

- **Description**: Treat Docker sandboxing as another Harness kind alongside codex, claude, and pi.
- **Pros**: Reuses existing Harness selection language and some readiness patterns.
- **Cons**: Conflicts with the glossary and current architecture because sandboxing is a repository-level execution boundary, not a logical-agent backend. It also blurs the distinction between transport/execution isolation and agent-provider selection.
- **Why rejected**: It overloads the meaning of **Agent Harness** and creates a poor long-term fit with existing domain language.

### Alternative 2: Validate sandbox only at launch time

- **Description**: Keep sandbox configuration mostly unchecked until a task is about to run.
- **Pros**: Smaller initial parser and readiness changes.
- **Cons**: Produces inconsistent UX, weakens strict blocking semantics, and risks divergence between startup readiness views and dispatch-time failures.
- **Why rejected**: The selected product behavior explicitly requires strict readiness when sandboxing is enabled.

## Consequences

### Positive

- Keeps sandbox activation repository-owned and visible in the **Runtime Contract**.
- Reuses existing readiness plumbing for CLI, Terminal Console, and Web Dashboard consistency.
- Avoids redefining or overloading **Agent Harness** semantics.

### Negative

- Adds a new top-level Runtime Settings section to parse, validate, document, and test.
- Requires new readiness rules and remediation text for Docker-specific prerequisites.
- Leaves future provider expansion to a later refactor if V2 needs a more abstract model.

### Risks

- A too-minimal V1 shape may need reshaping if later providers are introduced.
- Static validation can only cover configuration and detectable prerequisites, not every runtime health problem.
- Poor remediation text would make strict blocking feel punitive instead of protective.

## Implementation Notes

- Use `sandbox.enabled` as the repository toggle.
- Add sandbox parsing to `Config.t` and bootstrap examples to `runtime_home.ml`.
- Gate sandbox readiness only when `sandbox.enabled = true`.
- Surface sandbox readiness through existing `Runtime_state.readiness_gaps`.
