# ADR-002: Use Repository-Level Opt-In With Strict Sandbox Readiness

## Status

Accepted

## Date

2026-05-15

## Context

The Optional Docker Sandbox feature needs a product-level activation model for a Workspace Repository. The main product goals are to increase user willingness to run autonomous agents locally, keep activation low-friction for existing Symphony users, and preserve a clear trust promise once sandboxing is enabled.

The user selected an MVP where sandboxing should apply across all agent stages in a repository once enabled. The user also specified that sandbox unavailability or unhealthy sandbox state should block agent execution rather than falling back to direct host execution.

The main alternatives were stage-scoped rollout and harness-scoped rollout. Those alternatives reduce initial breadth but introduce a more fragmented user mental model and a weaker safety promise.

## Decision

V1 will use repository-level opt-in with strict readiness.

When a Workspace Repository enables sandboxing in Runtime Settings, Personal Symphony will treat sandboxed execution as the required execution mode for that repository's agent runs. The feature will apply across all agent stages in scope for the repository rather than being framed as a partial or per-stage opt-in capability.

If sandboxing is unavailable, misconfigured, or unhealthy, Personal Symphony will block agent execution and present clear remediation guidance instead of silently or automatically falling back to host execution.

The product experience will optimize for low setup friction through opinionated defaults, but the trust contract will remain strong: once sandboxing is turned on, users should be able to assume their repository is operating under that execution boundary.

## Alternatives Considered

### Alternative 1: Stage-Scoped Rollout

- **Description**: Allow sandboxing only for selected agent stages, such as engineer or reviewer, while other stages continue to run on the host.
- **Pros**: Smaller rollout surface, simpler phased testing, easier early troubleshooting.
- **Cons**: More confusing product story, inconsistent repository behavior, weaker user confidence in what "sandbox enabled" means.
- **Why rejected**: It weakens the core trust promise and adds mental overhead at the exact point the feature is supposed to reduce hesitation.

### Alternative 2: Harness-Scoped Availability

- **Description**: Restrict sandboxing to specific harnesses or logical agents in MVP.
- **Pros**: Smallest product slice, lower immediate support burden, easier initial compatibility targeting.
- **Cons**: Feels partial, exposes internal product structure to users, limits business impact on local-agent confidence.
- **Why rejected**: It optimizes for implementation caution at the expense of product clarity and user trust.

## Consequences

### Positive

- Creates a strong and understandable user promise at the repository level.
- Supports the primary business outcome of increased willingness to run autonomous agents locally.
- Keeps activation simple for existing Symphony users: enable once per repository and use it consistently.

### Negative

- Raises the product bar for readiness checks and error messaging.
- Reduces flexibility for mixed sandbox and host execution inside the same repository in V1.
- May block work more often in early versions if sandbox readiness is fragile.

### Risks

- Users may experience friction if Docker or image prerequisites are not easy to satisfy.
- Blocking behavior may feel punitive if readiness diagnostics are vague or hard to resolve.
- Some repositories may have stage-specific needs that are deferred by the repository-wide activation model.

## Implementation Notes

- Keep activation repository-owned through Runtime Settings in the Runtime Contract.
- Surface readiness failures clearly before or at dispatch time.
- Treat fallback-to-host as out of scope for sandbox-enabled repositories in V1.
- Preserve room for future stage-scoped or harness-scoped variants only if later research justifies them.
