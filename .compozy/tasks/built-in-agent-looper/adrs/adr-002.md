# ADR-002: Evidence-First Goal Loop Approach

## Status

Accepted

## Date

2026-05-20

## Context

The PRD clarification round established a stricter product posture for the built-in agent looper. The V1 outcome should optimize for maintainer trust and visibility, while still making **Goal met** the primary successful stop outcome. The primary operator persona is a maintainer supervising multiple **Stage Agents** in a **Workspace Repository**. The user selected deterministic checks as required evidence for a V1 **Goal met** outcome.

This creates a product tension: a loop that feels autonomous must still avoid false completion. If the loop can mark a goal complete based only on agent or evaluator confidence, maintainers may trust an automation state that is not backed by verifiable evidence.

## Decision

The PRD will use an **Evidence-First Goal Loop** approach.

V1 should optimize for trust and visibility. A loop may stop as **Goal met** only when deterministic evidence supports the claim. If the work is ambiguous, blocked, or missing required evidence, the loop must stop in a clear attention outcome rather than claim success. Budget exhaustion remains a predictable stop outcome, but it is secondary to making successful completion evidence-backed.

The PRD will describe user-facing outcomes and business value only. It will not prescribe implementation details for how deterministic evidence is collected or evaluated; that belongs in the TechSpec.

## Alternatives Considered

### Alternative 1: Completion-First Loop

- **Description**: Optimize V1 for reaching a completed goal with minimal operator interruption.
- **Pros**: Strong automation story; directly targets fewer manual nudges; may feel closer to provider goal-loop experiences.
- **Cons**: Higher false-completion risk; weaker maintainer trust if completion evidence is inconsistent; makes ambiguous goals too tempting to mark complete.
- **Why rejected**: The user chose trust and visibility as the top V1 outcome and deterministic evidence as required for **Goal met**.

### Alternative 2: Platform Foundation Loop

- **Description**: Optimize V1 around reusable loop recipes and multi-harness growth.
- **Pros**: Strong long-term product shape; aligns with the configurable-platform ambition from the idea phase.
- **Cons**: Too broad for the first PRD; could defer the evidence and stop-outcome behavior that makes maintainers trust loops.
- **Why rejected**: The first PRD needs to validate maintainer trust in evidence-backed goal completion before expanding recipes.

## Consequences

### Positive

- Maintainers get a reliable distinction between **Goal met**, **Needs attention**, and **Budget exhausted**.
- Successful loop completion is backed by visible evidence instead of agent self-report alone.
- The PRD stays focused on the highest-trust V1 while preserving future platform growth.

### Negative

- Some qualitative or ambiguous work will stop as attention rather than success in V1.
- The automation may feel less magical than a completion-first loop because it refuses unverifiable success.
- Success metrics must track evidence quality, not only completion rate.

### Risks

- **Overly strict evidence requirements**: Mitigate by allowing the PRD to identify qualitative work as attention-worthy until later product decisions define acceptable qualitative evidence.
- **Operator fatigue from attention states**: Mitigate by requiring attention outcomes to include concise missing-evidence or blocked-reason guidance.
- **Deferred platform ambition**: Mitigate by preserving platform-shaped state language from ADR-001 and treating recipes as a later phase.

## Implementation Notes

- Keep the PRD centered on what operators see and need: goal state, evidence, stop reason, and next action.
- Avoid implementation choices for evidence collection, command execution, schemas, or storage.
- The TechSpec should translate deterministic evidence requirements into concrete runtime behavior.
