# ADR-003: Stage-Scoped Goal Loop Runtime State

## Status

Accepted

## Date

2026-05-20

## Context

The PRD requires Goal Loop status to be visible across Runtime State, Terminal Console, and Web Dashboard. Existing **Stage Goal Handoff** is configured per **Stage Agent**, while **Harness Loop** belongs to the selected **Agent Harness** and only controls launch-time loop command handoff. The Goal Loop must not overload those existing meanings.

Goal Loop status also needs to remain visible after a task stops as **Goal met**, **Needs attention**, or **Budget exhausted**. Running, retrying, and issue-error rows alone are not sufficient because successful completion currently removes active rows from Runtime State.

## Decision

Goal Loop configuration will be scoped to **Stage Agent** settings in V1.

Canonical Goal Loop state will live as top-level Runtime State data and will be persisted under `.symphony/state/goal-loops/*.json`. Runtime State rows may include summary projections, but they are not the source of truth.

The persisted state will be keyed by issue and loop run identity and include the active goal, selected stage agent, selected harness identity, attempt count, configured budget, latest evidence summary, stop outcome, stop reason, next action, updated timestamp, and optional diagnostics path.

## Alternatives Considered

### Alternative 1: Embed Goal Loop only on active rows

- **Description**: Store loop data only on running, retrying, and attention rows.
- **Pros**: Small JSON shape; close to existing Goal Usage and Context Status projections.
- **Cons**: Successful **Goal met** outcomes disappear when active rows are cleared; no durable run record; difficult to resume or inspect after stop.
- **Why rejected**: The PRD requires trustworthy stop outcomes and visibility beyond active execution.

### Alternative 2: Harness-scoped Goal Loop configuration

- **Description**: Put Goal Loop config on Agent Harness definitions.
- **Pros**: Aligns loop behavior with execution backend capabilities.
- **Cons**: Conflicts with existing Harness Loop meaning; makes product behavior follow provider selection instead of stage intent.
- **Why rejected**: V1 is a stage behavior for maintainers supervising workflow stages, not a provider capability toggle.

### Alternative 3: Reuse Goal Usage as state

- **Description**: Treat parsed provider Goal Usage as the Goal Loop state source.
- **Pros**: Minimal implementation surface; uses existing fields.
- **Cons**: Provider output is optional, non-fatal, and not deterministic completion evidence.
- **Why rejected**: Goal Usage cannot anchor evidence-first completion.

## Consequences

### Positive

- Goal Loop state remains visible after success, attention, or budget exhaustion.
- Stage configuration matches the operator's workflow model.
- Future recipes can build on the persisted state without changing Runtime State again.

### Negative

- Adds a new Runtime State collection and persistence path.
- Requires UI and console projection work beyond existing per-row fields.
- Needs migration-safe defaults so old Workspace Repositories remain unchanged.

### Risks

- **State drift**: Mitigate by treating persisted Goal Loop files as canonical and deriving Runtime State projections from them.
- **Terminology overlap**: Mitigate with `CONTEXT.md` updates that distinguish Goal Loop, Harness Loop, Stage Goal Handoff, and Goal Usage.
- **Sensitive evidence leakage**: Mitigate by storing bounded secret-free summaries in Runtime State and private diagnostics under Runtime Home state.

## Implementation Notes

- Add a pure Goal Loop domain module for state and transition types.
- Add stage-scoped Runtime Settings fields without changing existing Bootstrap defaults unless explicitly accepted during implementation.
- Keep Live Dashboard delivery as the existing Runtime State snapshot stream.
