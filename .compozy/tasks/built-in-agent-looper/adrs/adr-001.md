# ADR-001: Goal Loop Runtime Scope

## Status

Accepted

## Date

2026-05-20

## Context

Personal Symphony already has **Harness Loop**, **Stage Goal Handoff**, **Stage Goal Context**, and **Goal Usage**. Those concepts currently handle launch-time loop handoff, not a Runtime-owned decision loop that keeps an agent working toward a goal until the goal is satisfied, blocked, or exhausted.

The idea asks for a built-in agent looper for Codex operators, similar to Goal and Ralph-style loops. The user selected a configurable loop platform as the V1 ambition, closest to Goal from the operator perspective, with the primary success signal that the loop reliably reaches an explicit goal without extra user nudges.

Market research shows that coding-agent products increasingly emphasize delegation, monitoring, review handoff, explicit stop conditions, progress evidence, cost visibility, and isolated execution. The risk is that a broad configurable platform could blur Symphony's existing lifecycle boundaries around retry, completion, Stage Commit, Stage Push, Task Branch Integration, and pull request behavior.

## Decision

V1 will define a Runtime-owned **Goal Loop** capability as a narrow user-facing vertical slice with platform-shaped internal contracts.

The V1 user experience will focus on one clear path: an operator provides an explicit goal, Symphony launches the selected Agent Harness through a bounded loop, the loop records progress and usage, and the loop stops with a visible reason when the goal is met, blocked, or budget-exhausted.

The internal scope must model the loop as durable Runtime-owned state rather than a prompt-only wrapper. The minimum V1 state contract includes active goal, selected harness, attempt count, stop budget, stop reason, latest progress evidence, next action, usage or cost summary when available, and visibility through Runtime State. Terminal Console and Web Dashboard visibility should expose the same authoritative state rather than inventing separate interpretations.

The Goal Loop must not own delivery authority in V1. It must not silently change retry, completion, status transition, Stage Commit, Stage Push, Task Branch Integration, auto-merge, or pull request behavior. Model judgment may summarize or interpret evidence, but deterministic evidence and explicit budgets must anchor stop and completion decisions whenever the goal claims a verifiable condition.

## Alternatives Considered

### Alternative 1: Prompt-only provider loop wrapper

- **Description**: Reuse Stage Goal Handoff by prepending a provider command such as `/goal` and rely on the provider to continue or stop.
- **Pros**: Small implementation surface; preserves existing Symphony lifecycle semantics; faster to prototype.
- **Cons**: Keeps the core loop outside Runtime State; weak cost visibility; weak cross-harness portability; does not create a reusable platform for future loop recipes.
- **Why rejected**: It does not satisfy the user's platform ambition or the success signal of reliable goal completion without repeated nudges under Symphony-owned observability.

### Alternative 2: Full autonomous loop platform

- **Description**: Let the loop own retries, completion review, commits, pushes, merges, and PR handoff.
- **Pros**: Potentially high automation leverage; closer to a fully delegated software delivery system.
- **Cons**: Changes core lifecycle semantics; expands attack surface; increases false-completion risk; conflicts with existing ADRs that keep Stage Goal Handoff non-semantic.
- **Why rejected**: Too broad for V1 and too risky without separate ADRs for completion review and delivery authority.

### Alternative 3: Runtime-owned narrow Goal Loop

- **Description**: Build a narrow Goal-centered vertical slice backed by explicit Runtime-owned loop state, budgets, evidence, and stop reasons.
- **Pros**: Validates operator value quickly while preserving architecture boundaries; creates reusable contracts for later recipes; keeps completion and delivery authority separate.
- **Cons**: Requires new domain language, Runtime State fields, and UI/status work before the loop feels complete.
- **Why accepted**: It balances the user's configurable-platform direction with the council's recommendation to prove the narrow goal loop before expanding authority.

## Consequences

### Positive

- Operators get a visible, bounded loop that can continue toward a goal without manual nudges.
- Symphony owns the state needed to explain why a loop continued, stopped, or moved to attention.
- Future loop recipes can build on the same Goal Loop contract instead of adding provider-specific behavior.

### Negative

- V1 cannot be only a configuration tweak; it needs Runtime State and status-surface work to be credible.
- Completion semantics remain constrained, so some ambiguous goals will stop in attention rather than claim success.
- Dashboard and Terminal Console visibility may become required for trust even if the first loop engine is backend-heavy.

### Risks

- **False completion**: Mitigate by requiring deterministic evidence for verifiable goals and recording the evidence used.
- **Unbounded spend**: Mitigate with explicit time, turn, and usage budgets.
- **Scope creep into delivery**: Mitigate by keeping commits, pushes, merges, PRs, and status transitions under existing lifecycle rules unless a later ADR changes them.
- **Provider lock-in**: Mitigate by modeling Goal Loop state at the Runtime level and treating provider loop commands as harness adapters.

## Implementation Notes

- Update `CONTEXT.md` when accepting final domain language for Goal Loop concepts.
- Add a product ADR under `docs/adr/` before implementation because Runtime-owned loop semantics change more than prompt composition.
- Preserve existing **Stage Goal Handoff** semantics unless the PRD explicitly proposes and approves a migration path.
- Treat independent completion review as related but out of scope for this idea unless a separate ADR accepts it.
