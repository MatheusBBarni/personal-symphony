# ADR-002: Adopt Unified Terminal Console Inspect Mode

## Status

Accepted

## Date

2026-05-23

## Context

The original scope recommendation was to hide absent Queue and add progressive selected-task detail to Tasks. After the opportunity scan, the user selected the more ambitious direction: a unified Terminal Console inspect mode across the read-first tabs.

The Terminal Console currently has tab-specific row selection and Queue-specific expansion. Tasks already has rich selected-task detail available through a separate Task Detail panel, but that detail is not presented as a consistent active-tab inspection pattern. Queue, Tasks, Readiness, and Needs attention all render Runtime State rows that an operator may need to inspect while scanning a live run.

This decision must preserve Terminal Console product boundaries: the surface remains read-first, derives from Runtime State, does not mutate task lifecycle state, and does not infer Ordered Queue semantics when no Ordered Queue exists.

## Decision

V1 will adopt a unified Terminal Console inspect mode for selectable read-first tabs. Queue, Tasks, Readiness, and Needs attention will share a consistent inspection interaction for the selected row. The inspected content may differ by tab, but the operator model stays the same: move selection, open or close detail, and read the relevant Runtime State context without leaving the Terminal Console flow.

Queue visibility remains dynamic. The Queue tab is hidden only when Runtime State proves no Ordered Queue exists. A present Ordered Queue keeps explicit empty, filtered-empty, completed, skipped, failed, and attention states.

Tasks becomes the primary scan-and-inspect surface when Queue is absent, but it is no longer the only beneficiary of richer detail. Readiness and Needs attention also get focused inspection affordances so operators can inspect remediation, errors, task metadata, Context Status, Goal Loop, and related evidence through one consistent interaction model.

## Alternatives Considered

### Alternative 1: Keep the Narrow Queue and Tasks Scope

- **Description**: Hide absent Queue and add selected-task detail only to Tasks.
- **Pros**: Lower implementation risk; smaller verification surface.
- **Cons**: Leaves Queue expansion as a special case and misses the chance to make Terminal Console row inspection coherent.
- **Why rejected**: The user selected the more ambitious inspect-mode direction after reviewing the opportunity scan.

### Alternative 2: Add Detail to Every Tab Independently

- **Description**: Add per-tab detail behavior with separate state and key handling for each tab.
- **Pros**: Allows every panel to move independently.
- **Cons**: Repeats interaction logic and makes future Terminal Console behavior harder to reason about.
- **Why rejected**: V1 should improve the operator model, not create several unrelated detail mechanisms.

### Alternative 3: Move Detail Work to the Web Dashboard

- **Description**: Keep Terminal Console simple and implement richer row detail in the browser surface.
- **Pros**: Browser UI has more space for complex detail.
- **Cons**: Does not solve the local terminal operator flow; pushes users out of the default surface.
- **Why rejected**: The user asked for TUI improvements, and Terminal Console is the default operating surface.

## Consequences

### Positive

- Operators learn one inspection interaction across Terminal Console rows.
- Queue expansion stops being a one-off behavior.
- Tasks, Queue, Readiness, and Needs attention become more useful without adding lifecycle commands.
- The design compounds as Runtime State gains richer diagnostics.

### Negative

- V1 has a larger verification surface than the original narrow scope.
- Dynamic tabs plus shared inspection state require careful focus and fallback behavior.
- Detail copy must stay concise enough for terminal constraints.

### Risks

- The feature could drift into a general control plane. Mitigation: keep inspect mode read-only and exclude retry, pause, merge, push, status mutation, and Runtime Contract edits.
- Detail panels could make the TUI noisy. Mitigation: preserve compact default rows and show richer content only after explicit inspection.
- Queue absence could be confused with an empty queue. Mitigation: hide Queue only for `ordered_queue = None` and keep explicit empty states for present queues.

## Implementation Notes

- Preserve explicit Ordered Queue presence in Terminal Console projection.
- Derive visible tabs from Runtime State and clamp the active tab when Queue disappears.
- Replace Queue-only expansion state with an active-tab inspection state that can represent Queue, Tasks, Readiness, and Needs attention selections.
- Reuse existing Task Detail projection for task-bearing tabs.
- Keep Readiness inspection focused on requirement and remediation; keep attention inspection focused on task error, status, and related Runtime State context.
- Update help and footer copy so the inspect command describes the selected tab rather than only Queue.
