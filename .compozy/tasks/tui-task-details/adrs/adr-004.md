# ADR-004: Use Projection-Backed Inline Inspect State

## Status

Accepted

## Date

2026-05-23

## Context

The Terminal Console currently receives a sanitized `Terminal_console_model.t` projection derived from `Runtime_state.t`. `Runtime_state.ordered_queue` preserves the difference between no Ordered Queue and an existing queue, but `Terminal_console_model.t.queue` currently collapses that distinction into a plain row list.

V1 needs dynamic Queue tab visibility and status-first inspect behavior across non-Logs selectable tabs. The implementation must keep Terminal Console behavior read-only and avoid changing orchestration or Runtime State semantics.

## Decision

Preserve Queue presence in `Terminal_console_model.t` and expose inspect-ready row information from the projection layer. `terminal_console_tui.re` will derive visible tabs from that projection and render inline status-first inspect details beneath the selected row in the active panel.

The inspect model will be shared through `terminal_console_model.re` where it helps avoid duplicating projection logic, but the interactive state and rendering behavior remain in `terminal_console_tui.re`.

## Alternatives Considered

### Alternative 1: Infer Queue Presence in the TUI

- **Description**: Hide Queue when the projected queue row list is empty.
- **Pros**: Smaller code change.
- **Cons**: Cannot distinguish no Ordered Queue from an existing empty or filtered queue.
- **Why rejected**: It violates the PRD requirement to preserve Ordered Queue absence separately from present empty state.

### Alternative 2: Add Inspect Data to Runtime State

- **Description**: Extend `Runtime_state.t` with reusable inspect/detail payloads.
- **Pros**: Could support Web Dashboard parity later.
- **Cons**: Expands runtime semantics for a Terminal Console-only V1 and risks coupling UI detail order to Runtime State.
- **Why rejected**: The PRD explicitly excludes Web Dashboard work and requires a bounded Terminal Console implementation.

### Alternative 3: Add a New Backend Inspect Module

- **Description**: Create a new backend module for Terminal Console inspect behavior.
- **Pros**: Clear file-level separation.
- **Cons**: Adds a new abstraction before the behavior needs one.
- **Why rejected**: Existing projection and TUI modules already own the relevant boundaries.

## Consequences

### Positive

- Queue visibility is based on semantic presence, not row count.
- Status-first inspect content can be shared across Queue, Tasks, and Needs attention without duplicating detail parsing.
- Runtime State and orchestrator behavior stay unchanged.

### Negative

- `Terminal_console_model.t` gains additional display-state fields.
- Existing tests that assume static tab text require updates.

### Risks

- Projection helpers could become a broad UI abstraction. Mitigation: keep them scoped to read-only row detail and avoid adding lifecycle behavior.
- Inline detail could make panels noisy. Mitigation: render details only after explicit Enter toggling.

## Implementation Notes

- Add a Queue presence field or equivalent optional queue representation to `Terminal_console_model.t`.
- Add inspect detail helpers for task-like rows and readiness rows in `terminal_console_model.re`.
- Keep selected row indices and open/closed inspect interaction state in `terminal_console_tui.re`.
- Render inline details under the selected row only when inspect mode is active for the current tab.
