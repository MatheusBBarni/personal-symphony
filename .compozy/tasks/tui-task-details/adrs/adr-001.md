# ADR-001: Preserve Queue Absence and Add Progressive Task Detail

## Status

Superseded by ADR-002

## Date

2026-05-23

## Context

The Terminal Console currently presents a static tab order that includes Queue even when the Runtime State snapshot has no Ordered Queue. That creates a dead first surface for solo operators who are scanning active work without running an Ordered Queue.

The Tasks tab already shows active, retrying, and attention rows, and the Terminal Console already has a Task Detail panel capable of rendering issue metadata, stage state, harness identity, Goal Loop, Goal Usage, Context Status, and current errors. However, Space only expands Queue rows today, so richer selected-task context is not available through the same scan-and-inspect interaction in Tasks.

The Terminal Console must remain a read-first Runtime State surface. This decision must not introduce task lifecycle mutation, queue inference from tracker order, or Runtime Contract changes.

## Decision

V1 will hide the Queue tab only when Runtime State proves there is no Ordered Queue. A present Ordered Queue with zero rows, filtered rows, completed rows, skipped rows, or attention states remains a Queue surface with explicit empty or state-specific copy.

V1 will make the Tasks tab a complete common-flow scan-and-inspect surface. The default Tasks view remains compact, while explicit selected-task detail toggling reveals the existing task-detail metadata for the selected task. The detail behavior must stay read-only and must reuse Runtime State fields instead of inventing new task semantics.

## Alternatives Considered

### Alternative 1: Keep Queue Always Visible

- **Description**: Preserve the current static Queue tab and empty-state panel for all Runtime State snapshots.
- **Pros**: Smallest possible UI change; keeps tab order stable.
- **Cons**: Shows an irrelevant surface when no Ordered Queue exists; defaults solo operators to a dead panel.
- **Why rejected**: It optimizes implementation stability over operator scan clarity and misrepresents queue absence as an empty queue experience.

### Alternative 2: Turn Tasks Into a Queue Clone

- **Description**: Replicate Queue row expansion behavior and metadata directly inside Tasks without a broader selected-row detail boundary.
- **Pros**: Fast to describe; creates immediate parity for selected rows.
- **Cons**: Duplicates Queue semantics; risks making Tasks dense and ambiguous; increases future divergence between panels.
- **Why rejected**: Tasks should own the common scan-and-inspect flow, not queue-specific lifecycle or duplicate queue behavior.

### Alternative 3: Build a Full Tab Interaction Framework

- **Description**: Generalize tab visibility, selection, row expansion, and detail rendering across all Terminal Console tabs.
- **Pros**: Strong long-term architecture; reduces future special cases.
- **Cons**: Larger V1 blast radius; expands a usability improvement into a Terminal Console redesign.
- **Why rejected**: V1 needs a bounded improvement. A small active-tab detail boundary is enough for Queue and Tasks without redesigning every tab.

## Consequences

### Positive

- Solo operators start from meaningful Terminal Console surfaces when they are not using an Ordered Queue.
- Tasks becomes the primary read-only place to inspect active, retrying, attention, Goal Loop, Goal Usage, and Context Status details.
- Queue absence, Queue presence, and filtered-empty states remain semantically distinct.

### Negative

- Dynamic tab visibility changes the static tab-order expectation and requires careful default-tab fallback.
- Tasks gains more interaction weight, so copy and detail toggling must avoid ambient clutter.

### Risks

- Runtime State projection may currently lose the distinction between no Ordered Queue and an empty Ordered Queue. Mitigation: preserve queue presence explicitly before deriving visible tabs.
- Hiding Queue could hide a degraded or partial state if absence is not semantically proven. Mitigation: hide only on `ordered_queue = None`; keep explicit Queue empty states whenever the queue exists.
- Detail toggling could imply lifecycle action. Mitigation: keep all detail behavior read-only and avoid command verbs that suggest mutation.

## Implementation Notes

- Preserve an explicit queue-presence signal in the Terminal Console projection.
- Derive visible tabs from Runtime State rather than a fully static tab list.
- When Queue is hidden and the current active tab would be Queue, move focus to Tasks.
- Extend the Space/detail interaction so Tasks can reveal selected-task details without making Queue-specific behavior the only expansion path.
- Keep Tasks detail content sourced from the existing Task Detail projection.
