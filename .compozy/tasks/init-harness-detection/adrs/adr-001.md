# ADR-001: Seed Missing Runtime Settings From Local Harness Detection

## Status

Accepted

## Date

2026-05-22

## Context

`symphony init` currently performs Bootstrap by creating missing Runtime Home files and writing a static `.symphony/settings.json` only when the file does not already exist. The static Runtime Settings define Codex, Claude, Cursor, Cursor direct-write, and PI Agent Harnesses, while Logical Agents route planner work to Codex, engineer work to Claude, and reviewer work to PI.

That default is structurally valid, but it can create first-run setup friction for an individual developer whose machine has only one supported Agent Harness installed and authenticated. The user must understand Harness definitions, Logical Agents, Stage Agent routing, and readiness gaps before the first useful run.

The existing Symphony domain model already separates Agent Harness definitions from Logical Agents and Stage Agent routing. Runtime readiness validates selected Agent Harnesses through Logical Agent routes. The new idea should reduce first-run friction without collapsing those boundaries or treating local machine detection as permanent runtime truth.

## Decision

V1 will seed missing Runtime Settings during Bootstrap from a narrow, local, allowlisted Agent Harness detection pass. When `.symphony/settings.json` does not exist, Bootstrap may detect supported installed and authenticated Harnesses, select one reasonable default, route the default Logical Agents to that selected Harness, and explain the selected Harness in the Bootstrap output.

Detection is a provisional onboarding signal, not a runtime authority. Runtime readiness remains responsible for validating the selected Agent Harness before dispatch. Bootstrap must preserve Idempotent Bootstrap behavior, must not overwrite existing Runtime Contract files, must not write secrets or credential-derived values, must keep Stage Agents routing to Logical Agents, and must keep Agent Harness definitions separate from Logical Agent definitions.

If no supported usable Harness is found, Bootstrap should still create the Runtime Contract and report concrete install or authentication guidance for supported Harnesses instead of silently producing a misleading success state.

## Alternatives Considered

### Alternative 1: Keep Static Defaults

- **Description**: Leave Bootstrap as a static `settings.json` template with the current mixed-Harness defaults.
- **Pros**: No new detection code, fully deterministic, no new local probing risk.
- **Cons**: New users can receive selected Harness routes for tools they do not have installed or authenticated.
- **Why rejected**: It preserves the setup friction the idea is meant to solve.

### Alternative 2: Full Interactive Harness Setup Wizard

- **Description**: Add a broad setup flow that prompts for roles, Harness preferences, install steps, and authentication choices.
- **Pros**: More explicit user control and richer team policy options.
- **Cons**: Larger scope, higher maintenance cost, more secret-adjacent UX risk, and more decisions before first run.
- **Why rejected**: V1 should be a low-friction Bootstrap improvement, not a full configuration product.

### Alternative 3: Dynamic Runtime Harness Selection

- **Description**: Defer Harness choice until dispatch time and dynamically choose among installed tools per task or stage.
- **Pros**: Avoids stale init-time choices and could optimize by task type later.
- **Cons**: Blurs Runtime Settings, readiness, and routing semantics; makes dispatch harder to debug.
- **Why rejected**: It changes runtime semantics instead of improving the initial Runtime Contract.

## Consequences

### Positive

- New Workspace Repositories are more likely to start with Runtime Settings that match the developer's machine.
- Existing selected-Harness readiness semantics remain the dispatch authority.
- The design preserves the current `harnesses` and `agents` separation.
- No existing Runtime Contract files are rewritten during repeated Bootstrap.

### Negative

- Bootstrap now depends on local environment observation, so tests need deterministic probe injection.
- A one-time detection result can become stale when the developer installs, removes, or reauthenticates agent CLIs later.
- The Bootstrap output must explain enough provenance for users to understand the generated choice.

### Risks

- **PATH spoofing or shim ambiguity**: Mitigate with allowlisted detection, conservative provenance, and readiness validation before dispatch.
- **Secret leakage**: Mitigate by never writing token values, credential contents, or authentication artifacts into Runtime Settings or logs.
- **Boundary drift**: Mitigate by keeping Stage Agents routed only by Logical Agent name and avoiding stage-level Harness shortcuts.

## Implementation Notes

- Generate settings as structured JSON rather than hand-editing template strings.
- Keep unused supported Harness definitions if doing so avoids readiness gaps and preserves editability, but only selected Logical Agent routes should drive readiness.
- Add focused backend tests for Codex-only, Claude-only, Cursor-only, PI-only, multi-Harness, no-Harness, and existing-settings idempotency scenarios.
- Update README setup guidance and product ADRs only when implementation proceeds beyond idea creation.
