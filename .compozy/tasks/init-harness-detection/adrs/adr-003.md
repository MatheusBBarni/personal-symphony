# ADR-003: Isolate Bootstrap Detection and Settings Generation in Reason Helpers

## Status

Accepted

## Date

2026-05-22

## Context

The TechSpec must translate transparent Bootstrap Harness guidance into backend changes without weakening Runtime Contract idempotency. Current Bootstrap behavior is owned by `Runtime_home.bootstrap`, which writes a static `settings_json` string only when `.symphony/settings.json` is missing. Current Harness parsing and selected-Harness readiness live in `Config`.

The implementation needs deterministic tests and must not depend on the test runner's real PATH or authentication state. New backend source modules under `apps/backend/` should be written in ReasonML. At the same time, `Runtime_home.ml`, `Config.ml`, and `main.ml` are existing OCaml owners and should not be rewritten wholesale.

## Decision

Create two small Reason helper modules for the feature:

- `Bootstrap_harness_detection.re` owns an injectable probe boundary and produces secret-free Harness detection results, selected Harness metadata, and guidance messages.
- `Bootstrap_settings.re` owns structured `Yojson.Safe` generation for missing Runtime Settings from the selected detection result.

`Runtime_home.bootstrap` remains responsible for idempotent Runtime Home file creation and calls the new helpers only when `.symphony/settings.json` is absent. Generated settings keep all supported Harness definitions for editability, but default Logical Agents route only to the selected Harness. `cursor-force` remains available as an explicit editable Harness definition but is not auto-selected.

Bootstrap detection treats Codex as usable only when the `codex` executable is available. It must not claim full Codex authentication or dispatch readiness, because runtime readiness does not currently validate Codex install and authentication generally. Runtime readiness remains the final dispatch authority for all Harnesses.

Tests use injected probe results plus focused Bootstrap shape and output assertions. They must not require real Codex, Claude, Cursor, or PI installations.

## Alternatives Considered

### Alternative 1: Keep Everything in `Runtime_home.ml`

- **Description**: Add detection, JSON generation, and guidance directly to the existing Bootstrap owner.
- **Pros**: Fewer files and fewer call boundaries.
- **Cons**: Makes a large static-runtime module own probing, selection, JSON construction, and test fixtures.
- **Why rejected**: It concentrates unrelated responsibilities and makes deterministic probe testing harder.

### Alternative 2: Move Detection into `Config.ml`

- **Description**: Extend readiness parsing and validation logic so Bootstrap can reuse Config output.
- **Pros**: Reuses existing selected-Harness readiness concepts.
- **Cons**: Creates an awkward dependency from Bootstrap generation to runtime validation and risks turning detection into runtime authority.
- **Why rejected**: The PRD requires Bootstrap detection to stay provisional while runtime readiness remains authoritative.

### Alternative 3: Generate Only the Selected Harness

- **Description**: Emit a minimal settings file containing only the chosen Harness.
- **Pros**: Smaller generated Runtime Settings.
- **Cons**: Removes useful editable defaults and makes switching Harnesses after Bootstrap more manual.
- **Why rejected**: Keeping all supported definitions preserves the existing examples while selected Logical Agent routes determine readiness impact.

## Consequences

### Positive

- The implementation has a clear deterministic test seam.
- Runtime Home idempotency remains centralized in `Runtime_home.bootstrap`.
- The settings generator can move away from fragile raw string defaults without forcing a `Config.ml` rewrite.
- The generated Runtime Contract preserves existing Harness and Logical Agent boundaries.

### Negative

- The feature adds two backend helper modules and a small amount of threading through existing OCaml owners.
- Some helper functions in `Config` may need extraction or wrapper access to avoid duplicate probing logic.
- Codex detection remains intentionally weaker than Claude, Cursor, and PI detection until full Codex readiness is modeled separately.

### Risks

- **Module cycles**: Keep dependencies one-way from Bootstrap helpers to reusable Config data, not from Config back into Bootstrap.
- **Secret leakage**: Probe outputs and guidance must contain capability names and remediation only, not credential values.
- **Overconfident output**: Guidance must distinguish "selected by Bootstrap" from "ready for dispatch".
- **Mixed OCaml/Reason friction**: Keep new source in Reason and make surgical edits to existing OCaml files.

## Implementation Notes

- The probe interface should be injectable for tests.
- The settings builder should emit `Yojson.Safe` and serialize it for file creation.
- `main.ml` should render Bootstrap guidance alongside the existing Bootstrap report for both `symphony init` and implicit runtime Bootstrap.
- Backend tests should cover Codex-only, Claude-only, Cursor-only, PI-only, multi-Harness priority, no-Harness, existing settings preserved, and secret marker absence.
