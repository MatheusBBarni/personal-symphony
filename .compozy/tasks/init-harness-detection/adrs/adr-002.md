# ADR-002: Optimize MVP Around Transparent Bootstrap Guidance

## Status

Accepted

## Date

2026-05-22

## Context

The PRD for Init Harness Detection needs a product approach that turns the approved idea into user-facing requirements. The primary user is an individual developer creating a new local Workspace Repository. The most important MVP constraint is preserving Idempotent Bootstrap behavior: existing Runtime Contract files must not be overwritten.

The feature should improve first-run setup without making local detection look like permanent runtime truth. Runtime readiness already validates selected Agent Harnesses before dispatch, and that authority should remain visible to the user.

## Decision

The PRD will use the Transparent Bootstrap Guidance approach. Bootstrap may use local Harness detection only when `.symphony/settings.json` is missing, write normal Runtime Settings, and make the Bootstrap output explain what was selected, why it was selected, and what still depends on runtime readiness.

The user-facing promise is clarity first: the operator should understand the generated Harness choice and the next step, whether the result is a detected usable Harness, a provisional default, or no supported Harness found. Existing Runtime Contract files remain untouched.

## Alternatives Considered

### Alternative 1: Ready-to-Run Auto-Selection

- **Description**: Prioritize avoiding selected-Harness readiness gaps by aggressively choosing the most usable detected Harness.
- **Pros**: Best chance of immediate dispatch success when detection is accurate.
- **Cons**: Easier to overstate readiness, harder to explain stale local state, and more likely to blur Bootstrap detection with runtime authority.
- **Why rejected**: The user selected transparent guidance over aggressive readiness optimization.

### Alternative 2: Conservative Guidance-Only Bootstrap

- **Description**: Keep static or near-static settings and only print detection guidance.
- **Pros**: Low risk to defaults and avoids local detection influencing generated Runtime Settings.
- **Cons**: Leaves more manual settings work and solves less of the first-run friction.
- **Why rejected**: It does not go far enough to make the first generated Runtime Contract match the developer's local environment.

## Consequences

### Positive

- The MVP gives users an understandable first-run result instead of a silent or surprising Harness choice.
- Runtime readiness remains authoritative before dispatch.
- Idempotent Bootstrap stays central to the user experience.

### Negative

- Some users may still need follow-up action before dispatch can run.
- The product must define concise Bootstrap output for several local Harness states.

### Risks

- **Ambiguous messaging**: Avoid words that imply dispatch is ready until readiness confirms it.
- **Scope creep**: Defer setup doctor, team policy, and dynamic Harness routing to later phases.
- **User confusion on existing settings**: Make it explicit that existing Runtime Contract files are preserved and not reinterpreted by Bootstrap.

## Implementation Notes

- The PRD should stay business-focused and describe the user's Bootstrap experience, not technical implementation details.
- The PRD should keep no-overwrite behavior, no secret persistence, and runtime-readiness authority as product constraints.
